What we can prove about consistency

October 7, 2026 · 16 min read
Andres Gutierrez
Creator of CamusDB

A database for money needs a report, not a promise.

This post is that report. It follows the shape of a Jepsen analysis: what the system claims, how we tested the claims, what broke, what we fixed, and what we still cannot prove. Jepsen LLC did not write it. We wrote it, with our own harnesses, and two of those harnesses are built on the Jepsen library. Every number below comes from a file in one of four repositories, and the last section tells you how to run the same tests yourself.

The system under test​

CamusDB is a SQL database on three layers. Kommander is the Raft implementation. Kahuna is the replicated transactional key-value store built on Kommander. CamusDB is the SQL engine on Kahuna. A bug can live in any layer, so each layer has its own test suite and its own history of findings.

The claims​

The transaction documentation makes these claims. The rest of the post tests them.

  1. The default isolation level is Serializable, for autocommit statements and for explicit transactions. Read Committed is an explicit opt-out.
  2. A Serializable read-write transaction uses strict two-phase locking. Reads take shared point locks and shared range locks, and hold them to commit. This blocks non-repeatable reads, phantoms, write skew, and lost updates.
  3. A Serializable read-only transaction reads one snapshot, pinned to one hybrid logical clock timestamp. It never blocks and is never blocked.
  4. Deadlocks resolve by wait-die. The older transaction waits and wins. The younger one aborts at once.
  5. A commit is durable when a majority of replicas hold it.
  6. A commit whose outcome the client cannot learn returns one specific error, and the client retries the same commit on the same handle.

One claim is absent on purpose. CamusDB does not claim external consistency or linearizability across transactions. Transaction order is logically consistent through the hybrid logical clock. There is no commit-wait. Keep that in mind when you read the Kahuna and Kommander sections, where linearizability is checked at the key-value and log level.

Four suites test the three layers.

The faults are real. A kill is SIGKILL. A partition is a firewall rule. A slow disk is a kernel I/O limit of 4 KiB per second. A clock jump is a shim on the real-time clock, up to 12 hours.

The two Jepsen suites run every night in CI. Both suites say in their design documents that they are not a per-pull-request gate, because the runs are nondeterministic. A green night is evidence. A red night is a finding to investigate, not always a bug.

Results by layer​

Kommander: the Raft log​

The register workload checks linearizability per key with Knossos. The log-append workload checks the Raft Log Matching Property: every acknowledged entry is present on every replica that answers, no index holds two values, no value applies twice, and application is monotonic.

The register workload found no linearizability violation in any recorded run.

Three findings are open. None of the three is on the default path of a CamusDB cluster today. Key-range sharding and online replica placement are opt-in features. That is a reason to keep them opt-in, not a reason to ignore them.

CamusDB: SQL under faults​

Caraxes runs real SQL through the gRPC client against a three-node cluster, and checks two things that a bank cares about.

The first check is Elle. The append workload runs list-append transactions over 8 keys with 16 workers, and Elle searches the history for cycles under the serializable model. Only a verdict of valid passes. A timeout fails.

The second check is the bank invariant. Transfers move money between random rows, and the sum of all balances must be identical after the run. Since the second dragon post, the verdict reads the sum twice, once through the aggregate and once through a full row scan, and both must match the seed.

These are the most serious CamusDB-level findings of the year, so they get the detail.

A transaction's staged writes lived only in the memory of the partition leader. A leader change dropped them, and nothing told the transaction. The new leader answered the next read with the committed value, and staged the next write from the committed head, as if the key were untouched. The commit then wrote the last staged value and lost the transaction's own earlier write. The base check passed, because no other commit had moved the head. Kahuna 1.10.3 fences the staging chain. A restaged key must sit exactly one revision above the previous staging, and a break refuses the commit.

The same class of bug had a second shape, found by the nightly on Kahuna 1.10.6. A lock also lived only in the leader's memory. After a leader change, a renewal or a shared-to-exclusive upgrade came back as a fresh grant, and the commit never checked that the lock was still held. In between, the new leader granted the same key to a competitor. One writer overwrote a competitor's commit with a value computed from the old row. One reader committed a view of one key at two committed states. The fix on 2026-10-01 refuses a commit whose locks a leader change dropped. Both fixes ship in Kahuna 1.11.2, the version CamusDB uses today, and both carry regression tests in the Kahuna suite.

The honest caveat: the local archive has no leader-transfer Elle run on 1.11.2. The nightly append matrix runs the scenario every night, and the nightly is where the second shape was found. We will post the numbers when a month of nights is in.

The bank invariant history is in the second dragon post. The short version: one dropped transfer leg in 1,805,784 operations, three units out of three billion, found in July and fixed; a chain of eight 45-minute runs that ended with two consecutive clean windows; and a live scan probe after a run returned 1,962 to 1,999 rows out of 2,000 under load. The rule that came out of that chain still holds. A build must pass two consecutive windows before we call it stable.

What this report does not prove​

A consistency report is only as good as its list of gaps. These are ours.

  • No linearizability claim for SQL. Elle checks serializable, not strict serializable. Real-time order across transactions is not asserted anywhere for CamusDB. The register workloads check linearizability for Kahuna keys and Kommander entries, not for SQL rows.
  • Clock faults are thin. Caraxes jumps the real-time clock, and Kommander skews the hybrid logical clock. The Kahuna Jepsen suite does not test clock skew at all. Raft timers run on a monotonic clock, so the exposure is in transaction timestamps, not elections.
  • No disk faults in the Kommander suite. Full-disk and slow-disk faults are Caraxes only.
  • Kill mid-transaction in NUnit is absent. The NUnit restart tests close and reopen a database on one node. No NUnit test kills a Raft node in the middle of a transaction. That coverage lives in the three chaos suites.
  • The 3-node anomaly claim in the docs is not a test. The anomaly suite in NUnit runs on one node. The documentation says the same suite passes on a 3-node cluster, and the Caraxes Elle runs support it, but no checked-in test asserts it.
  • Verification is probabilistic. Several closures rest on an absence. A 1-in-3 bug that passes two runs is not fixed with confidence. The findings files say so for each case, and this post repeats it.
  • Replication factor 1 and online placement are weakly verified. The placement job at factor 1 is bistable in CI, and completed moves at factor 1 are not asserted.
  • One Kommander durability finding is open. An acknowledged append absent from every replica is the kind of bug a bank cannot accept. It has not recurred since August. That is not closure.

How to run it yourself​

Each suite builds the layer from source on your disk.

# Kommander: linearizable register under partitions, 5 nodes
cd kommander-jepsen
lein run test --workload register --faults partition --time-limit 180 --rate 10

# Kahuna: Elle list-append under partition and kill
cd kahuna-jepsen
lein run test --workload append --faults partition,kill --time-limit 180 --rate 10

# CamusDB: Elle list-append during five leader transfers, real Docker cluster
cd camusdb-caraxes
dotnet run --project Caraxes -- run --scenario scenarios/append-leader-transfer.yml

# CamusDB: the bank invariant under a node kill
dotnet run --project Caraxes -- run --scenario scenarios/bank-kill.yml

Every run writes a history, a verdict, and the node logs. A FAIL exits with code 1. The findings files in the two Jepsen repositories are public, and they record the false alarms next to the real bugs.

What this means for a ledger​

A bank asks three questions of a database. Did a confirmed write survive? Did any transaction see half of another? Can you show me?

For the first two, the answer today is: under every fault we inject on the default configuration, with the current versions, the checkers find nothing. Under two opt-in features, key-range sharding and online placement, two anomalies are open. One Raft-level durability defect from August has no root cause.

For the third question, this post is the answer, and it is not finished. The next report will carry a month of nightly leader-transfer results on Kahuna 1.11.2, a strict-serializable Elle arm, and clock skew in the Kahuna suite. A database earns trust on its worst day, and the only way to know what that day looks like is to keep causing it.
