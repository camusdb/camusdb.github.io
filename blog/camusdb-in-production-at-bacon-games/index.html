CamusDB in production at Bacon Games: a first-party report

November 14, 2026 · 9 min read
Andres Gutierrez
Creator of CamusDB

This post describes the CamusDB deployment at Bacon Games: the workload, the cluster, how teams use database branches, the defects that our backend found in CamusDB, and the data that stays on other systems. If you are evaluating CamusDB, it shows you one real production system and its limits.

I wrote CamusDB, and I am the CTO of Bacon Games. This is a report from the team that builds the database, about its own production use. It is evidence that CamusDB runs a real workload. It is no endorsement from an independent customer, and no independent production user is public yet.

What runs on CamusDB​

Bacon Games has used CamusDB since 2025. It is the backend database for many games. All games use one backend platform, and each system of that platform stores its data in CamusDB:

Kind of dataSystems
Player valueWallets and currencies, inventories and item upgrades, rewards, code redemption
PurchasesThe store, in-app purchase receipts, checkout orders, the transaction log
PlayersUsers, identity, devices, sessions, consent records, player statistics
SocialSocial features, presence, leaderboards
Live operationsGame configs, parameters, game events, feature flags, experiments, player segments, scheduled jobs
Messages and contentThe player inbox, player mail, news, localization
MarketingInstall attribution, ad placements, ad conversions

The first group is a ledger. A wallet must never go below zero, an item has exactly one owner, and a reward is granted once. We explained why that workload needs serializable transactions, with a trade between two players in SQL, in Game wallets and inventories need distributed transactions.

The other groups are ordinary relational data. They live in the same database as the ledger, so a purchase, the inventory change, and the inbox message that confirms it can commit in one transaction.

Branches in daily work​

A database branch is an isolated copy of a database that shares the data of its source. A write to the branch never reaches the source. Two teams use branches every day.

Customer support and QA create a branch to examine the case of one player. They can repeat a purchase, grant an item, or run a fix against the real state of that player, and the live data does not change.

Developers create a branch of the development database and work there. A schema change or a test data set of one developer does not break the work of another developer. When the work is done, the developer drops the branch.

The statement is the same in both cases. The names here are examples:

CREATE DATABASE support_case_4812 BRANCH FROM game_prod;

The deployment​

Used since2025
CamusDB version today0.18
ModeCluster mode
Nodes3, each with 4 cores and 16 GB of memory
Where it runsGoogle Cloud
Replication factor3
ClientThe EF Core provider, over gRPC
BackupsPoint-in-time recovery

With three nodes and a replication factor of 3, every node holds a copy of every partition. A write commits when two of the three copies accept it, so the cluster keeps committing while one node is down.

Point-in-time recovery restores the database to a chosen moment inside a retention window, in addition to the moment of the last backup.

Why we run our own database​

Before CamusDB, our games used MongoDB, DynamoDB and Google Cloud Spanner.

MongoDB/DynamoDB. Our data had no enforced structure, so all validation logic lived in the application. Queries that needed joins were hard to write without SQL. The transaction support was too limited for our ledger data.

Google Spanner. It gave us SQL and strong transactions across servers, and it showed us that a database can provide consistency and scale together. It was also costly for our workload, and it was a closed system for us: we could not read the engine, and we could not extend it. It had no database branches, no query result cache, and none of the other features that we later built into CamusDB, such as C# extensions.

CockroachDB/YugabyteDB. These are distributed SQL databases with available source code, and we considered them. Two things kept us from them. A different company directs each product and decides its roadmap and its license. They are also built on other technology: CockroachDB is written in Go, and YugabyteDB is written in C and C++.

That second point matters to us because Bacon Games is a .NET studio. All of our developers work in C#. With CamusDB, the game, the backend, and the database use one language and one toolchain. A backend developer can read the database source, debug it with the usual tools, and write a trigger or a function in C# that runs inside the server.

These are the reasons of one team with one workload. All four products are mature, and all of them run systems much larger than ours.

We chose CamusDB because we build it, so our judgment of this choice has a bias. A team that does not build CamusDB must compare it with PostgreSQL and with the established distributed SQL databases for its own workload. Why CamusDB? lists the cases where CamusDB is a weaker fit, and The origins of CamusDB gives the longer history.

Defects that our backend found​

Our backend is the first heavy user of each CamusDB release, so it finds defects before other users do. We keep a record of each one. This is that record.

Two defects had the largest effect:

A commit that never returned. EF Core saved the changes inside an explicit transaction, and the commit that followed did not complete and gave no error. Config writes from our operations portal stopped. A driver release fixed it.

A filter that became slower with each row. A filter with a correlated EXISTS subquery ran the subquery as a scan for each candidate row, at 3 to 30 ms per row. A filtered page of an inventory with 300 items reached the 10-second timeout. The query also became slower when other players had more rows. The planner now reads the subquery table through its primary key, the same queries on 1,200 items complete promptly, and two regression tests hold that result.

Twelve of the fifteen entries are fixed. The entries that remain are one server defect with a driver workaround, one preset that needs a clear error, and one upgrade order that you must follow.

Most of these defects are in the driver, the EF Core provider, and the query planner. Caraxes, our fault-injection harness, tests a different layer: it kills nodes, cuts the network, and fills disks while it checks that no committed data is lost. A real application that uses the provider every day found what the fault tests do not look for.

What does not run on CamusDB​

Analytics data runs in ClickHouse. ClickHouse is an analytics database, and CamusDB is built for transactions. Large scans and aggregations over event history belong in a system that is designed for them.

What this report shows​

  • CamusDB holds authoritative production data for a real product.
  • It replaced MongoDB and Spanner for many games, and it has run in production since 2025.
  • Database branches are part of the daily work of support, QA, and development.

It does not show these things:

  • That CamusDB fits a workload that is different from ours.
  • How CamusDB behaves at a size larger than the deployment above.
  • That a team without the authors of the database can operate it. We fix the engine ourselves when production finds a defect.

CamusDB is still young, and APIs and storage formats can change between versions. See Current scope.

If you want to try CamusDB and find anything to improve tell us in a GitHub issue. A report from an independent team is worth more to other readers than this one.
