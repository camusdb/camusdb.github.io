Transactions and isolation

Two requests withdraw 100 from an account that holds 150, at the same moment. Each one reads 150 and writes the new balance. If both succeed, the account pays out 200 from 150. PostgreSQL defaults to Read Committed and MySQL to Repeatable Read, and at those levels this can happen unless you add explicit locks. CamusDB runs transactions as serializable by default, so one withdrawal commits and the other gets a conflict that your application retries. You keep the data correct without extra locks, version checks, or "check and then write" logic in your code.

Every statement CamusDB runs is inside a transaction. If you do not open one, the server opens a transaction around your statement and commits it for you.

CamusDB always guarantees that:

  • Writes are atomic.
  • Commits are durable.
  • There are no dirty reads (reads of data that another transaction has not committed yet).
  • Write-write conflicts are detected.
  • Execution is serializable by default.
  • A write across more than one partition (a slice of the data that the cluster replicates as one unit) is atomic, through two-phase commit.

This page describes the guarantees. For the SQL syntax, see Transactions In SQL.

What serializable protects you from​

When many clients change the same data at the same time, two transactions that are each correct on their own can produce a wrong result together, as in the withdrawal example above.

Serializable isolation stops this class of error: the result is always the same as running the transactions one after the other. In the example, CamusDB commits one withdrawal and aborts the other with a conflict. When your application retries it, the retry sees the new balance of 50. See Retries and conflicts.

This matters most for data where a wrong answer is expensive: money, inventory, reservations, and ownership.

Isolation levels​

There are two levels, and Serializable is the default.

LevelReadsProtects against
SERIALIZABLESnapshot, or locking scans in read-write modeRead skew, phantoms, write skew, lost updates
READ COMMITTEDCommitted MVCC versions, skipping write intentsDirty reads and write-write conflicts only

Serializable means the result is the same as running the committed transactions one at a time, in some order. Read Committed is an explicit opt-out for workloads that must not pay the cost of Serializable.

Set the level in the first statement of a transaction:

BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

The statement must come before any read or write, because an earlier statement would already have missed the locks and snapshot setup that the level needs. CamusDB rejects a late change of level rather than pretending it applied.

What Read Committed gives up​

Read Committed keeps these properties:

  • Reads return committed versions only, skipping uncommitted write intents.
  • Writes still use locks, write intents, and atomic commit.
  • Readers block neither readers nor writers.

It gives up:

  • One snapshot shared by every sub-read of a query.
  • Repeatable reads across a multi-statement transaction.
  • Phantom protection on range scans. A phantom is a row that appears in a repeated scan because another transaction inserted it.
  • Write skew protection. Write skew is a fault in application code that reads a value, makes a decision, and then writes.

Under pessimistic Read Committed, a point read can record the row revision it saw when the same transaction later writes that key, but this is not a general repeatable-read guarantee. A range scan does not pin every scanned row. It returns each row's latest committed version as pages are read, which is the non-repeatable behavior this isolation level permits.

A single UPDATE or DELETE statement still protects itself from lost updates. It first finds candidate rows, then takes exclusive row locks, reads those rows again, re-evaluates the WHERE clause, and computes the write from that locked read. In practice, UPDATE accounts SET balance = balance + 1 WHERE id = ... adds to the latest committed balance. Rows that a concurrent commit moved out of the predicate are skipped, and so are deleted rows. A read in one statement followed by a write in a later statement is different; for that, use Serializable or express the change as one UPDATE.

Read-only and read-write modes​

Serializable has two execution modes, and choosing between them matters more than any other decision on this page.

A serializable read-only transaction fixes one snapshot timestamp at BEGIN, and every statement reads from that snapshot. Later commits stay invisible and repeated reads are stable, all without locks. CamusDB can hold the snapshot across several requests when the client resumes the same transaction id, so this mode suits multi-query reports, not just single statements.

BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE READ ONLY;

A serializable read-write transaction adds locks on top of MVCC (multi-version concurrency control, where a write creates a new version instead of overwriting). A point read can hold a shared point lock, a scan can hold a shared range lock, and a write takes exclusive key-level protection. No other transaction can change a key that this transaction read and still commit. The cost is that a conflicting transaction may have to retry.

Use read-write mode when correctness depends on a read-then-write invariant. Use read-only mode for reports, and for reads that need consistency but must not block writers.

Locking​

As a user, you deal with write locks and read locks.

Every write takes a per-key lock and places a write intent (a provisional version that becomes final at commit) on each key it modifies. Together these give you:

  1. Write-write conflict detection on rows.
  2. Conflict detection on unique indexes.
  3. Atomic updates of a row together with its index entries.

Point read locks and range read locks protect what a serializable read-write transaction reads. A shared point lock covers the exact key the transaction read, so a concurrent writer cannot modify that key and still commit. If the same transaction later writes the key, CamusDB promotes the lock to write protection. For a scan, a shared range lock covers the scanned span. Two overlapping scans can still run at the same time, while a conflicting write into the range waits or retries.

When two serializable transactions conflict, CamusDB resolves the conflict by age (the wait-die rule). An older requester waits for the younger holder. A younger requester that already holds a lock or a staged write aborts at once and must retry. CamusDB does not search for wait cycles: because only an older transaction ever waits, a cycle cannot form. A transaction that has not yet held a lock or staged a write can safely wait for a short in-flight writer, because it is not itself blocking anyone.

When a transaction holds lock_escalation_threshold (default 50) shared point locks in one table bucket or one index bucket, CamusDB escalates them, replacing them with one shared lock over that whole bucket. Bookkeeping stays bounded, but the protected range gets wider.

Pessimistic and optimistic locking​

The default strategy is pessimistic: CamusDB takes a lock before any conflicting work continues.

Optimistic locking is opt-in. It skips the exclusive write lock and validates at commit instead, aborting the transaction if another transaction wrote a key that this transaction wrote, or if a row this transaction read has changed. The application then retries from the start.

BEGIN;
SET TRANSACTION LOCKING OPTIMISTIC;

The locking strategy is a separate axis from the isolation level, and the combination decides the guarantee:

CombinationBehavior
SERIALIZABLE + pessimisticDefault. CamusDB takes the locks first.
SERIALIZABLE + optimisticHybrid. Writes validate at commit, but reads and scans still take shared locks, so phantoms remain excluded.
READ COMMITTED + optimisticNo locks at all. CamusDB validates only the observed rows. There is no phantom protection.

SET TRANSACTION LOCKING must also run before any data statement, and you can combine it with SET TRANSACTION ISOLATION LEVEL in either order. HTTP and gRPC clients select the strategy with the locking request field. Operators change the server-wide default with default_transaction_locking.

How a write commits​

Each INSERT, UPDATE, or DELETE places write intents and takes key-level locks on the row and index keys it changes, then commits them atomically. If another transaction is already writing a conflicting key, one side fails or retries; neither silently overwrites the other. For the full commit path, including two-phase commit across partitions, see How a commit works.

Multi-statement transactions​

Use an explicit BEGIN when:

  1. Several writes must commit together.
  2. A read-write sequence must be all-or-nothing.
  3. Several queries need one stable serializable snapshot.

Aborts are normal here, not exceptional. CamusDB does not replay an aborted multi-statement transaction for you: the client restarts from BEGIN. Retries and conflicts lists the causes, the error codes that are safe to retry, and the driver helpers that replay a unit of work for you.

One failure is not a retry signal: TransactionMutationLimitExceeded means the transaction is too large, and replaying the same batch fails again. See Transaction Limits.

Timestamps and schema safety​

Every read-write transaction gets a timestamp from Kahuna, the transactional storage layer. The timestamp comes from a hybrid logical clock (HLC), which combines physical time with a logical counter. Clients never assign their own timestamps. The timestamp identifies the transaction, orders committed versions, and coordinates the distributed commit. The resulting order is logically consistent, but it is not a real-time wall-clock guarantee. See Distributed Transactions And HLC.

CamusDB also pins the schema version of each table a transaction touches. If a table changes incompatibly before the commit, CamusDB rejects the transaction rather than commit a write that mixes an old layout with a new one.

Single node and cluster​

The model is the same in both: MVCC reads, locks and write intents on writes, and conflicts that are detected rather than ignored. A cluster adds routing to partitions and two-phase commit across them. See Distributed transactions.

Serializable is not a single-node feature. CamusDB runs its anomaly coverage on a single node and on a three-node cluster, including read-write transactions across more than one partition.

What is guaranteed today​

Serializable is complete, acceptance-tested, and the default. It covers read skew, phantoms, write skew, and lost updates.

A transaction that spans more than one partition runs in cluster mode, which is still an alpha feature. Its APIs and behavior can change between versions. See Distributed Transactions.

The implementation includes:

  • Wait-die deadlock fairness, so two contending transactions have a determinate winner.
  • Coordinator renewal of range locks for long transactions.
  • Lock escalation after lock_escalation_threshold (default 50) shared point locks in one table or index bucket.
  • Tight predicate-lock bounds for bounded scans, UPDATE, and DELETE.

One gap remains: there is no externally consistent commit-wait guarantee. The order is logically consistent, but not tied to real time.
