Configuration

A node's configuration controls how it starts and runs: its ports, data directory, standalone or cluster mode, TLS, storage engine, caches, and background jobs. The Settings reference lists every key.

You do not need a configuration file to start a local node; the built-in defaults work for development and for the tutorial. Edit the configuration when you:

  • Prepare a node for production, for example with a data directory on a dedicated disk, TLS, and authentication.
  • Set up a cluster. Each node needs its name, its peers, and the partition count.
  • Turn on a feature that is off by default, such as spill to disk or performance diagnostics.
  • Deploy C# extensions that add scalar functions, triggers, or procedures to a node.

Some settings can change while the cluster runs, without a restart. See Runtime cluster settings. To see the values a running node uses, run SHOW VARIABLES.

The configuration file​

CamusDB reads the first configuration file it finds at startup. For an installed node, run camusdb init to write a user-owned starter file:

camusdb init

That creates ~/.camusdb/config.yml on macOS and Linux, or %APPDATA%\camusdb\config.yml on Windows. Set CAMUS_HOME to relocate both the user configuration and the default data directory.

The source-tree CamusDB/Config/config.yml is an annotated reference. It is not the right place to keep settings for an installed node, because a checkout or pull can replace it.

CamusDB merges the selected YAML file with CLI flags and environment variables into one resolved configuration object.

Configuration discovery​

CamusDB searches in this order:

  1. --config <path>
  2. CAMUS_CONFIG_PATH
  3. ./camusdb.yml
  4. ./Config/config.yml
  5. ~/.camusdb/config.yml on macOS/Linux, or %APPDATA%\camusdb\config.yml on Windows
  6. built-in defaults

If --config or CAMUS_CONFIG_PATH names a missing file, startup fails instead of silently falling through to another location.

To see what a node resolved, run SHOW VARIABLES against it instead of reconstructing the merge by hand. The output names the layer that supplied each value.

Precedence​

The highest layer wins:

  1. A CLI flag. Only flags you pass explicitly override YAML; the options are nullable and have no sentinel defaults.
  2. An environment variable. CAMUS_KEY_RANGE_SHARDING overrides key_range_sharding. Authentication is switched on with CAMUSDB_AUTH_ENABLED, and its secrets are read only from the environment.
  3. config.yml.
  4. The built-in default, listed in the settings reference.

For example, if YAML holds mode: cluster, passing --mode standalone starts the node in standalone mode. Without a --mode flag, the node stays in cluster mode.

Inline C# functions and triggers​

Inline definitions let database users create C# functions and row triggers without deploying DLLs. Both creation features are off by default and enabled independently:

inline_functions_enabled: true
inline_triggers_enabled: true

Restart after changing these settings, and use the same cluster-scope values on every node. Disabling a feature prevents new definitions; existing functions remain callable and existing triggers still fire. See C# inline functions, inline triggers, and the budget settings.

Inline bodies are checked against an allowlist and execute with resource budgets. Checks happen between framework operations; a process heap hard limit is the memory backstop. See memory-proportional cache defaults.

HTTP/3 on the HTTPS port​

The REST API can also serve HTTP/3 over QUIC. HTTP/3 is off by default; to turn it on, set http3_enabled: true and give the node an HTTPS certificate:

https_port: 7141
https_certificate: /etc/camusdb/api.pfx
http3_enabled: true

The HTTPS port then serves HTTP/1.1, HTTP/2, and HTTP/3. The setting is read when the node starts, so changing it requires a restart.

HTTP/3 requires:

  • TLS. HTTP/3 always uses TLS, so the setting applies to the HTTPS port only. Without https_certificate, the node has no HTTPS port and the setting has no effect. The plain HTTP port, the Raft port (node-to-node cluster traffic), and the gRPC port do not change.
  • UDP. QUIC uses UDP, so open https_port for both UDP and TCP, in the firewall and in any container port mapping, for example -p 7141:7141/tcp -p 7141:7141/udp.
  • A QUIC library. Linux and macOS need libmsquic. Windows needs Windows 11, Windows Server 2022, or later. Without the library, the port serves HTTP/1.1 and HTTP/2 only. On macOS, .NET does not search the Homebrew library folder by default, so start the node with DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib. macOS strips DYLD_* variables for system binaries such as nohup, so set the variable in the node process's own environment.

Clients that connect over TCP receive an Alt-Svc header on each response, telling them the same port serves HTTP/3. Browsers and other HTTP/3-capable clients then use it for later requests.

If http3_enabled is on but HTTP/3 cannot start, the node still starts and logs a warning that names the cause: no https_certificate, or no QUIC library. SHOW CONNECTIONS shows an HTTP/3 connection with the protocol HTTP/3.

gRPC listener​

The client-facing gRPC API is enabled by default:

grpc_enabled: true
grpc_port: 5096
grpc_batch_max_in_flight: 64
grpc_tls_enabled: true

grpc_port is separate from the HTTP API port. When raft_certificate is set, CamusDB reuses that certificate for the gRPC listener unless grpc_certificate names a separate PFX certificate. Otherwise the listener uses plaintext HTTP/2, which is suitable for local development and trusted private test networks.

Set grpc_tls_enabled: false to force plaintext h2c (HTTP/2 without TLS) on the client-facing gRPC port even when grpc_certificate or raft_certificate is configured. This does not change the Raft port. Use it only on a trusted network or behind a proxy that terminates TLS for clients.

Use grpc_certificate when the Raft port and the client-facing gRPC port serve different trust domains. A cluster-internal certificate is often right for Raft, while clients need a certificate that their own trust store accepts.

grpc_batch_max_in_flight bounds how many operations one BatchExecute stream can run at once before the server applies backpressure.

See gRPC API.

Cluster peer transport​

In cluster mode, CamusDB uses peer HTTP endpoints for schema-DDL forwarding, cluster-settings forwarding, and query-fragment exchange. Set peer_tls_enabled: true when those peer HTTP endpoints serve HTTPS:

peer_tls_enabled: true

An http_peers entry with an explicit https:// scheme overrides this default for that peer. Without peer TLS, the shared node secret that internal routes use travels over plaintext peer HTTP. CamusDB logs startup warnings for exposed cluster configurations that leave peer HTTP, Raft gRPC, or client-facing gRPC traffic in plaintext.

Dashboard​

The read-only operator dashboard is enabled by default on the HTTP port:

dashboard_enabled: true
dashboard_refresh_seconds: 2

Disable it with dashboard_enabled: false; the dashboard pages and endpoints then return 404. With authentication disabled, the dashboard is loopback-only. With authentication enabled, it uses a dashboard session cookie and applies the user's privileges to each panel.

See Operator Dashboard.

Slow query log​

The slow query log is off by default:

slow_query_log_enabled: false
slow_query_log_threshold_ms: 1000
slow_query_log_max_entries: 200
slow_query_log_max_sql_length: 4096

Turn it on when you are diagnosing a node. It records qualifying statements in a bounded in-memory ring and exposes them through SHOW SLOW QUERIES. The log is node-local and does not survive a restart. If the node started with the log off, it can still be enabled at runtime.

See Slow Query Log.

Statement statistics and index usage​

Use statement statistics to find expensive repeated query shapes and index usage to assess indexes against their write cost:

statement_stats_enabled: false
statement_stats_max_shapes: 2000
index_usage_enabled: true

The two enable flags can change at runtime. Shape capacity requires a restart. Both features keep in-memory, node-local totals that reset when the node restarts.

Key-range sharding and range splits​

key_range_sharding defaults to false for new clusters. The cluster records its routing mode at creation; a restart cannot change it on existing data:

key_range_sharding: false

When it is on, eligible table and index key spaces can split by key range instead of staying on one hash-routed partition. The nested kahuna: settings control automatic splitting:

kahuna:
  range_split_threshold: 0
  range_split_min_range_size: 10
  range_split_load_threshold: 500
  range_split_load_min_queue_depth: 8
  range_split_load_min_commit_wait_ms: 0
  range_split_load_window_ms: 15000
  range_split_load_poll_interval_ms: 5000
  range_split_load_imbalance_max: 0.8
  range_split_settle_window_ms: 10000
  range_split_indivisible_cooldown_ms: 300000
  range_move_settle_timeout_ms: 10000
  range_merge_min_size: 10
  enable_load_reports: false

Both kinds of split stay off until you set a threshold for them. Count-based splits use range_split_threshold. Load-based splits use range_split_load_threshold, gated by queue depth and, optionally, commit wait.

See Key-Range Sharding and SHOW RANGES.

Transaction outcome retention​

Kahuna can keep a transaction's final outcome record after the transaction finishes. CamusDB uses these records when a finalize path needs to resume, or to diagnose an uncertain commit outcome:

kahuna:
  transaction_outcome_retention_ttl_ms: 600000
  transaction_outcome_retention_max: 100000

transaction_outcome_retention_ttl_ms sets the age window; 0 disables age pruning and leaves only the size cap. transaction_outcome_retention_max sets the maximum number of retained records. For an investigation or a long fault-injection run, raise both together, because a large TTL does nothing if the count cap evicts records first.

Kahuna engine section​

The nested kahuna: map tunes Kahuna, the transactional key/value layer embedded in each node, and through it Kommander (the Raft library) and the on-disk engine: RocksDB by default, with SQLite and Solarium as alternatives. See Architecture: storage components for their roles. CamusDB applies the map in both standalone and cluster mode, and an unset key keeps the CamusDB baseline for that mode. The node reads the map once at startup, so a change requires a restart.

Kahuna keys lists every accepted key with its default. An unknown key fails validation at startup, and the error message lists every accepted key. The kahuna: block in CamusDB/Config/config.yml is commented out and documents each key inline.

storage_revision names the directory that Kahuna opens under {data_dir}/kv. The current CamusDB baseline pins it, together with the WAL revision, to the current key layout. Do not set it to an older revision to reach older data. A server that finds an older revision directory leaves it untouched; to move data across revisions, use a logical dump and reimport.

Kahuna serves keys and locks through a fixed set of in-memory workers called actors (key_value_workers and locks_workers). Each key-value actor caches the entries it serves, and evicts them in two ways:

  • A size cap: max_entries_per_actor and max_bytes_per_actor bound what one actor holds in memory.
  • A timed collection sweep: every collection_interval_ms, a pass evicts up to cache_entries_to_remove entries older than cache_entry_ttl_ms.

Three keys govern Raft log compaction: compact_every_operations sets how often it runs, compact_number_entries sets how many trailing entries stay, and max_entries_per_compaction caps how many entries one pass removes.

compact_every_operations counts persisted WAL batches, not individual log entries. A busy batch can hold many entries, so this setting is a compaction cadence rather than a direct row count. With the RocksDB Raft log, a pass also drops whole files that lie below the persisted compaction floor, so it can free more disk than max_entries_per_compaction suggests. This holds for the Kahuna 1.12.8 release that CamusDB ships with.

The storage backends are memory, sqlite, rocksdb, and solarium.

RocksDB buffers recent writes in memory (memtables) and flushes them to sorted files on disk (SST files). See The RocksDB backend.

kahuna.rocksdb_direct_reads is off in CamusDB's baseline. With the default buffered reads, a read that misses the RocksDB block cache and goes to an SST file can be served from the operating system page cache, which helps when the same disk is also handling Raft WAL fsyncs. Set it to true when you need RocksDB reads to bypass the page cache and rely on the RocksDB block cache alone.

Storage damage and lost log entries​

With RocksDB or Solarium, a store that detects damage stops serving data. The node gives up leadership and withholds candidacy; it does not rewrite the damaged files. Reads that surface CADB0837 StorageCorrupted have failed, rather than found no rows. Do not retry this error as a transient transaction conflict. See storage health for monitoring.

After a restart, kahuna.raft_lost_acknowledged_entries_policy controls a replica that discovers it lost log entries it had acknowledged:

ValueBehavior
quarantine (default)The replica neither votes nor campaigns until its leader repairs it. With one replica there is no peer to repair from, so the partition stays leaderless and emits a Critical log.
accept_and_logAccepts and logs the loss, disabling this safety fence. It does not restore entries; with one replica the loss is permanent.

Changing the policy requires a restart. It is separate from repairing damaged storage or restoring a backup.

Solarium's adapter now implements the storage-damage contract, including stopping service and reporting a fault when corruption is detected. These protections remain backend-specific: SQLite lacks page checksums, and its WAL replay can stop at a damaged frame. Its Raft metadata uses synchronous=NORMAL regardless of wal_sync_writes. A healthy endpoint alone does not verify every stored byte.

Solarium storage engine​

Solarium is a managed key/value engine that can store the KV state, the Raft WAL, or both without a native RocksDB library. CamusDB includes and registers its providers; no extension DLL is needed:

kahuna:
  storage: solarium
  wal_storage: solarium
  solarium_environment: default

All nodes must agree on storage and wal_storage. Solarium and RocksDB files are incompatible; switch engines using a logical dump and reimport, not by opening existing files with another engine. PITR bootstrap through pitr_bootstrap_from still requires RocksDB for both layers.

solarium_environment selects file I/O for both Solarium layers. default uses the portable environment; io_uring needs a Linux kernel able to create a ring, otherwise startup fails. RocksDB tuning and WAL-shard settings do not apply to Solarium, except the two shared-budget keys below.

Cache and memtable budgets​

Solarium 0.1.4 and later hold memtable entries and cached data blocks in native memory. Index and filter partitions and their handles remain managed; the partitions account for roughly 2% of table bytes. Shared cache and memtable budgets therefore sit outside the GC heap limit, while still counting toward the node or container's total memory use.

rocksdb_shared_memory_budget_mb and rocksdb_shared_memtable_budget_mb configure Solarium's shared cache and memtable sub-budget. Positive budgets are shared regardless of rocksdb_shared_memory; that boolean controls RocksDB sharing only. Unset prod budgets derive from machine or container memory, as they do for RocksDB. Explicit values win.

The startup log identifies these budgets as native. The older warning about them exceeding one third of the managed heap was removed. Leave room for native storage budgets alongside the managed application and actor caches. Node stats reports gc_memory_limit_bytes.

The Solarium WAL's flush unit plus headroom is 256 MiB. The computed memtable budget tries to cover it, but stops at half the shared cache. With 10% cache sizing, that unit fits from roughly 5 GiB of machine memory. Smaller nodes can log budget-forced WAL flush warnings; size both budgets explicitly to cover it.

Flush and compaction pacing​

For either RocksDB or Solarium, storage_compaction_rate_mbps limits KV-store flush and compaction writes in decimal MB/s; zero or unset leaves them unpaced. storage_max_background_compactions sets parallel compactions; zero or unset uses the engine default. Both are nonnegative, restart-time settings.

Solarium defaults to one compaction at a time without pacing. Setting a rate also enables max(2, CPUs / 2) compactions unless an explicit concurrency wins. RocksDB defaults to max(2, CPUs / 2). Choose pacing for the disk and workload: too little bandwidth lets pending compactions accumulate and can slow writes.

One-phase apply-time validation​

kahuna.one_phase_apply_time_validation is on by default. It lets an eligible read-modify-write transaction commit in one durable Raft round instead of the normal two-phase path. To be eligible, the transaction must have one participant partition, its anchor on that partition, and a read set that can be validated there. Cross-partition transactions still use two-phase commit.

kahuna.staged_base_fence_retention_ms (default 600000) is how far back the validation fence and committed-head ledger remember transactionally written keys. Set it above the longest transaction lifetime your deployment allows; otherwise long transactions can be refused because their validation base fell out of the retained window.

Treat the setting as a cluster-wide operational switch:

  • Give every node the same values for both keys.
  • During a rolling upgrade across Kahuna versions, set one_phase_apply_time_validation: false until every node runs a version that supports the apply-time check.
  • When you start a data directory or snapshot that predates the committed-head ledger, start once with the setting off and let a checkpoint run. After that checkpoint rewrites the ledger, remove the override and restart.

Persistent MVCC revision retention​

Kahuna keeps several versions of each row so that readers see a consistent snapshot (MVCC). Every version of every row is stored physically in the key-value layer, so without pruning, a hot table's retained history and disk usage grow for the life of the store.

When both retention keys are unset, CamusDB keeps persisted history by age, aligned with the effective point-in-time recovery window (kahuna.pitr_window_seconds, default 3600). In-window restores stay valid, and older revision rows can be reclaimed. Snapshot reads older than the retention age are not guaranteed. Branch forks pin their own snapshot floors, and reclamation honors those pins while they remain protected.

  • kahuna.persistent_revision_retention_age_seconds sets an explicit age bound. It must be at least the effective PITR window. 0 disables age pruning.
  • kahuna.persistent_revision_retention_count sets a hard per-key revision cap. The default 0 disables it. A count cap can trim history below the PITR window on hot keys, so prefer the age bound unless you specifically want a per-key cap.

Write aggregation​

Kahuna groups key-value writes into Raft batches before replication:

  • kahuna.key_value_write_max_in_flight_batches_per_partition (default 1) controls how many write batches a partition may have waiting on Raft at once. Higher values pipeline batches, but change it only after an A/B test on the workload you are tuning.
  • kahuna.key_value_write_linger_ms (default 1) is how long the oldest queued write may wait, while nothing is in flight, before a batch is dispatched.
  • kahuna.key_value_write_max_batch_items (default 512) caps the number of items in one write batch.
  • kahuna.key_value_write_post_completion_hold_ms (default 1) waits after a batch completes before dispatching the next one. CamusDB ships a nonzero default to increase batch density at full occupancy. Set it to 0 to restore Kahuna's dispatch-at-once behavior.
  • kahuna.key_value_write_precise_wake (default false) moves the write aggregator's hold, linger, and queue-age wakeups onto a dedicated timer thread. Use it when testing low-latency write aggregation, because it can wake closer to the configured millisecond deadline than the shared timer queue.
  • kahuna.key_value_write_fill_target_trigger (default false) dispatches a held or lingering partition buffer as soon as it reaches the learned fill target, instead of always waiting for the timer. Kahuna keeps probing the timer path so the target can follow the current load.

These settings affect write latency and throughput. Record them alongside benchmark results, because runs with different batching settings are not directly comparable.

Raft WAL shard column families​

Eight kahuna.wal_shard_* keys override the RocksDB column-family settings for the Raft log. CamusDB leaves them all unset by default, so Kommander's measured defaults apply field by field. They take effect only when kahuna.wal_storage is rocksdb.

KeyKommander defaultMeaning
wal_shard_write_buffer_size_mb64Size of one shard memtable.
wal_shard_min_write_buffer_number_to_merge2Immutable memtables merged into one flush.
wal_shard_max_write_buffer_number4Memtables per shard, mutable plus immutable. Must exceed the merge count.
wal_shard_level0_file_num_compaction_trigger8L0 files that trigger compaction.
wal_shard_level0_slowdown_writes_trigger28L0 files at which writers are slowed.
wal_shard_level0_stop_writes_trigger44L0 files at which writers are stopped.
wal_shard_max_bytes_for_level_base_mbRocksDB's 256Base-level size for leveled compaction.

Treat these as storage-engine tuning knobs. Larger flush units can reduce write amplification in the Raft log, but they also raise memory pressure and restart replay work. If wal_shard_universal_compaction is true, wal_shard_max_bytes_for_level_base_mb has no effect, because RocksDB ignores level sizing under universal compaction.

Memory profile​

memory_profile (or --memory-profile) selects the defaults for the four cache-size settings below, and nothing else. It does not change the number of workers or durability. The only effect an application can observe is how often a read comes from cache instead of disk.

ProfileBlock cacheMemtable sub-budgetActor cachesTotal
prod, the default10% of machine memory (RocksDB or Solarium), up to 2 GiBOne quarter of the block cache, raised to the Raft-log flush unit when possible, up to 1 GiB6.25% of the managed heap budget, 64 MiB or moreDepends on engine and heap limit; see cache sizing below
dev64 MiB16 MiB32 MiBAbout 96 MiB, on any machine

Use dev for a node that shares a developer machine with the application you are building. Its budgets are fixed, so the node is the same size on a 64 GiB workstation and in a 2 GiB container.

The cost of dev is throughput once the working set outgrows the cache (see the TPC-C measurement under Cache defaults proportional to memory), so dev is not a server setting.

An explicit kahuna.* budget always beats the profile, so dev with one raised budget is a valid combination, not a conflict.

The caches are ceilings, and CamusDB fills them lazily. A burst of large writes can still push the process's resident memory far above the cache total. That peak is dominated by transient managed allocations and the .NET garbage collector. The server garbage collector is the default and uses one heap per core. DOTNET_gcServer=0 in the environment controls that half of the memory footprint; it is a runtime setting, not a CamusDB setting.

CAMUS_THREADPOOL_MIN_THREADS overrides CamusDB's .NET worker-thread floor. The default floor is 1024 worker threads, with a completion-port floor of 512. Use the override for controlled load tests or diagnostics when runtime metrics show work queued in the thread pool. It is an environment variable and takes effect when the process starts.

Cache defaults proportional to memory​

Under memory_profile: prod, most unset keys keep the Kahuna default. The four cache-size settings are the exception: when you leave them unset, CamusDB computes them at startup from the node's memory instead of using a fixed constant.

Two memory sizes feed the computation:

  • Machine memory sizes the RocksDB and Solarium block cache and memtable budgets. It is the container cgroup limit when one is set, otherwise physical RAM.
  • The managed heap budget sizes the actor caches. It is the GC-reported limit: an explicit hard limit, the runtime's container default (normally 75% of the container limit), or machine memory when no heap limit applies.

RocksDB and Solarium use native memory for these storage budgets, which sit outside a .NET heap hard limit but still count against the container. Leave room for both when you set DOTNET_GCHeapHardLimit, DOTNET_GCHeapHardLimitPercent, or related runtime limits.

A measurement motivated this behavior. A fixed 320 MB block cache forced a 1.2 GB TPC-C working set through a disk read on almost every statement. Sizing the cache to the machine took the same workload from 24.5 to 119.6 transactions per second, at 8 clients.

KeyComputed value when unsetClamp
rocksdb_shared_memory_budget_mb10% of machine memory (RocksDB or Solarium)64 MiB to 2 GiB; the 320 MiB floor yields on small nodes
rocksdb_shared_memtable_budget_mbOne quarter of the block cache, raised to the Raft-log flush unit when possible16 MiB to 1 GiB; the 128 MiB floor yields on small nodes
max_bytes_per_actor6.25% of the managed heap budget, and at least 64 MiB for the layer, divided by key_value_workers1 MiB to 2 GiB for each actor; the 8 MiB floor yields on small nodes

Across the two cache layers, the total never exceeds 4 GiB, however large the machine.

The fractions and ceilings are conservative because an unconfigured node is more often a developer workstation, or a CI container sharing the machine with a compiler and an editor, than a dedicated database server.

For example, on an 8 GiB machine with 8 cores, no heap limit, and none of the four keys set, the block cache is 819 MiB and the memtable sub-budget is 204 MiB. The 8 cores give 32 key-value workers, each with a 16 MiB actor cache, for 512 MiB together. The total is about 1.3 GiB.

On a dedicated server, raise all four values explicitly. The computed sizes are a floor to build from, not a recommendation for a machine whose only job is CamusDB.

The 6.25% share and its 64 MiB floor bound the actor-cache layer as a whole. CamusDB divides that budget by key_value_workers (default max(32, 4 × CPU cores)), and only the 8 MiB minimum applies per actor. More cores divide the same budget into more parts rather than enlarging it, so a machine with many cores and little RAM does not get a multiple of the intended share. Because max_bytes_per_actor applies to one actor, multiply it by key_value_workers to get the total.

The two RocksDB budgets are shared by the KV store and the Raft WAL. See Shared RocksDB memory for how rocksdb_shared_memory works and when it applies.

CamusDB charges the memtable sub-budget inside the block-cache budget rather than adding it on top, so the sub-budget must not exceed the total. CamusDB compares the two values after merging all layers, so overriding only one of them can produce an inconsistent pair, such as a 100 MiB total with an explicit 512 MiB memtable budget. Set both values together. The computed memtable default never exceeds the total, including the flush-unit floor.

When rocksdb_shared_memory is on and both the KV store and the Raft WAL use RocksDB, CamusDB tries to keep the computed memtable budget large enough for the Raft-log flush unit, which is 192 MiB at the default WAL shard settings. If a small container cannot fit that budget inside half of the block cache, CamusDB keeps the smaller percentage-based value and Kommander logs a startup warning. If that warning matters for your workload, raise both RocksDB budgets explicitly or reduce WAL shard sizing.
