Workload utility

CamusDB.Workload measures and checks a CamusDB server under load. It creates a repeatable data set, and it sends reads and writes through the CamusDB client. After the run, it verifies the data. The results are written as files that you can compare between two server builds or two configurations.

You can use it for the following tasks:

  • Check that a deployment handles concurrent reads and writes correctly.
  • Measure the effect of a configuration change, such as a write-ahead log (WAL) setting.
  • Compare the gRPC client with the REST client.
  • Record a baseline from repeated measurements, and test a later build against it.

The utility is in the CamusDB source repository. Start it with dotnet run from a checkout. To drive the same workload against a Docker cluster while faults are injected, see Caraxes.

Data set​

The default workload uses this table:

CREATE TABLE workload_accounts (
  id OID PRIMARY KEY,
  owner INT64 NOT NULL,
  balance INT64 NOT NULL,
  version INT64 NOT NULL,
  payload STRING NOT NULL
);

CREATE INDEX workload_accounts_owner ON workload_accounts (owner);

The rows are generated from the seed, the row count, and the payload size. The same values give the same data set fingerprint. The run command uses the fingerprint to check that the data is what it expects.

With --tables above 1, the rows are spread over workload_accounts_00, workload_accounts_01, and so on. This puts data on each partition, for a workload that touches several key ranges. Use the same --tables value for init and run.

Setup and the checks after the run aren't part of the measured interval.

Initialize​

Run init once to create the schema and the rows:

dotnet run -c Release --project CamusDB.Workload -- init \
  --endpoint http://127.0.0.1:5096 \
  --database workload \
  --protocol grpc \
  --rows 100000 \
  --payload-bytes 256 \
  --batch 500

You can run init again safely. If the schema and the rows exist, the data doesn't change.

The following options apply to init and to the other commands that connect to a server:

OptionDefaultMeaning
--endpointRequiredThe server endpoint. With --protocol grpc, use the gRPC port, such as http://127.0.0.1:5096. A comma-separated pool of endpoints is allowed.
--databaseRequiredThe workload database.
--protocolgrpcThe client protocol: grpc or rest.
--seed1847The seed for the generated data and the choice of operations.
--rows100000The number of rows, over all workload tables.
--tables1The number of workload tables. It can't be larger than --rows.
--payload-bytes256The size of the payload string of each row.
--no-auto-preparefalseAdd MaxAutoPrepare=0 to each connection string.
--connection-optionsNoneExtra connection-string pairs for each connection, such as CoalescingDelay=0;ChannelPoolSize=4. They're recorded in manifest.json.
--routing-modeDriver defaultLearned statement routing: Off, Learned, or Auto. The driver default is Auto, which takes effect when --routing-nodes maps two or more different endpoints.
--routing-nodesNoneA map from server node identities to endpoint pool members, such as node-a:7070=http://a:5095,node-b:7070=http://b:5095.
--request-timeoutClient defaultThe timeout in seconds for each request.

init also takes --batch, the rows in each seeding transaction (default 500). With --workload tpch or --workload tpcc, it also loads the tables of that workload. See Analytical workload and Transactional workload.

Run​

run does the following steps in order. It writes the measured results before the checks start. This means that a check that can't finish doesn't discard the results.

Open-loop mode sends a target number of operations per second:

dotnet run -c Release --project CamusDB.Workload -- run \
  --endpoint http://127.0.0.1:5096 \
  --database workload \
  --protocol grpc \
  --output /tmp/camus-workload-run \
  --mode open \
  --target-ops 800 \
  --workers 64 \
  --connections 8 \
  --duration 5m \
  --warmup 30s \
  --drain 10s

Closed-loop mode gives each worker one operation at a time. Use it to find the saturation point:

dotnet run -c Release --project CamusDB.Workload -- run \
  --endpoint http://127.0.0.1:5096 \
  --database workload \
  --protocol grpc \
  --output /tmp/camus-workload-closed \
  --mode closed \
  --workers 64 \
  --connections 8 \
  --duration 5m \
  --warmup 30s

The following options apply to run:

OptionDefaultMeaning
--outputRequiredThe output directory. It must not exist.
--modeopenopen for a target rate, closed to saturate the workers.
--target-ops800Open loop: the operations per second to send.
--workers64The number of concurrent workers.
--concurrency-sweepNoneClosed loop: a comma-separated list of worker counts, such as 1,8,16,32,64,128.
--read-percent60The percentage of operations that are read-only point reads.
--write-percent40The percentage of write transactions. The two percentages must add up to 100.
--writes-per-transaction1The row updates in each write transaction.
--duration5mThe measured interval.
--warmup30sThe warm-up period before measurement.
--drain10sOpen loop: the wait for in-flight work after measurement.
--stop-after-completed0End the measured interval after this many successful operations, or at --duration. 0 uses the full duration. The rates are computed over the measured time.
--connections8The number of read connections. The same number of write connections is opened.
--max-in-flight4096Open loop: the maximum pending and in-flight operations. Above it, the utility counts a schedule drop.
--init-if-missingfalseCreate and seed the data set if it doesn't exist. Setup isn't measured.
--lockingoptimisticThe locking of write transactions: optimistic or pessimistic.
--isolationread_committedThe isolation of write transactions: read_committed or serializable. The utility sets it on each write transaction. This means that its default replaces the server default, serializable.

--reconcile-timeout600The seconds that the checks after the run retry while a cluster settles.
--reconcile-request-timeout120The timeout in seconds for each setup and check request. Keep --request-timeout for the measured operations.
--scan-probe-intervaloffCount the rows with SELECT COUNT(*) on each gateway at this interval, such as 5s. A count below the row count fails the run. A failed probe also fails it, unless --expect-faults is set.
--scan-probe-timeout60The timeout in seconds for each scan probe.
--no-row-attributionfalseTransfer workloads: check the total balance only. See Workloads.
--metrics-endpointNoneThe Prometheus endpoints of the nodes, as name=url. Repeat the option, or separate the values with commas.
--metrics-interval5sThe scrape interval for --metrics-endpoint.
--node-endpointNoneThe HTTP API base of each node, as name=url. The run writes cluster-facts.json with the version, health, and placement of each node.
--pipelinefalsegRPC: send each write transaction as pipelined frames. See Pipelined writes.

--metrics-endpoint and --node-endpoint are most useful in a cluster. The first records how the work and the backlogs moved between nodes. The second records the setup that the run measured, such as the build and the placement. compare uses it to refuse two results that look similar but aren't the same experiment.

Workloads​

WorkloadWhat it testsCheck after the run
accountsRead-modify-write updates. Each worker updates a separate set of rows.The row count and the row versions. A conflict makes the run invalid.
bankContended transfers between rows.SUM(balance) doesn't change.
fanoutTransfers whose two legs are in different tables. Needs --tables of 2 or more.SUM(balance) doesn't change.
tokensEach write deletes a token row and inserts the next one, in one transaction.Each of the --tokens slots (default 2000) has exactly one row.
appendList-append transactions for Elle.A history for Elle's list-append checker.
rwBlind writes and point reads of single-value registers.A history for Elle's rw-register checker.
predicateGroup reads by a predicate, against inserts and updates.A history for Elle's rw-register checker.
tpch22 analytical queries.Each answer matches a reference answer.
tpccThe five TPC-C transaction types.The TPC-C consistency conditions.

In the accounts workload, two workers don't write the same row. A conflict is evidence against the run, and the utility doesn't retry it. Note that on a node with a small memory profile, such as --memory-profile dev, a few CADB0504 conflicts can occur when cached rows are evicted. The run is then marked invalid. Use the default memory profile for measurements.

The transfer workloads (bank and fanout) also check the balance and the version of each row. They write transfer-ledger.csv, and the row checks can write violation details that show which rows and attempts broke the invariant. --no-row-attribution checks the total only. It's cheaper, but it can miss two opposite leaked writes that cancel each other out. Use it if the full row scan takes too long.

Pipelined writes​

With --pipeline, the accounts, bank, and fanout workloads send each write transaction over gRPC as batch frames. The client uses the server's txn_start_ref and COMMIT_IF_OK contract when the server announces support. On the bank workload, the six exchanges (START, two reads, two updates, COMMIT) become two.

If the server or the protocol can't use the pipeline, the client sends one exchange for each step. The exchangesPerWriteTxn field in summary.json shows what the run achieved. A result with --pipeline and a result without it measure different client behavior.

Elle histories​

Elle is the transaction isolation checker of the Jepsen project. A conserved sum can show that no money was created or lost. However, it can't show dependency cycles, such as lost updates or write skew. An Elle history can.

The append, rw, and predicate workloads record a history in history.edn and elle.json. The utility doesn't check the history. Run the Elle checker separately.

  • append uses a separate elle_append table. A transaction reads a list or appends a unique value to it.
  • rw writes and reads single-value registers.
  • predicate reads groups by a predicate. A group read records each key that the predicate can match, including keys that don't exist. This lets the checker find rows that appear.

For example, change the endpoint and the data set options from the run command above:

dotnet run -c Release --project CamusDB.Workload -- run \
  --endpoint http://localhost:5096 --protocol grpc --database workload \
  --workload rw --rw-access join --isolation serializable --duration 60s \
  --mode closed --workers 8 --output runs/rw-join
OptionDefaultMeaning
--txn-modeexplicitexplicit uses BEGIN and COMMIT. autocommit makes each statement a transaction. pipeline sends the statements as frames, with BEGIN in the first frame and the commit in the last.
--elle-key-distributionuniform for append, exponential for the othersuniform picks each active key with the same chance. exponential puts about half the steps on the first key, a quarter on the next, and so on.
--rw-keys, --rw-max-writes-per-key, --rw-max-txn-length10, 32, 4The active registers, the writes before a key is replaced, and the maximum steps in a transaction.
--rw-key-typeint64Also string or numeric.
--rw-accesspkpk, secondary (an unindexed copy of the key), index, or join. The pipeline mode supports pk and join.
--predicate-groups, --predicate-group-size8, 8The active groups, and the possible keys in each group.
--predicate-max-writes-per-group, --predicate-max-txn-length12, 3The writes before a group is replaced, and the maximum steps in a transaction.
--predicate-readindexindex reads by an indexed group column, scan by an unindexed one, and range by primary-key bounds.
--append-keys10The active lists. Fewer keys give more contention.
--append-max-writes-per-key64The appends before a list is replaced. This limits the length of each list for the checker.
--append-max-txn-length4The maximum read or append steps in a transaction.

In autocommit mode, each transaction has one step. This means that it can't test invariants across statements. --txn-mode is separate from --pipeline. Compare results that use the same mode.

After the drain, these workloads also read the final state and compare it with the ledger of attempted writes. The result is in reconciliation.json. It checks for the following problems:

  • An acknowledged write that was lost.
  • A write that returned an error but became visible.
  • A duplicate or unknown value.
  • A different answer through a different access path.

A write with an unknown outcome can have either result. A predicate count is compared with the rows only if both reads used the same transaction snapshot. Two separate statements in Read Committed or autocommit mode can see a concurrent change.

Analytical workload: tpch​

--workload tpch tests analytical queries, such as joins and grouping, with the 22 TPC-H queries on eight generated tables. Setup records a reference answer for each query before the measurement. Each execution is checked against it. The loaded data is also checked against row counts and facts from the generator, for example for Q1 and Q6.

dotnet run -c Release --project CamusDB.Workload -- init \
  --endpoint http://127.0.0.1:5096 --database analytics \
  --workload tpch --tpch-scale 0.01 --rows 1000

dotnet run -c Release --project CamusDB.Workload -- run \
  --endpoint http://127.0.0.1:5096 --database analytics \
  --workload tpch --tpch-scale 0.01 --rows 1000 \
  --mode closed --read-percent 100 --write-percent 0 --workers 4 \
  --duration 5m --output /tmp/camus-tpch

The scale defaults to 0.01, about 86,000 rows. At 1, it's about 8.66 million rows. The tables are added next to the base accounts data set. --tpch-load-connections sets the load concurrency (default 8). init and run must use the same scale and seed.

This workload needs --mode closed and --read-percent 100. By default, all 22 queries are used. --tpch-queries 1,3,6 or --tpch-queries 1-6,14 selects some of them. Each selected query must complete a verified execution in the measured interval.

The results are in tpch.json, with the latency and the verification of each query. The reference answers are in tpch-reference.json, and the differences are in tpch-mismatches.jsonl. Note that these numbers aren't TPC-H scores. Published scores use different rules.

Transactional workload: tpcc​

--workload tpcc tests order-entry transactions. It uses the standard mix of the five TPC-C transaction types:

TransactionShare
New-Order45%
Payment43%
Order-Status4%
Delivery4%
Stock-Level4%
dotnet run -c Release --project CamusDB.Workload -- init \
  --endpoint http://127.0.0.1:5096 --database orders_bench \
  --workload tpcc --tpcc-warehouses 1 --tpcc-scale 0.01 --rows 1000

dotnet run -c Release --project CamusDB.Workload -- run \
  --endpoint http://127.0.0.1:5096 --database orders_bench \
  --workload tpcc --tpcc-warehouses 1 --tpcc-scale 0.01 --rows 1000 \
  --mode closed --read-percent 0 --write-percent 100 --workers 4 \
  --duration 5m --output /tmp/camus-tpcc

This workload needs --write-percent 100. That value selects the full mix, including its read-only transactions. The write transactions use --isolation and --locking, and a conflict is retried in a new transaction. The read-only types use Serializable snapshots. Delivery uses one transaction for each district.

--tpcc-warehouses defaults to 1. One warehouse at --tpcc-scale 1 is about 500,000 rows. Workers are assigned to warehouses by worker index, modulo the warehouse count. You should use at least as many workers as warehouses. --tpcc-scale defaults to 1, and it can be from 0.01 to 1. It reduces the data sizes for smaller tests, and it's separate from the warehouse count. init and run must use the same warehouse count, scale, and seed. --tpcc-load-connections defaults to 8.

The consistency conditions are checked before and after the run, and each transaction records the anomalies that it finds. The run fails in the following cases:

  • An anomaly was found.
  • A final check failed.
  • A transaction type had no measured commit.

tpcc.json has the latency and the throughput of each type, and the consistency results. tpcc-anomalies.jsonl lists the anomalies. The workload has no keying time and no think time. This means that its New-Order rate can't be compared with a published tpmC.

Output files​

A successful run writes the following files:

FileContents
manifest.jsonThe settings of the run, such as the tool version, the endpoint, the workload, and the data set fingerprint.
summary.jsonThe throughput, latency, errors, exchangesPerWriteTxn, and validity, for scripts.
summary.mdA summary to read.
intervals.csvSamples for each second: the operations offered, started, completed, failed, and in flight, and the latency.
errors.jsonThe error counts by code, with sample messages.
reconciliation.jsonThe checks of the committed writes and the final row versions.
run-meta.jsonThe start time of the measured interval, and the durations of the warm-up, measurement, and drain.
client-resources.jsonThe CPU and memory use of the load generator, to show a bottleneck on the client.

Some options and workloads add files:

FileWritten when
scan-probe.csv--scan-probe-interval is set.
history.edn, elle.jsonThe workload is append, rw, or predicate.
transfer-ledger.csvThe workload is bank or fanout.
token-ledger.csvThe workload is tokens.
tpch.json, tpch-reference.json, tpch-mismatches.jsonlThe workload is tpch.
tpcc.json, tpcc-anomalies.jsonlThe workload is tpcc.
node-metrics.csv, node-metrics-meta.json, bottleneck-report.md--metrics-endpoint is set.
cluster-facts.json--node-endpoint is set.

In errors.json, the classes section groups messages that differ only in details such as IDs or counts. This separates different failures that have the same CamusDB error code.

The process exits with a code above zero when the run is invalid or a check fails. With --concurrency-sweep, each worker count is a complete run in <output>/workers-N. The top level has sweep.csv and sweep.md with a summary of all points.

Bottleneck report​

The report compares the throughput and latency on the client with the server metrics. With metrics and facts from each node, it can also show how requests and leaders are spread over the nodes, and where the storage or the WAL limits the throughput. Use it to find the stage that needs attention before you tune anything.

The server serves Prometheus metrics when diagnostics.prometheus_enabled is true. For more information, see Performance diagnostics. A run with --metrics-endpoint builds bottleneck-report.md. The report command builds it later, from one scraped /metrics file or from node-metrics.csv:

dotnet run -c Release --project CamusDB.Workload -- report \
  --output /tmp/camus-workload-run \
  --metrics /tmp/server-metrics.txt

dotnet run -c Release --project CamusDB.Workload -- report \
  --output /tmp/camus-workload-run \
  --node-metrics /tmp/camus-workload-run/node-metrics.csv

The report is written to the run directory.

Compare and baseline​

compare compares two run directories. If a field that defines the experiment differs, such as the isolation or the build, the pair can't be compared. To test the effect of one field, waive it with --allow:

dotnet run -c Release --project CamusDB.Workload -- compare \
  --baseline /tmp/camus-workload-base \
  --candidate /tmp/camus-workload-candidate \
  --allow isolation \
  --require-ratio 1.10 \
  --p99-budget-ms 250 \
  --output /tmp/camus-workload-comparison

Differences in fields such as workers and connections are shown, but they don't make the pair incomparable. --require-ratio, --require-ops, and --p99-budget-ms make the comparison a gate. With --output, the result is also written to comparison.md. The exit code is one of the following values:

Exit codeMeaning
0The results are comparable, and the candidate passes.
1The results are comparable, and the candidate misses a gate.
3The results can't be compared.

baseline summarizes several run directories of the same workload. Use it to know the median and the variation before you judge a later candidate:

dotnet run -c Release --project CamusDB.Workload -- baseline \
  --runs /tmp/run-1,/tmp/run-2,/tmp/run-3 \
  --output /tmp/camus-workload-baseline

A baseline needs at least three usable results, with a coefficient of variation of 10% or less in the throughput. With --output, the result is also written to baseline.md. The exit code is 0 for an established baseline, 1 when it isn't established, and 3 when the results can't be compared.

Cleanup​

cleanup drops the workload database. You must confirm the name:

dotnet run -c Release --project CamusDB.Workload -- cleanup \
  --endpoint http://127.0.0.1:5096 \
  --database workload \
  --protocol grpc \
  --confirm workload

An empty name, the default database name, and a name that doesn't match --confirm return exit code 2.
