Date/time functions

Date and time functions let you answer time questions in SQL: orders placed this month, sessions grouped by hour, days until a subscription expires, or a timestamp formatted for a report. Clock functions such as now() follow PostgreSQL rules, and CamusDB also accepts the PostgreSQL and MySQL formatting functions (to_char, date_format) and the MySQL shortcuts (year, dayname), so queries you port need fewer changes.

Each function returns a typed value: DATE, DATETIME, or INT64. to_char, date_format, dayname, and monthname return STRING.

These functions accept DATE and DATETIME columns directly, as well as two string forms:

  • A date in the form YYYY-MM-DD.
  • A timestamp with an explicit UTC marker or offset, such as 2024-06-15T10:30:00Z or 2024-06-15T10:30:00+05:00.

CamusDB rejects local timestamp strings without an offset, such as 2024-06-15T10:30:00 and 2024-06-15 10:30:00, because their time zone is ambiguous.

The supported units are year, month, day, hour, minute, second, millisecond, microsecond (or us), week, quarter, decade, century, and millennium. CamusDB also accepts plural names, such as days, months, and millennia.

The following units name a position, so they work only in date_part and EXTRACT: dow (0 = Sunday), isodow (1 = Monday to 7 = Sunday), doy (day of the year), isoyear, and epoch (whole Unix seconds).

When extracted as a part, week is the ISO-8601 week, and millisecond and microsecond are only the fraction of the current second (0-999 and 0-999999).

Which clock?​

The clock functions follow PostgreSQL:

  • now(), current_timestamp(), transaction_timestamp(), current_date(), unix_timestamp(), and unix_timestamp_ms() return the start of the transaction. Every row and statement in a transaction sees the same value.
  • statement_timestamp() returns the start of the statement, so each statement gets a new value.
  • clock_timestamp() and sysdate() read the clock on each call, so two rows in one statement can get different values.

Use now() for a consistent time across a transaction. Use clock_timestamp() to measure elapsed time inside one.

MySQL shortcuts​

Each shortcut takes a temporal value and returns one of its UTC parts.

FunctionReturnsDescription
year(x), month(x), day(x), hour(x), minute(x), second(x)INT64The same part as date_part.
dayofmonth(x)INT64Alias for day(x).
quarter(x)INT641 to 4.
dayofyear(x)INT641 to 366.
dayofweek(x)INT641 = Sunday to 7 = Saturday.

dayname(x)STRINGThe English day name, such as Sunday.

week(x[, mode])INT64Mode 0, the default: weeks start on Sunday, and the days before the first Sunday are week 0 (0 to 53). Mode 3: the ISO-8601 week (1 to 53). Any other mode is an error.

dayofweek(x) counts from 1, but date_part('dow', x) counts from 0. CamusDB has no DATE(x) function, because DATE is a type keyword. Use CAST(x AS DATE).

SELECT EXTRACT(year FROM '2024-06-16'), dayofweek('2024-06-16'), week('2024-01-07');
-- 2024, 1, 1

Typed results​

You can insert a temporal function's result into a temporal column, or compare it with one, without a cast:

INSERT INTO events (id, happened_at)
VALUES (GEN_ID(), now());

SELECT *
FROM events
WHERE happened_at < current_timestamp();

SELECT date_add(happened_at, 7, 'days')
FROM events;

date_add always returns a DATETIME, so adding a day to a DATE value returns a datetime at UTC midnight, not another DATE.

Examples​

SELECT current_timestamp(), now(), current_date();

SELECT date_add('2024-06-15', 1, 'day');
-- 2024-06-16T00:00:00.0000000Z

SELECT date_add('2024-06-15T10:30:00Z', 2, 'hours');
-- 2024-06-15T12:30:00.0000000Z

SELECT date_diff('2024-06-01', '2024-06-11', 'days');
-- 10

SELECT date_part('hour', '2024-06-15T10:30:00+05:00');
-- 5

SELECT date_trunc('month', '2024-06-15T10:30:45.123Z');
-- 2024-06-01T00:00:00.0000000Z

SELECT unix_timestamp('2024-06-15T10:30:00Z');
-- 1718447400

SELECT unix_timestamp('2024-06-15');
-- 1718409600

SELECT from_unixtime(1718447400);
-- 2024-06-15T10:30:00.0000000Z

SELECT from_unixtime(unix_timestamp('2024-06-15T10:30:00+00:00'));
-- 2024-06-15T10:30:00.0000000Z

SELECT make_date(2024, 2, 29);
-- 2024-02-29

SELECT make_timestamp(2026, 1, 1, 0, 0, 0.123);
-- 2026-01-01T00:00:00.1230000Z

SELECT makedate(2024, 60), last_day('2024-02-10');
-- 2024-02-29, 2024-02-29

SELECT unix_timestamp_ms('2024-06-15T10:30:00Z');
-- 1718447400000

The date constructors return NULL when an argument is NULL. Invalid parts raise CADB0400 InvalidInput with the invalid year, month, day, hour, minute, or second named in the message. Years must be from 1 through 9999.

make_timestamp rounds fractional seconds to the nearest microsecond. A value that rounds up to 60 seconds carries into the next minute. makedate permits a day beyond the end of the named year and continues into the next year, while a day below 1 is an error.

NULLs and overflow​

These functions return NULL when any argument is NULL: date_add, date_diff, date_part (and EXTRACT), date_trunc, unix_timestamp(value), from_unixtime(seconds), and the MySQL shortcuts.

unix_timestamp() takes no argument and returns the start of the current transaction as a Unix timestamp in seconds.

These conditions make the query fail:

  • An invalid unit.
  • An invalid date string.
  • An ambiguous local timestamp.
  • A Unix timestamp outside the supported date/time range.
  • Date or time overflow.

Pattern formatting and parsing​

These functions use a pattern to format a DATE or DATETIME value as text, or to parse text back into a value. CamusDB accepts two pattern languages:

  • PostgreSQL template patterns, for example 'YYYY-MM-DD HH24:MI:SS'.
  • MySQL % specifiers, for example '%Y-%m-%d %H:%i:%s'.

Both languages compile to the same fields, so a field formats and parses the same way in both.

FunctionResultPattern language
to_char(temporal, pattern)STRINGPostgreSQL
to_timestamp(text, pattern)DATETIMEPostgreSQL
to_date(text, pattern)DATEPostgreSQL
date_format(temporal, pattern)STRINGMySQL
str_to_date(text, pattern)DATETIMEMySQL

Two one-argument forms keep their meaning:

  • to_date(x) is the cast to DATE, the same as CAST(x AS DATE).
  • to_timestamp(seconds) is the PostgreSQL spelling of from_unixtime(seconds).

A temporal argument is a DATE, a DATETIME, or an ISO-8601 string with an explicit offset, the same rule as the other date functions. A NULL argument gives NULL.

SELECT to_char(created, 'FMDay, DD Mon YYYY HH12:MI AM') FROM events;
-- Sunday, 16 Jun 2024 10:30 AM

INSERT INTO imports (id, day) VALUES (1, to_date('03/15/2026', 'MM/DD/YYYY'));

SELECT date_format(created, '%W %M %e, %Y') FROM events;
-- Sunday June 16, 2024

SELECT * FROM events WHERE created >= str_to_date('June 17, 2024', '%M %e, %Y');

Rules for all patterns​

  • All values are UTC. The time zone fields print UTC and +00.
  • Names are English only. Month and day names do not change with the server culture, and there is no locale setting.
  • The functions are deterministic. They are not volatile, so a CHECK constraint, a column DEFAULT, and a view body can use them.
  • The year range is 1-9999. A value outside this range is an error; it does not wrap.
  • The fraction has six digits. No field prints or reads the seventh fraction digit (100 ns) of a DATETIME. to_char drops that digit.
  • Each pattern compiles once. The engine keeps the compiled form of each distinct pattern text in a small cache, so a literal pattern is not recompiled for every row.

How parsing works​

to_timestamp, to_date, and str_to_date parse strictly. Text that does not match the pattern gives an InvalidInput error whose message quotes the text and the pattern and gives the reason. For example:

Function 'to_date' could not parse '02/30/2026' with pattern 'MM/DD/YYYY': day 30 is out of range for February 2026, which has 28 days

The rules:

  1. A numeric field reads from 1 digit up to its full width. Thus 3/5/2026 matches MM/DD/YYYY, and 20260315 matches YYYYMMDD.
  2. A fraction field reads the digits after the decimal point. MS reads 5 as 500 ms, and US or %f reads 5 as 500000 microseconds.
  3. A name field matches English names case-insensitively. Mar, MAR, and mar all match Mon.
  4. A run of spaces in the pattern matches a run of one or more spaces in the text, so the blank padding that Month and Day print reads back.
  5. Any other pattern character, and quoted text, must match the text exactly.
  6. The whole text must match. Extra characters after the end of the pattern are an error.
  7. Each field must be in range. For example, MM is 1-12, HH24 is 0-23, and SS is 0-59.
  8. The pattern must have a year field. CamusDB cannot hold a date without a year.
  9. A missing month or day is 1. A missing hour, minute, second, or fraction is 0.
  10. Two fields that give the same value must agree. For example, MM and Mon must name the same month.

The date comes from one of these sources:

  • the year, the month, and the day;
  • the year and DDD or %j (day of the year), when the pattern has no month and no day;
  • IYYY, IW, and ID (ISO year, ISO week, and ISO day). A missing IW is week 1, and a missing ID is Monday.

A pattern with IYYY must not also have a Gregorian date field (YYYY, MM, DD, DDD).

Some fields only repeat what the date already says. Parsing checks these fields against the result: D, ID, Dy, Day, %W, %a, Q, WW, IW, %u, %v, and DDD / %j when the pattern also has a month or a day. A mismatch is an error, because the text would then name two different dates.

The clock fields follow these rules:

  • With a 12-hour field (HH, HH12, %h, %I), AM / PM sets the half of the day. Without AM / PM, the hour is AM, so 12 means midnight.
  • AM / PM without a 12-hour field is an error.
  • When a pattern has both a 12-hour and a 24-hour field, they must give the same hour.
  • When a pattern has both MS and US, they must agree. to_char prints 020 and 020000 for 20 ms, and that text reads back as 20 ms.
  • TZ reads UTC and OF reads +00. Any other time zone is an error.

to_date reads and checks the time fields, then keeps only the date.

Two-digit and three-digit years​

YYY, YY, and Y (and %y) give the nearest year to 2020, with the PostgreSQL rule:

Value readYear
0-692000-2069
70-991970-1999
100-5192100-2519
520-9991520-1999

YYYY and %Y read the year as written, so 26 with YYYY is the year 26.

Pattern result types​

str_to_date always returns DATETIME. MySQL returns either DATE or DATETIME depending on the pattern, but in CamusDB the result type comes only from the argument types, not from the pattern text.

CamusDB does not compare a DATE with a DATETIME. To compare the result of str_to_date with a DATE column, cast the result:

SELECT *
FROM events
WHERE day = CAST(str_to_date('June 17, 2024', '%M %e, %Y') AS DATE);

You can also use to_date(text, pattern), which returns DATE.

Differences from PostgreSQL​

  • Separators. PostgreSQL lets any separator in the pattern match any separator in the text, and skips extra spaces. CamusDB requires the same character. Only a run of spaces can match a run of spaces of a different length.
  • Quoted text. PostgreSQL skips the same number of characters without checking them. CamusDB requires the same text.
  • Extra text. PostgreSQL ignores some characters after the end of the pattern. CamusDB gives an error.
  • Checked fields. PostgreSQL ignores D, Dy, Day, and Q when parsing, and uses WW to find a date. CamusDB checks each of these fields against the date, and WW does not set the date.
  • No year. PostgreSQL gives a date in the year 1 BC when the pattern has no year field. CamusDB gives an error, because it cannot hold that year.
  • MS and US together. PostgreSQL adds the two values. CamusDB requires them to agree, so the text that to_char prints reads back.
  • AM / PM with HH24. PostgreSQL ignores the meridian. CamusDB gives an error.
  • TZ and OF in a parse. CamusDB reads only UTC and +00.
  • Empty pattern. PostgreSQL to_char(x, '') gives NULL. CamusDB gives an empty string.
  • Not supported. Number formatting (to_char(123, '999')), the TH suffix, FX, TM, CC, J, RM, A.M. / P.M., BC / AD, TZH / TZM, and SSSS.

Differences from MySQL​

  • Unknown specifiers. MySQL prints the letter. CamusDB gives an error.
  • Strict parse. MySQL accepts some text that does not match the pattern, and can give a zero date (0000-00-00). CamusDB gives an error for every mismatch and requires a year.
  • Checked fields. MySQL does not check %W, %a, %u, and %v against a year-month-day date. CamusDB checks each of them against the date.
  • Result type. str_to_date always returns DATETIME.
  • Names do not pad. %M and %W print the name without blanks, as in MySQL.
  • Not supported. %D, %k, %l, %r, %T, %U, %V, %w, %X, and %x.
