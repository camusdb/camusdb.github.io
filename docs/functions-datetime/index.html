Date/time functions

Date and time functions answer time questions in SQL, for example the orders of this month or the days until a subscription expires. The clock functions, such as now(), follow PostgreSQL. CamusDB also has the PostgreSQL and MySQL formatting functions. It also has MySQL shortcuts, such as year. This means that queries that you port need fewer changes.

The functions take DATE and DATETIME values, and two string forms:

  • A date, such as 2024-06-15.
  • A timestamp with a UTC marker or an offset, such as 2024-06-15T10:30:00Z or 2024-06-15T10:30:00+05:00.

A timestamp string that doesn't have an offset, such as 2024-06-15 10:30:00, returns CADB0400. Its time zone is ambiguous. You can also write typed literals, such as DATE '2024-06-15'.

Units​

UnitsWhere
year, quarter, month, week, day, hour, minute, secondAll functions that take a unit.
millisecond, microsecond (or us), decade, century, millenniumAll functions that take a unit.
dow (0 = Sunday), isodow (1 = Monday to 7 = Sunday), doy (day of the year), isoyear, epoch (Unix seconds)date_part and EXTRACT only.

Plural names, such as days and millennia, also work. As a part, week is the ISO 8601 week. millisecond and microsecond are the fraction of the second (0 to 999, and 0 to 999999).

Transaction, statement, and clock time​

The clock functions follow PostgreSQL:

  • now() and the other transaction-time functions return the start of the transaction. All rows and statements of a transaction get the same value. The unix_timestamp functions use this time when you don't pass a value.
  • statement_timestamp() returns the start of the statement. Each statement gets a new value.
  • clock_timestamp() and sysdate() read the clock at each call. Two rows of one statement can get different values.

Use now() for one time across a transaction. To measure elapsed time in a transaction, use clock_timestamp().

MySQL shortcuts​

Each shortcut takes a temporal value and returns one of its UTC parts:

FunctionReturnsDescription
year(x), month(x), day(x)INT64The same part as date_part. dayofmonth(x) is an alias for day(x).
hour(x), minute(x), second(x)INT64The same part as date_part.
quarter(x)INT641 to 4.
dayofyear(x)INT641 to 366.
dayofweek(x)INT641 = Sunday to 7 = Saturday.
weekday(x)INT640 = Monday to 6 = Sunday.
dayname(x)STRINGThe English day name, such as Sunday.
monthname(x)STRINGThe English month name, such as June.
week(x[, mode])INT64Mode 0 (default): weeks start on Sunday, and the days before the first Sunday are week 0. Mode 3: the ISO 8601 week. Other modes return CADB0400.

dayofweek(x) counts from 1, and date_part('dow', x) counts from 0. DATE is a type keyword, and there is no DATE(x) function. Use CAST(x AS DATE).

SELECT EXTRACT(year FROM '2024-06-16'), dayofweek('2024-06-16'), week('2024-01-07');
-- 2024, 1, 1

Typed results​

You can insert the result of a temporal function into a temporal column, or compare it with one, and you don't need a cast:

INSERT INTO events (id, happened_at)
VALUES (GEN_ID(), now());

SELECT *
FROM events
WHERE happened_at < current_timestamp();

SELECT date_add(happened_at, 7, 'days')
FROM events;

date_add returns a DATETIME. This means that a day added to a DATE gives a datetime at UTC midnight. A DATE and a DATETIME can be compared.

Examples​

SELECT current_timestamp(), now(), current_date();

SELECT date_add('2024-06-15', 1, 'day');
-- 2024-06-16T00:00:00.0000000Z

SELECT date_add('2024-06-15T10:30:00Z', 2, 'hours');
-- 2024-06-15T12:30:00.0000000Z

SELECT date_diff('2024-06-01', '2024-06-11', 'days');
-- 10

SELECT date_part('hour', '2024-06-15T10:30:00+05:00');
-- 5

SELECT date_trunc('month', '2024-06-15T10:30:45.123Z');
-- 2024-06-01T00:00:00.0000000Z

SELECT unix_timestamp('2024-06-15T10:30:00Z');
-- 1718447400

SELECT unix_timestamp('2024-06-15');
-- 1718409600

SELECT from_unixtime(1718447400);
-- 2024-06-15T10:30:00.0000000Z

SELECT make_date(2024, 2, 29);
-- 2024-02-29

SELECT make_timestamp(2026, 1, 1, 0, 0, 0.123);
-- 2026-01-01T00:00:00.1230000Z

SELECT makedate(2024, 60), last_day('2024-02-10');
-- 2024-02-29, 2024-02-29

SELECT unix_timestamp_ms('2024-06-15T10:30:00Z');
-- 1718447400000

The date constructors return NULL if an argument is NULL. An invalid part returns CADB0400, and the message names the part. Years must be from 1 to 9999.

make_timestamp rounds a fractional second to the microsecond. A value that rounds up to 60 seconds goes to the next minute. A makedate day after the end of the year continues into the next year. A day below 1 returns CADB0400.

Interval functions​

Use intervals to compute calendar ages or to group timestamps into buckets:

FunctionReturnsBehavior
age(a, b)INTERVALThe calendar difference a - b, with calendar parts and time.
age(a)INTERVALThe same as age(current_date(), a), with the UTC date of the transaction at midnight.
make_interval(years, months, weeks, days, hours, mins, secs)INTERVALAn interval from positional parts. Trailing parts that you omit are zero.
justify_days(i)INTERVALConverts each 30 days to a month, and aligns the signs of months and days.
justify_hours(i)INTERVALConverts each 24 hours to a day, and aligns the signs of days and time.
justify_interval(i)INTERVALApplies both conversions.
date_bin(stride, source, origin)DATETIMEThe start of the bucket that has source, aligned to origin.
SELECT age(DATE '2001-04-10', DATE '1957-06-13');
-- P43Y9M27D

SELECT make_interval(0, 0, 0, 1, 2);
-- P1DT2H

SELECT justify_interval(INTERVAL '1 month -1 hour');
-- P29DT23H

SELECT date_bin(INTERVAL '15 minutes',
  TIMESTAMP '2024-06-15T15:44:17Z',
  TIMESTAMP '2024-06-15T00:00:00Z');
-- 2024-06-15T15:30:00Z

SELECT DATE_ADD(DATE '2024-01-31', INTERVAL 1 MONTH);
-- 2024-02-29T00:00:00Z

age borrows days with the month length of the earlier date, as in PostgreSQL. Both forms of age are volatile in CamusDB. A CHECK constraint can't use them, and a query that calls them doesn't use the result cache. In PostgreSQL, the two-argument form is immutable.

make_interval takes up to seven positional arguments. Named arguments aren't supported. All the parts except seconds must be INT64. Seconds can have a fraction, which is rounded to the microsecond. A part out of range returns CADB0400.

date_bin needs a positive stride that doesn't use months, and an explicit origin. A value before the origin goes to the bucket before it. A NULL argument of an interval function returns NULL.

Extracting interval fields​

EXTRACT and date_part read the parts of an interval, and they don't normalize them:

SELECT EXTRACT(hour FROM INTERVAL '36 hours'),
       date_part('day', INTERVAL '36 hours');
-- 36, 0

The year is the total months divided by 12, and the month is the remainder. Each field has the sign of its part. The results are INT64, and PostgreSQL returns a fractional NUMERIC. Seconds are integers, and milliseconds and microseconds are the fraction of the second. For an interval, epoch returns seconds, rounded down, with 365.25 days for each year and 30 days for each remaining month.

The calendar positions, such as dow, can't be extracted from an interval. They return CADB0400.

NULLs and errors​

The functions return NULL if an argument is NULL. This also applies to EXTRACT and the MySQL shortcuts.

The following conditions return CADB0400:

  • An invalid unit.
  • An invalid date string, or a timestamp that doesn't have an offset.
  • A Unix timestamp outside the supported range.
  • A date or time overflow.

Pattern formatting and parsing​

These functions format a DATE or DATETIME as text with a pattern, or parse text into a value. There are two pattern languages:

  • PostgreSQL template patterns, for example 'YYYY-MM-DD HH24:MI:SS'.
  • MySQL % specifiers, for example '%Y-%m-%d %H:%i:%s'.

Both languages compile to the same fields. This means that a field formats and parses in the same way in both.

FunctionResultPattern language
to_char(temporal, pattern)STRINGPostgreSQL
to_timestamp(text, pattern)DATETIMEPostgreSQL
to_date(text, pattern)DATEPostgreSQL
date_format(temporal, pattern)STRINGMySQL
str_to_date(text, pattern)DATETIMEMySQL

Two one-argument forms have a different meaning:

  • to_date(x) is the cast to DATE, the same as CAST(x AS DATE).
  • to_timestamp(seconds) is the PostgreSQL name of from_unixtime(seconds).

A temporal argument follows the input rules at the start of this page. A NULL argument returns NULL.

SELECT to_char(created, 'FMDay, DD Mon YYYY HH12:MI AM') FROM events;
-- Sunday, 16 Jun 2024 10:30 AM

INSERT INTO imports (id, day) VALUES (1, to_date('03/15/2026', 'MM/DD/YYYY'));

SELECT date_format(created, '%W %M %e, %Y') FROM events;
-- Sunday June 16, 2024

SELECT * FROM events WHERE created >= str_to_date('June 17, 2024', '%M %e, %Y');

Rules for all patterns​

  • All values are UTC. The time zone fields print UTC and +00.
  • Names are English. Month and day names don't change with the server culture, and there is no locale setting.
  • The functions are deterministic. Stored definitions can use them, such as a CHECK constraint or a view body.
  • The year range is 1 to 9999. A value outside this range returns an error.
  • The fraction has six digits. No field prints or reads the seventh digit (100 ns) of a DATETIME.
  • Each pattern compiles once. The compiled form of each pattern text is cached. This means that a literal pattern isn't compiled again for each row.

How parsing works​

The parse functions are strict. Text that doesn't match the pattern returns CADB0400. The message quotes the text and the pattern, and it gives the reason:

Function 'to_date' could not parse '02/30/2026' with pattern 'MM/DD/YYYY': day 30 is out of range for February 2026, which has 28 days

The parser follows these rules:

  1. A numeric field reads from 1 digit up to its full width. For example, 3/5/2026 matches MM/DD/YYYY. 20260315 matches YYYYMMDD.
  2. A fraction field reads the digits after the decimal point. MS reads 5 as 500 ms. US and %f read 5 as 500000 microseconds.
  3. A name field matches English names in any case. For example, MAR matches Mon.
  4. A run of spaces in the pattern matches one or more spaces in the text. This means that the padding that Month and Day print reads back.
  5. Other pattern characters, and quoted text, must match exactly.
  6. The full text must match. Extra characters after the pattern return an error.
  7. Each field must be in range. For example, MM must be 1-12.
  8. The pattern must have a year field. Each date needs a year.
  9. A missing month or day is 1. A missing time field is 0.
  10. Two fields that give the same value must agree. For example, MM and Mon must name the same month.

The date comes from one of these sources:

  • The year, the month, and the day.
  • The year and DDD or %j (the day of the year), if the pattern doesn't have a month or a day.
  • IYYY, IW, and ID (the ISO year, week, and day). A missing IW is week 1, and a missing ID is Monday.

A pattern with IYYY can't also have a Gregorian date field, such as YYYY.

Some fields repeat what the date says, for example Day or %W. The parser checks these fields against the date. A day of the year (DDD or %j) is also checked, if the pattern has a month or a day. A mismatch returns an error. The text names two different dates.

The clock fields follow these rules:

  • With a 12-hour field (HH, HH12, %h, %I), AM or PM sets the half of the day. If there is no AM or PM field, the hour is AM. Then 12 means midnight.
  • An AM or PM field needs a 12-hour field. Otherwise, it returns an error.
  • A 12-hour and a 24-hour field in one pattern must give the same hour.
  • MS and US in one pattern must agree. to_char prints 020 and 020000 for 20 ms, and that text reads back as 20 ms.
  • TZ reads UTC, and OF reads +00. Another time zone returns an error.

to_date reads and checks the time fields, and then it returns the date only.

Two-digit and three-digit years​

The short year fields, such as YY and %y, give the nearest year to 2020, as in PostgreSQL:

Value readYear
0-692000-2069
70-991970-1999
100-5192100-2519
520-9991520-1999

YYYY and %Y read the year as written. For example, 26 with YYYY is the year 26.

Pattern result types​

str_to_date returns DATETIME. In MySQL, the pattern decides whether it returns DATE or DATETIME. In CamusDB, the result type comes from the argument types. For a DATE, use to_date(text, pattern).

Differences from PostgreSQL​

  • Separators. PostgreSQL lets any separator in the pattern match any separator in the text, and it skips extra spaces. CamusDB requires the same character. A run of spaces can match a run of a different length.
  • Quoted text. PostgreSQL skips the same number of characters, and it doesn't check them. CamusDB requires the same text.
  • Extra text. PostgreSQL ignores some characters after the end of the pattern. CamusDB returns an error.
  • Checked fields. PostgreSQL ignores the day-of-week fields and Q when it parses, and it uses WW to find a date. CamusDB checks these fields against the date, and WW doesn't set the date.
  • No year. PostgreSQL gives a date in the year 1 BC if the pattern doesn't have a year field. CamusDB returns an error. It can't store that year.
  • MS and US together. PostgreSQL adds the two values. CamusDB requires them to agree. This means that the text that to_char prints reads back.
  • AM or PM with HH24. PostgreSQL ignores the meridian. CamusDB returns an error.
  • TZ and OF in a parse. CamusDB reads UTC and +00 only.
  • Empty pattern. PostgreSQL to_char(x, '') returns NULL. CamusDB returns an empty string.
  • Not supported. Number formatting, such as to_char(123, '999'). These template keywords aren't supported either: TH FX TM CC J RM A.M. P.M. BC AD TZH TZM SSSS.

Differences from MySQL​

  • Unknown specifiers. MySQL prints the letter. CamusDB returns an error.
  • Strict parse. MySQL allows some text that doesn't match the pattern, and it can give a zero date (0000-00-00). CamusDB returns an error for each mismatch, and it requires a year.
  • Checked fields. MySQL doesn't check the day-name and week fields, such as %W, against a year-month-day date. CamusDB checks them.
  • Result type. str_to_date returns DATETIME.
  • Names aren't padded. %M and %W don't pad the name, as in MySQL.
  • Not supported. These specifiers aren't supported: %D %k %l %r %T %U %V %w %X %x.
