Tables and columns

A table definition is where you make the database enforce your data rules: column types, primary keys, defaults, CHECK constraints, and foreign keys. Every client then gets the same rules, not only the application that wrote them. The statements look like the CREATE TABLE and ALTER TABLE you know from PostgreSQL or MySQL. One difference helps when mistakes happen: by default, a dropped table stays recoverable for a retention window.

Table statements run inside an existing database, so create the database first or select it. Then you can create a table, alter a column, rename a table or a column, or drop a table.

Create a table​

CREATE TABLE robots (
  id OID PRIMARY KEY NOT NULL DEFAULT (gen_id()),
  name STRING NOT NULL,
  year INT64 DEFAULT (2024),
  active BOOL DEFAULT (true)
);

Create a table only when it does not exist:

CREATE TABLE IF NOT EXISTS robots (
  id OID PRIMARY KEY NOT NULL DEFAULT (gen_id()),
  name STRING NOT NULL
);

Create a table from the result of a query:

CREATE TABLE vintage_robots AS
SELECT name, year
FROM robots
WHERE year < 1990;

CREATE TABLE empty_robot_archive AS
SELECT *
FROM robots
WITH NO DATA;

CREATE TABLE ... AS SELECT adds its own generated primary key column and copies only the shape of the result. It inherits no indexes, constraints, defaults, comments, or settings from the source table. See Copying Query Results for CTAS rules, time travel copies, and limits.

Inline constraints in the column list can define a primary key or make a column unique:

CREATE TABLE app_users (
  id STRING PRIMARY KEY NOT NULL,
  email STRING UNIQUE NOT NULL,
  display_name STRING NOT NULL
);

Primary key columns are always NOT NULL. CamusDB records them as NOT NULL even when the column definition omits it.

Use a CHECK constraint when a column or row must satisfy a predicate. CamusDB applies the predicate before each insert and update:

CREATE TABLE products (
  id OID PRIMARY KEY NOT NULL DEFAULT (gen_id()),
  name STRING NOT NULL,
  price FLOAT64 NOT NULL CHECK (price > 0),
  discounted_price FLOAT64,
  CONSTRAINT valid_discount CHECK (discounted_price IS NULL OR price > discounted_price)
);

See Check Constraints for constraint names, ALTER TABLE, NULL behavior, and supported expressions.

Use a FOREIGN KEY constraint when a child table must reference a parent key:

CREATE TABLE cities (
  name STRING PRIMARY KEY NOT NULL
);

CREATE TABLE weather (
  id OID PRIMARY KEY NOT NULL DEFAULT (gen_id()),
  city STRING REFERENCES cities (name)
);

You can also add or drop foreign keys later:

ALTER TABLE weather
ADD CONSTRAINT weather_city_fk
FOREIGN KEY (city) REFERENCES cities (name);

ALTER TABLE weather DROP CONSTRAINT weather_city_fk;

See Foreign Keys for enforcement, indexes, branches, and schema changes blocked by a constraint.

Declare a composite primary key after the column list:

CREATE TABLE readings (
  sensor_id STRING NOT NULL,
  ts INT64 NOT NULL,
  value FLOAT64 NOT NULL
) PRIMARY KEY (sensor_id ASC, ts DESC);

CamusDB also accepts index-style inline constraints inside CREATE TABLE:

CREATE TABLE robots (
  id OID NOT NULL DEFAULT (gen_id()),
  code STRING NOT NULL,
  name STRING,
  PRIMARY KEY (id),
  UNIQUE KEY code_uk (code),
  KEY name_idx (name),
  KEY code_lookup_idx (code) INCLUDE (name)
);

An inline KEY ... INCLUDE (...) creates a covering secondary index. See Indexes for when included columns help a query by letting it skip the primary row fetch.

Schema comments​

Tables, columns, and inline secondary indexes accept an inline COMMENT '<text>' clause, and COMMENT ON sets or removes a comment later. See Schema Comments for the syntax, limits, and where comments appear.

Column storage strategies​

For STRING, BYTES/BLOB, and ARRAY columns, use STORAGE to control whether large values may be compressed or stored outside the row:

CREATE TABLE docs (
  id OID PRIMARY KEY,
  title STRING,
  body STRING STORAGE EXTENDED,
  image BYTES STORAGE EXTERNAL,
  embedding BYTES(3072) STORAGE PLAIN
);

The strategies are EXTENDED, MAIN, EXTERNAL, and PLAIN. The default is EXTENDED.

Change a strategy later with:

ALTER TABLE docs ALTER COLUMN image SET STORAGE PLAIN;

Changing the strategy affects future writes only. To convert existing rows, run:

ALTER TABLE docs REWRITE STORAGE;

See Large Values for the strategy choices, rewrite behavior, downgrade steps, and transaction-limit impact.

Column defaults​

Use DEFAULT (...) to define a default value. CamusDB applies it when an insert omits the column or uses the DEFAULT keyword.

CREATE TABLE events (
  id UUID PRIMARY KEY NOT NULL DEFAULT (gen_uuid_v7()),
  event_name STRING NOT NULL,
  priority INT64 DEFAULT (0)
);

INSERT INTO events (event_name)
VALUES ('robot-created');

INSERT INTO events (id, event_name, priority)
VALUES (DEFAULT, 'robot-updated', DEFAULT);

Most defaults are evaluated once, when the DDL runs, and CamusDB stores the value in the schema. That covers literals and deterministic expressions, including function calls with arguments such as upper('new').

These defaults run again for each inserted row, including each row of a multi-row INSERT:

  • A zero-argument volatile function, such as gen_id(), gen_uuid_v7(), random(), now(), or clock_timestamp().
  • nextval('sequence_name').
Default expressionColumn typeUse
DEFAULT (gen_id())OIDGenerate an ObjectId when the row is inserted.
DEFAULT (gen_uuid_v4())UUID or GUIDGenerate a random UUID when the row is inserted.
DEFAULT (gen_uuid_v7())UUID or GUIDGenerate a time-ordered UUID when the row is inserted.
DEFAULT (random())FLOAT64Generate a random number when the row is inserted.
DEFAULT (now())TIMESTAMPRecord the transaction start time.
DEFAULT (clock_timestamp())TIMESTAMPRecord the time the row is inserted.
DEFAULT (nextval('sequence_name'))INT64Draw the next value from a sequence.

now(), current_timestamp(), and current_date() return the transaction start time, so every row of a transaction gets the same value. See Functions for the full list of volatile functions.

A volatile default must be a bare call with no arguments. CamusDB rejects DEFAULT (random() * 10) and session functions such as current_user(). It also rejects defaults that do not match the column type, such as DEFAULT (gen_id()) on a UUID column.

Identity columns​

Use an identity column when a table needs a readable numeric counter:

CREATE TABLE invoices (
  id OID PRIMARY KEY NOT NULL DEFAULT (gen_id()),
  invoice_no INT64 GENERATED BY DEFAULT AS IDENTITY,
  total FLOAT64 NOT NULL
);

CREATE TABLE tickets (
  id OID PRIMARY KEY NOT NULL DEFAULT (gen_id()),
  ticket_no INT64 GENERATED ALWAYS AS IDENTITY,
  subject STRING NOT NULL
);

GENERATED ALWAYS AS IDENTITY refuses inserts that supply a value for the column. GENERATED BY DEFAULT AS IDENTITY uses the sequence only when the column is omitted. CamusDB also accepts SERIAL and BIGSERIAL as shorthand for an INT64 column backed by an owned sequence.

See Sequences for CREATE SEQUENCE, nextval, currval, setval, ownership rules, and the behavior of cached sequence values.

Column types​

CamusDB columns use types such as OID, UUID, INT64, NUMERIC, FLOAT64, BOOL, STRING, DATETIME, BYTES, and ARRAY(T), plus familiar aliases such as INT, TEXT, and TIMESTAMP. See Data Types for the full type and alias tables, length limits, literal formats, casts, and array rules.

Alter a table​

Add or drop a column:

ALTER TABLE robots ADD COLUMN model STRING NULL;
ALTER TABLE robots ADD COLUMN notes STRING NULL COMMENT 'Operator notes';
ALTER TABLE robots DROP COLUMN model;

Add or drop a primary key:

ALTER TABLE robots ADD PRIMARY KEY (id);
ALTER TABLE robots DROP PRIMARY KEY;

Rename a table​

ALTER TABLE robots RENAME TO machines;

After the rename, the old table name is no longer valid, and the new name resolves to the same table data. Rows and indexes survive the rename because the table's storage identity is not its display name.

Renaming to an existing name fails with TableAlreadyExists. Renaming a table that does not exist fails with TableDoesntExist.

Rename a column​

ALTER TABLE machines RENAME COLUMN name TO display_name;

Renaming a column changes only the stored rows' metadata. Existing values stay available under the new column name, and query results no longer include the old name.

Renaming a column that does not exist fails with UnknownColumn. Renaming to an existing name fails with DuplicateColumn.

Identifier case​

CamusDB keeps the case you use when you create or rename an object, but name lookups ignore case. See Identifiers and case.

Table settings​

Use ALTER TABLE ... SET (...) to update a table-level setting.

ALTER TABLE application_logs
SET (sql_stats_automatic_collection_enabled = false);

ALTER TABLE application_logs
SET (sql_stats_automatic_collection_enabled = true);

sql_stats_automatic_collection_enabled controls whether automatic analyze may refresh the table's statistics. It defaults to true. Setting it to false opts the table out of background statistics collection; a manual ANALYZE TABLE application_logs still runs.

Table settings can also enable row-level TTL:

ALTER TABLE sessions
SET (ttl_expiration_expression = 'expires_at', ttl_job_cron = '@hourly');

ALTER TABLE sessions
RESET (ttl);

See Row-Level TTL for the supported TTL parameters, expiry column rules, and sweep behavior.

Setting names are not case-sensitive. CamusDB rejects unknown setting names.

Drop a table​

DROP TABLE robots;
DROP TABLE IF EXISTS robots;
DROP TABLE robots FORCE;

DROP TABLE removes the table from the active schema immediately, but CamusDB keeps its data as a recoverable orphan for the configured retention window. SHOW TABLES no longer lists the table, and you can reuse the name.

Use SHOW ORPHAN TABLES in the current database to inspect recoverable tables, then recover one under a new name:

SHOW ORPHAN TABLES;
CREATE TABLE robots_recovered RELINK TO 'A0';

The recovered table keeps the rows, indexes, constraints, and column definitions it had when it was dropped.

Use FORCE only when CamusDB must delete the table physically, immediately, and permanently:

DROP TABLE robots FORCE;

A forced drop creates no orphan, so you cannot recover the table. See Recover Dropped Objects for retention settings, recovery examples, and limits.
