Insert, update, delete

This page shows how to add, change, and remove rows with INSERT, UPDATE, and DELETE. The statements look like the ones in PostgreSQL. They include RETURNING, which returns the changed rows in the same round trip. You get generated IDs or new totals with no extra SELECT.

CamusDB also protects against common mistakes. Each statement is atomic: all of its rows are written, or none are. UPDATE and DELETE require a WHERE clause. A missing filter can't change or delete a full table by accident.

Each write is part of a transaction. If you don't open one, CamusDB opens a transaction for the statement and commits it. For work across several statements, see Transactions in SQL.

INSERT​

One statement can insert one row or many:

INSERT INTO robots (id, name, year)
VALUES (GEN_ID(), 'R2-D2', 1977);

INSERT INTO robots (id, name, year)
VALUES
  (GEN_ID(), 'C-3PO', 1977),
  (GEN_ID(), 'T-800', 1984);

A multi-row INSERT is atomic: all rows are inserted, or none are.

Target each column once​

A column can be in an INSERT column list or an UPDATE ... SET list only once. This includes the update part of ON CONFLICT, INSERT ... SELECT target lists, and typed row writes. Names aren't case-sensitive, and SET quantity = 1, Quantity = 2 returns CADB0403 (DuplicateColumn) before any write.

Uncorrelated subqueries can supply INSERT values, UPDATE assignments, and write filters, also in a CASE or a function call. They are evaluated once before the write. Correlated scalar, EXISTS, IN, NOT IN, and quantified subqueries work in UPDATE ... SET and WHERE, and in DELETE ... WHERE. Their outer row is the target row, and they read at the statement timestamp. See subquery rules.

Defaults​

Omit the column from the column list, or write DEFAULT in the values list. Both apply a constant default, such as DEFAULT (2024):

INSERT INTO robots (id, name, year)
VALUES (GEN_ID(), 'K-2SO', DEFAULT);

A default can be a generator, such as DEFAULT (gen_id()) or DEFAULT (gen_uuid_v7()). The function is evaluated for each inserted row, and each row gets a different value. Note that a generator default applies only when you omit the column. The DEFAULT keyword gives NULL for it. For more information, see Tables and columns.

You can also produce an object id inline:

INSERT INTO robots (id, name) VALUES (GEN_ID(), 'R2-D2');
INSERT INTO robots (id, name) VALUES (STR_ID('507f1f77bcf86cd799439011'), 'C-3PO');

GEN_ID() creates a new object ID. STR_ID() reads an existing object ID from its hexadecimal string. See Object ID functions.

INSERT ... SELECT​

Copy a query result into an existing table:

INSERT INTO archived_robots (id, name, year)
SELECT id, name, year
FROM robots
WHERE year < 2000;

CamusDB matches the columns by position. For the full rules, the limits, and time-travel sources, see Copying query results. The same page shows how to create the target table from the query.

Skip or update conflicting rows​

Use ON CONFLICT to handle an existing unique key in the same statement. You don't need a separate check for the row. For example, add each delivery of inventory to the stored quantity:

CREATE TABLE inventory (
  sku STRING NOT NULL,
  quantity INT64 NOT NULL DEFAULT (0),
  location STRING,
  PRIMARY KEY (sku)
);
INSERT INTO inventory (sku, quantity) VALUES ('KETTLE-01', 5)
ON CONFLICT (sku) DO UPDATE
SET quantity = inventory.quantity + excluded.quantity
RETURNING sku, quantity;
┌───────────┬──────────┐
│ sku       │ quantity │
├───────────┼──────────┤
│ KETTLE-01 │ 5        │
└───────────┴──────────┘
Query OK, 1 rows affected (00:00:00.0417096)

The first run inserts quantity 5. Run the same statement again, and the update arm adds 5 to the stored row:

┌───────────┬──────────┐
│ sku       │ quantity │
├───────────┼──────────┤
│ KETTLE-01 │ 10       │
└───────────┴──────────┘
Query OK, 1 rows affected (00:00:00.0111309)

In the update part, bare column names and inventory.column read the stored row. excluded.column reads the proposed row, after defaults, type conversion, and BEFORE INSERT triggers. All SET expressions read the old stored values, and SET a = b, b = a swaps the two values.

To ignore duplicates instead:

INSERT INTO inventory (sku, quantity) VALUES ('KETTLE-01', 5)
ON CONFLICT (sku) DO NOTHING;
Query OK, 0 rows affected (00:00:00.0010853)

The skipped row doesn't count as affected.

The clause comes after VALUES or the source SELECT, and before RETURNING. It also works with identity override clauses.

Choose a conflict target​

The target sets which unique indexes decide whether to skip or update a row:

TargetConflicts handled
ON CONFLICT (a, b)Unique indexes with exactly those columns, in either order.
ON CONFLICT ON CONSTRAINT index_nameThe named unique index. Use <table>_pkey for the primary key.
ON CONFLICT DO NOTHINGAll unique indexes, including the primary key.

DO UPDATE requires a target, and it returns CADB0400 without one. The target must be a unique index that exists and is built. A CHECK or foreign-key constraint can't be a target. A duplicate on another unique index is an error as usual. Unique keys that contain NULL don't conflict, because they have no index entry.

Proposed rows must pass the NOT NULL and CHECK checks before conflict handling. DO NOTHING doesn't skip an invalid row.

Conditional updates and repeated keys​

Add WHERE after SET to update only selected conflicts:

INSERT INTO inventory (sku, quantity) VALUES ('KETTLE-01', 5)
ON CONFLICT (sku) DO UPDATE SET quantity = excluded.quantity
WHERE inventory.quantity < excluded.quantity;

If the condition isn't true, the row is skipped. The update part can't assign a primary-key column. Uncorrelated scalar, IN, and EXISTS subqueries are evaluated once before the writes. Correlated subqueries return an error there.

One DO UPDATE statement can't affect the same stored row or new key twice, also if its condition skipped the first conflict. Two proposed rows with the same key return CADB0400 (InvalidInput). With DO NOTHING, the later copies are skipped after the first insert.

UPSERT shorthand​

UPSERT INTO uses the primary key as its conflict target and replaces each listed non-key column with its proposed value:

UPSERT INTO inventory (sku, quantity)
VALUES ('KETTLE-01', 12)
RETURNING sku, quantity;
┌───────────┬──────────┐
│ sku       │ quantity │
├───────────┼──────────┤
│ KETTLE-01 │ 12       │
└───────────┴──────────┘
Query OK, 1 rows affected (00:00:00.0089565)

This sets the quantity to 12. Columns that aren't in the list have their stored values on update, and their defaults on insert. With no column list, all columns are included. A list with only primary-key columns doesn't change an existing row. Supply the key that you want to match. A new generated primary key doesn't match a different unique key, such as an email address.

Transactions, triggers, and limits​

CamusDB locks the conflicting keys before it checks the latest committed values, also in optimistic mode. Concurrent upserts can return retryable conflicts. Retry the transaction in that case. A duplicate on an index outside the target isn't a retryable result.

Triggers:

  • BEFORE INSERT fires for each proposed row, including a skipped row.
  • A successful insert then fires AFTER INSERT. A conflict that updates fires BEFORE UPDATE and AFTER UPDATE.
  • A skipped row doesn't fire update triggers or AFTER INSERT.
  • AFTER triggers wait until all writes and foreign-key checks of the statement are complete.

RETURNING returns the inserted rows and the new updated rows, in the order of the proposed rows. Skipped rows don't appear. The affected count is the inserts plus the updates. These writes count toward the transaction mutation limit, and skipped rows don't. SQL that a BEFORE INSERT trigger executes counts as usual. Sequence defaults are reserved before the conflict checks, and skipped or updated proposals can use sequence values.

DO NOTHING needs INSERT. DO UPDATE and UPSERT need INSERT and UPDATE, also when no row conflicts. RETURNING also needs SELECT.

On a branch, inherited keys can conflict. An update writes the branch's copy of the row, and the parent doesn't change. Upserts are SQL only: the typed HTTP and gRPC insert APIs don't have an upsert form. These aren't supported: MySQL ON DUPLICATE KEY UPDATE, MERGE, INSERT target aliases, and the name of a user-declared primary-key constraint as a conflict target. Use the primary-key columns or <table>_pkey. UPSERT, CONFLICT, DO, NOTHING, and EXCLUDED can also be identifiers.

UPDATE​

Change selected columns of the rows that match a condition. Columns that aren't in SET don't change:

UPDATE robots
SET name = @name, year = @year
WHERE id = @id
RETURNING id, name, year;

Assignments can use parameters, scalar functions, arithmetic, and existing column values. For example, decrease the inventory if enough stock remains:

UPDATE inventory
SET quantity = quantity - @sold
WHERE sku = @sku AND quantity >= @sold
RETURNING sku, quantity;

Each SET expression reads the values of the row before the update. The assignments happen at the same time, and SET a = b, b = a swaps the values. To set a nullable column to NULL, use SET column = NULL.

Primary-key columns can't change. Updated values must follow the column types, the length limits, and the NOT NULL, CHECK, unique, and foreign-key rules. CamusDB updates the affected indexes and fires the UPDATE triggers of the table. A constraint or trigger failure rolls back the changes of the statement.

Limit updated rows​

Place LIMIT after WHERE, before an optional RETURNING list:

UPDATE robots
SET year = year + 1
WHERE year < 1980
LIMIT @batch_size
RETURNING id, year;

The limit can be an integer literal or a bound integer parameter. LIMIT 0 changes no rows. The limit applies to the candidate rows that the scan finds. A later check for concurrent changes can skip a candidate, and the affected count can be smaller. See concurrent updates and deletes.

UPDATE doesn't support ORDER BY or OFFSET. Don't assume which matching rows a limited update selects. For values from other tables, use UPDATE ... FROM or a subquery:

UPDATE counters
SET n = (SELECT COUNT(*) FROM messages)
WHERE id = @id;

See subquery rules for the supported scalar, IN, and EXISTS forms.

DELETE​

Remove the rows that match a condition, with their index entries:

DELETE FROM robots
WHERE year < 1970
RETURNING id, name;

The affected count is the number of deleted rows. RETURNING returns their values before the delete. Without RETURNING, the statement returns only the count. A foreign key can prevent the delete of a referenced parent row, and a DELETE trigger can reject the delete. See foreign keys and C# triggers.

Use a subquery to select rows based on another table:

DELETE FROM sessions
WHERE id NOT IN (
  SELECT sessionid FROM messages WHERE sessionid IS NOT NULL
);

The IS NOT NULL filter in this example is important. A NULL in the result of the subquery makes the NOT IN condition unknown. See IN and NOT IN. ORDER BY and OFFSET aren't supported. To match rows through other tables, use DELETE ... USING.

Limit deleted rows​

Bound a cleanup operation with a literal or parameterized LIMIT:

DELETE FROM events
WHERE created_at < @cutoff
LIMIT @batch_size
RETURNING id;

The limit comes after WHERE and before RETURNING. It works as for UPDATE: LIMIT 0 deletes no rows, concurrent changes can reduce the affected count, and the order in which rows are selected isn't specified.

For a large cleanup, repeat limited deletes and commit each batch separately. For batched updates, make the condition of each batch exclude the rows that are already done. A repeated SET quantity = quantity + 1 WHERE quantity > 0 LIMIT 100 can select rows that it changed before.

LIMIT doesn't split a statement into transactions, and it doesn't remove the transaction mutation limit. Several limited writes in one explicit transaction share that limit, including the writes of their triggers. LIMIT also doesn't limit how many rows the scan reads to find matches. Index the filter where it helps. Large sets of matching rows can spill to disk.

To delete expired rows continuously, use row-level TTL. To empty a full table, use TRUNCATE. It doesn't delete rows one by one, and its transaction and trigger behavior is different.

UPDATE FROM and DELETE USING​

Use the rows of another table to adjust balances, or to remove the records of closed customers:

UPDATE accounts AS a
SET balance = a.balance + d.amount
FROM deltas AS d
WHERE d.account_id = a.id
RETURNING a.id, a.balance;

DELETE FROM orders AS o
USING customers AS c
WHERE c.id = o.customer_id AND c.closed = true
RETURNING o.id;

Only the target table changes. The FROM or USING list can contain the same sources as a SELECT, such as tables, views, derived tables, CTEs, and joins. For an inline batch, use a VALUES source:

UPDATE accounts AS a SET balance = a.balance + d.amount
FROM (VALUES (1, 25), (2, -10)) AS d (id, amount)
WHERE a.id = d.id;

A target alias also works with no source list: UPDATE accounts AS a SET balance = 0 WHERE a.id = @id. With an alias, qualify the target columns with the alias. A bare column name that the target and a source both have is ambiguous (CADB0400). A self join needs an alias on at least one copy of the target.

Matching and concurrent writes​

The statement collects the matching target keys and source values before it writes. A self join therefore reads the rows as the matching phase found them. Then the statement locks and reads each target row again. The assignments read the current values of that row and the source values collected before. For example, a.balance + d.amount adds the collected amount to the balance read under the lock. All assignments read the same target row from before the update. Subqueries in assignments are computed in the matching phase.

After the lock, CamusDB checks again each AND term that references a target column and contains no subquery. If concurrent changes make a row fail that check, the row is skipped, and it isn't counted. Triggers, constraints, index updates, and transaction limits apply as for regular writes. Under Serializable, the matching phase takes exclusive range locks on the target and source tables. The write phase also takes exclusive locks on the target rows.

If a target row matches more than one source row, an UPDATE returns CADB0400 and doesn't write any row. PostgreSQL picks one of the matches, and it doesn't say which. When several adjustments belong to one row, aggregate the source first:

UPDATE accounts AS a
SET balance = a.balance + d.amount
FROM (SELECT account_id, SUM(amount) AS amount FROM deltas GROUP BY account_id) AS d
WHERE d.account_id = a.id;

A DELETE removes a target row once, also if it matches several source rows.

Joined-write limits​

  • WHERE is required. Use WHERE TRUE when all matching rows must change.
  • LIMIT isn't supported in these forms, or in an UPDATE whose target has an alias. A regular UPDATE and DELETE support it.
  • RETURNING can contain only target columns and expressions on the target. Source columns and a bare RETURNING * return CADB0400. A target alias with no FROM or USING allows RETURNING *.
  • Primary-key assignments, EXPLAIN UPDATE, and EXPLAIN DELETE aren't supported.
  • The statement needs UPDATE or DELETE on the target, and SELECT on each table that it reads, including the target.

USING is a reserved word. Quote a table or column named using with backticks, as in `using`. Longer names such as using_id aren't affected.

RETURNING​

INSERT, UPDATE, and DELETE can return values from the rows they wrote. Add a RETURNING list at the end of the statement.

The examples in this section use this data:

Sample data for the RETURNING examples
CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  customer STRING NOT NULL,
  total NUMERIC NOT NULL
);

CREATE TABLE archived_orders (
  id INT64 PRIMARY KEY,
  customer STRING NOT NULL,
  total NUMERIC NOT NULL
);

INSERT INTO orders (customer, total)
VALUES ('carol', 150), ('dave', 240.50);
INSERT INTO orders (customer, total)
VALUES ('alice', 10), ('bob', 20)
RETURNING id, total * 2 AS doubled;
┌────┬─────────┐
│ id │ doubled │
├────┼─────────┤
│ 3  │ 20      │
│ 4  │ 40      │
└────┴─────────┘
Query OK, 2 rows affected (00:00:00.0187316)
INSERT INTO archived_orders
SELECT * FROM orders WHERE total > 100
RETURNING *;
UPDATE orders
SET total = total * 2
WHERE customer = 'alice'
RETURNING id, total;
┌────┬───────┐
│ id │ total │
├────┼───────┤
│ 3  │ 20    │
└────┴───────┘
Query OK, 1 rows affected (00:00:00.0067243)
DELETE FROM orders
WHERE total > 100
LIMIT 10
RETURNING *;
┌────┬──────────┬───────┐
│ id │ customer │ total │
├────┼──────────┼───────┤
│ 1  │ carol    │ 150   │
│ 2  │ dave     │ 240.5 │
└────┴──────────┴───────┘
Query OK, 2 rows affected (00:00:00.0076340)

In UPDATE and DELETE, the RETURNING list comes after the LIMIT, if the statement has one.

The result has the same shape as a SELECT result: a column schema, then one row for each row that the statement wrote. The affected count is the number of returned rows.

What RETURNING can contain​

The RETURNING list is a select list over the target table. It can contain:

  • *, which expands to all target columns in schema order. In joined writes, a bare * returns an error.
  • A column name, including a qualified name such as orders.total.
  • A scalar expression, such as arithmetic, CASE, a cast, or a scalar function.
  • An alias with AS.
  • A bound parameter.

An item that can't be evaluated once for each written row returns an error before any row is written:

ItemError
An aggregate such as COUNT(*) or SUM(x)CADB0400 InvalidInput
A subqueryCADB0400 InvalidInput
A sequence call such as nextval, setval, currval, or lastvalCADB0547 SequenceCallNotAllowedHere
A name that is not a column of the target tableCADB0404 UnknownColumn

What values come back​

RETURNING returns the stored row, after defaults and type conversion:

StatementRow image
INSERTThe inserted row.
INSERT ... ON CONFLICT, UPSERTInserted rows and new updated rows; skipped rows are omitted.
UPDATEThe new row, after the SET clause.
DELETEThe deleted row.
  • A column that an INSERT doesn't set has its default value.
  • A column that an UPDATE doesn't change has its stored value.
  • A function default, such as gen_id() or now(), is evaluated for each inserted row.
  • A value is returned after conversion to the column type.
  • A column with no value and no default returns NULL.
  • A large value stored outside the row is returned in full.

Inserted rows are returned in insert order. For INSERT ... SELECT, this is the order of the source query. UPDATE and DELETE return rows in the order that CamusDB changes them. Don't depend on that order.

Transactions and retries​

An autocommit write with RETURNING that is sent to a query endpoint uses a read-write transaction. CamusDB commits the write before it sends the schema or any rows. A client doesn't get rows from an attempt that didn't commit, and a Serializable conflict can retry in a new transaction before any rows are sent.

In an explicit transaction, the rows are returned before the final COMMIT, as for any other statement. If the transaction rolls back, the writes are removed.

Privileges​

A write with RETURNING needs the write privilege and SELECT on the target table, because the RETURNING list reads stored values, including defaults. For example, a user with only UPDATE can run a regular UPDATE, but UPDATE ... RETURNING returns an error for that user.

For INSERT ... SELECT ... RETURNING, the source tables also need SELECT, as they do for a regular INSERT ... SELECT.

Size limits​

Returned rows that are collected before the commit also follow max_buffered_result_rows (1,000,000) and max_buffered_result_bytes (256 MiB of estimated memory). Above either limit, the statement returns CADB0556 and rolls back. A streaming query endpoint avoids the gRPC limit for one message, but these limits apply when a write must collect RETURNING rows before the commit. Reduce the batch or the returned columns, or raise the limits. See request resource limits.

The returned rows are in server memory until the statement is complete. max_mutations_per_transaction also limits the number of written rows.

Over gRPC, a buffered reply has all returned rows in one message, and a default gRPC client takes at most 4 MiB per message. If the RETURNING rows would be larger, the statement returns CADB0550 ReturningResultTooLarge before the commit, and it is rolled back.

For large returned row sets, either:

  • Stream the rows: ExecuteStreamReaderAsync() in .NET, or queryStream() in TypeScript.
  • Ask for the count only: ExecuteNonQueryAsync() in .NET, or execute() in TypeScript. The server discards the returned rows. It checks the RETURNING list and the privileges as usual.

See the HTTP API and gRPC API references for the request fields.

Concurrent updates and deletes​

One UPDATE or DELETE statement is protected from concurrent commits to the same row. CamusDB finds the candidate rows, takes exclusive row locks, reads the rows again, evaluates the WHERE clause again, and then computes the write from that locked read.

For example, UPDATE accounts SET balance = balance + 1 WHERE id = ... adds to the latest committed balance of that row. If another transaction changed the row and it no longer matches the condition, or deleted it, CamusDB skips it.

To protect the rows of an earlier read from other writers, use SELECT FOR UPDATE in an explicit transaction.

This protection covers one statement. A read in one statement and a write in a later statement is a read-then-write pattern. Use Serializable for that case, or write the change as one UPDATE.

A WHERE clause is mandatory​

UPDATE and DELETE need a WHERE clause. If you forget the filter, the statement returns CADB0400 and changes no rows. This applies to a bare UPDATE robots SET ... and DELETE FROM robots.

The rule applies to standalone UPDATE and DELETE. An ON CONFLICT DO UPDATE part selects its row through a unique key, and its WHERE is optional.

To change all rows on purpose, write WHERE TRUE:

UPDATE robots SET year = 2000 WHERE TRUE;
DELETE FROM robots WHERE TRUE;

These statements check constraints and run row triggers as usual.

A write to a full table is one transaction, and the transaction limits apply to it. To delete expired rows in batches, use a TTL policy.

To empty a full table, use TRUNCATE. It replaces the key space of the table's rows and reads no rows. The mutation limit doesn't apply to it.
