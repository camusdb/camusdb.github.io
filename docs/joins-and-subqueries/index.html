Joins and subqueries

This page covers queries that read from more than one source: joins, subqueries in a WHERE clause, and subqueries in a FROM clause.

Everything here composes with the clauses in SELECT. Filtering, grouping, sorting, and pagination behave the same way after CamusDB combines the sources.

Join forms​

CamusDB supports these joins in the FROM clause:

FormSyntaxRows returned
InnerA JOIN B ON p or A INNER JOIN B ON pEvery pair of rows for which p is true.
Left outerA LEFT JOIN B ON p or A LEFT OUTER JOIN B ON pEvery inner-join pair, plus one row for each A row with no match, with the B columns set to NULL.
Right outerA RIGHT JOIN B ON p or A RIGHT OUTER JOIN B ON pThe same rows as B LEFT JOIN A ON p.
CrossA CROSS JOIN BEvery pair of rows. No ON clause is allowed.

Joins chain left to right, and a chain can mix forms:

SELECT a.id, b.id, c.id
FROM a
JOIN b ON b.a_id = a.id
LEFT JOIN c ON c.b_id = b.id;

Inner joins​

JOIN and INNER JOIN are equivalent:

SELECT u.email, p.title
FROM app_users u
JOIN posts p ON p.user_id = u.id
ORDER BY u.email, p.title;

Put the join condition in the ON clause, and single-table conditions in the WHERE clause:

SELECT u.email, p.title
FROM app_users u
JOIN posts p ON p.user_id = u.id
WHERE u.role = 'admin' AND p.published = true
ORDER BY u.email, p.title;

Give every source an alias and qualify every column reference. With more than one table in scope, a bare name is ambiguous when both sides define it.

Joins compose freely with grouping:

SELECT u.role, COUNT(*) AS cnt
FROM app_users u
JOIN posts p ON p.user_id = u.id
GROUP BY u.role
ORDER BY u.role;

Outer joins​

A left outer join preserves every row from the left side:

SELECT u.email, p.title
FROM app_users u
LEFT JOIN posts p ON p.user_id = u.id
ORDER BY u.email, p.title;

If a left row has one or more matches, CamusDB returns one row for each match. If it has no match, CamusDB returns one row with every right-side column set to NULL.

The ON clause decides whether a right row matches. The WHERE clause filters after CamusDB has produced the joined rows. This distinction matters for outer joins:

-- Users without a post.
SELECT u.email
FROM app_users u
LEFT JOIN posts p ON p.user_id = u.id
WHERE p.id IS NULL;

-- Users with a published post. The right-side WHERE predicate removes padded rows.
SELECT u.email, p.title
FROM app_users u
LEFT JOIN posts p ON p.user_id = u.id
WHERE p.published = true;

A NULL join key does not match another NULL join key. The comparison NULL = NULL is unknown, so a row with a NULL join key is padded unless another condition in ON matches it.

RIGHT JOIN runs as a left join with the operands swapped. Prefer an explicit column list with RIGHT JOIN: SELECT * follows the executed order, so the preserved table's columns come first.

A RIGHT JOIN whose left operand is itself a join is not supported. Rewrite the query with the preserved table on the left side, often through a derived table.

Cross joins​

CROSS JOIN returns the Cartesian product:

SELECT r.name, c.currency
FROM robots r
CROSS JOIN currencies c;

It is equivalent to the comma form without an equality predicate. When every source is a cross join, CamusDB can still lift an equality from the WHERE clause and plan it as a join predicate.

How joins execute​

For an inner or left outer join with an equality key, the planner picks one of three strategies:

StrategyCamusDB picks it whenCost
Indexed lookupThe right side has an index on the equality column, and the outer side is small.One probe per outer row.
Hash joinThe right side has no usable index, or the outer side is large compared with the indexed side.Builds a hash table from the side estimated to be smaller (the build side), then looks up each row of the other side (the probe side) in it.
Merge joinTwo compatible indexes already return both sides in join-key order, and the outer side is large.Streams both sides, with no build phase.

An equality join without an index uses a hash join rather than scanning the inner table once per outer row. CamusDB plans a nested loop only when the join has no usable equality key, for example ON o.total > c.credit_limit. An equality between columns of different declared types, or on an array column, is not a usable key.

An index on the right side's join column helps most when the outer side is small, because each outer row becomes one index probe.

When a hash join grows too large, it can spill intermediate rows to disk instead of growing memory without bound. That requires spill to disk. With spill to disk off, a hash join whose build side exceeds hash_join_max_build_rows falls back to a nested loop.

In a cluster with distributed queries enabled, CamusDB can broadcast a small hash join build side to the nodes that own the probe table's partitions (the units the cluster divides its data into). Those nodes probe locally and return only the matching rows. The output is the same either way.

For a left outer join, the preserved side must remain the probe side. So CamusDB does not use a broadcast hash join for left outer joins: a remote probe can return matches but cannot produce the padded rows for the preserved side.

Comma joins​

For compatibility, CamusDB supports comma joins. It lifts equality predicates out of the WHERE clause and treats them as join conditions. Predicates on a single source stay filters:

SELECT r.name, u.amount
FROM robots r, user_robots u
WHERE r.id = u.robots_id AND r.enabled = true
ORDER BY u.amount;

Prefer an explicit JOIN ... ON in new code. It separates the join condition from the filters, which makes both easier to read and change.

Current join limits​

CamusDB does not support FULL JOIN, FULL OUTER JOIN, NATURAL JOIN, or JOIN ... USING (...) yet. FULL JOIN is rejected as not supported; the other forms are syntax errors.

A query with an outer join keeps the join order the statement declares. Neither the heuristic planner nor the cost-based join-order search reorders a tree that contains an outer join.

Subqueries in WHERE​

Scalar subqueries​

A scalar subquery returns one column and stands in for a single value:

SELECT id, name
FROM robots
WHERE year = (SELECT MAX(year) FROM robots)
ORDER BY name;

Zero rows give NULL. More than one row is an error.

IN and NOT IN​

IN and NOT IN accept an uncorrelated subquery that returns exactly one column:

SELECT email
FROM app_users
WHERE id IN (
  SELECT user_id
  FROM posts
  WHERE published = true
)
ORDER BY email;

When the inner query is indexed and eligible, CamusDB runs a semi-join for IN (keeping each outer row with at least one match) and an anti-join for NOT IN (keeping each outer row with no match), instead of materializing the full inner result first.

NOT IN follows SQL null semantics. A single NULL in the inner result makes every non-matching row evaluate to unknown. CamusDB drops those rows, and the query commonly returns zero rows. Use NOT EXISTS when the inner column accepts NULL.

CamusDB rejects multi-column and correlated IN or NOT IN subqueries.

EXISTS​

EXISTS works with or without correlation. Only whether a row exists matters, so the inner projection can be *, one column, or several columns:

SELECT email
FROM app_users
WHERE EXISTS (
  SELECT *
  FROM posts
  WHERE posts.user_id = app_users.id
)
ORDER BY email;

For a correlated EXISTS, CamusDB uses an index on the inner table when the inner WHERE clause pins the index's leading columns with equalities. The other side of each equality can be an outer-row value, a literal, or a parameter:

CREATE INDEX posts_user_idx ON posts (user_id);

SELECT email
FROM app_users
WHERE EXISTS (
  SELECT *
  FROM posts
  WHERE posts.user_id = app_users.id
    AND posts.published = true
);

The index only narrows the candidate rows; the full inner predicate still runs after the seek. Without a suitable index, the result is identical, but CamusDB scans the inner table once per outer row.

Derived tables​

A derived table is a parenthesized SELECT inside the FROM clause. It needs an alias:

SELECT post_count
FROM (
  SELECT user_id, COUNT(*) AS post_count
  FROM posts
  GROUP BY user_id
) d
WHERE d.post_count = 2
ORDER BY post_count;

A derived table joins like any other source. That is the usual way to filter a table against per-group aggregates:

SELECT u.email, d.post_count
FROM app_users u
JOIN (
  SELECT user_id, COUNT(*) AS post_count
  FROM posts
  GROUP BY user_id
) d ON d.user_id = u.id
WHERE d.post_count >= 1
ORDER BY u.email;

A derived table's columns take their names from the inner projection. Give every computed column an alias, as in COUNT(*) AS post_count, or the outer query has no usable name to reference.

Check the plan​

Plan choice matters most for queries with several sources. EXPLAIN shows the chosen join strategy and whether CamusDB used an index:

EXPLAIN SELECT u.email, p.title
FROM app_users u
JOIN posts p ON p.user_id = u.id;

See EXPLAIN for the output reference and Query Planning for the rules behind the choice.
