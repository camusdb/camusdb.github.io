Settings reference

This page lists every setting that a CamusDB node accepts, with its default, its type, when a change takes effect, and whether all nodes must agree. Each variable that SHOW VARIABLES lists has an entry here. Use this page to look up a value that you see in that output, or to choose a value before you edit config.yml.

For how to write config.yml, the order in which the configuration layers apply, and the command-line flags, see Configuration.

Most keys are top-level keys in config.yml. Two nested maps have their own tables: Kahuna keys and Diagnostics keys.

The Change column says when a new value takes effect:

  • runtime: you can change the value with SET CLUSTER SETTING, and the next statement or background pass uses it.
  • restart: edit config.yml and restart the node. SET CLUSTER SETTING rejects the key, with six exceptions: it accepts those keys, but the node applies the new value only after a restart. Their rows and notes say so.

The Scope column says whether nodes must agree:

  • cluster: every node must use the same value. A runtime change reaches every node.
  • node: nodes may use different values, set in each node's config.yml. A SET CLUSTER SETTING value still applies to every node and overrides the file.

Sizes are in bytes and durations in milliseconds unless the key name says otherwise (_seconds, _mb).

Request resource limits​

These runtime settings bound the work and state a node accepts. A value of 0 or below disables the corresponding cap.

KeyDefaultUnitChangeScopeMeaning
max_statement_bytes8388608 (8 MiB)UTF-8 bytesruntimenodeMaximum inline SQL before parsing; excess fails with CADB0557, HTTP 413. Bound parameter values are excluded.
max_buffered_result_rows1000000rowsruntimenodeRows held for one buffered response; excess fails with CADB0556.
max_buffered_result_bytes268435456 (256 MiB)estimated bytesruntimenodeMemory estimate for one buffered response; excess fails with CADB0556.
max_open_explicit_transactions10000transactionsruntimenodeOpen explicit transactions per node; excess begins fail with CADB0558, HTTP 503. Autocommit is excluded.
max_client_connections10000connectionsruntimenodeOpen HTTP, HTTPS, and gRPC client connections; excess connections are closed before reading a request. Raft is excluded.
max_databases10000databasesruntimeclusterRegistry capacity for creates, branch creates, and relinks; excess fails with CADB0408.
cluster_activity_max_concurrent_fan_outs8requestsruntimenodeConcurrent SHOW CLUSTER QUERIES/CONNECTIONS requests; excess fails with CADB0558.

Buffered results are checked before commit, so exceeding a cap rolls back the statement. The byte estimate includes in-memory overhead and counts strings at two bytes per character; it is not the JSON payload size. Ordinary streaming reads bypass these result caps. Writes with RETURNING, and locking reads that buffer before autocommit, can still hit them even on a streaming endpoint.

Lowering the connection cap does not close existing connections. Transaction slots are released on commit, rollback, reaping, or a failed begin. Database capacity is checked against each node's registry view: concurrent creates on different nodes can briefly overshoot it, so it is not a strict global quota.

These settings do not impose per-client request rates or a statement execution timeout. A small response can still require a large scan. Prepared statements also have the separate max_prepared_statement_bytes cap. See transaction limits and query activity for operational guidance.

Kahuna keys​

Every key below goes under the kahuna: map. Each one is read once when the node starts, so a change requires a restart, and SET CLUSTER SETTING rejects it. Each node reads its own file; where a row says so, give every node the same value.

"Kahuna default" means the value comes from the storage engine itself.
