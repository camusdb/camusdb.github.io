SELECT

SELECT reads rows from a table and shapes them: you choose the columns, then filter, group, sort, and paginate the rows.

SELECT id, name, year
FROM robots
WHERE year >= 1970
ORDER BY year DESC
LIMIT 25;

This page covers reading from a single table. For joins, subqueries, and derived tables, see Joins And Subqueries. For a SELECT with no table at all, such as SELECT 1 + 1, see SELECT Without FROM.

Clause order​

You must write the clauses in this order, and CamusDB evaluates them in roughly the same order:

SELECT   [DISTINCT] projections
FROM     source [AS OF SYSTEM TIME ...] [@{hint}]
WHERE    row_filter
GROUP BY keys
HAVING   group_filter
ORDER BY sort_keys
LIMIT    n OFFSET m

In practice, WHERE filters input rows before grouping, and HAVING filters the grouped rows after it.

ORDER BY, LIMIT, and OFFSET apply last, to the projected result, so they can reference output aliases.

Select the columns​

SELECT * FROM robots;
SELECT id, name FROM robots;
SELECT r.id, r.name FROM robots r;
SELECT year + 100 AS display_year FROM robots;
SELECT upper(trim(name)) AS display_name FROM robots;

You can project any scalar expression, including function calls and arithmetic.

AS names the output column. Without AS, CamusDB derives the output name from the expression itself. See Functions for the available scalar functions.

DISTINCT​

DISTINCT removes duplicate output rows after projection. Two NULL values count as equal.

SELECT DISTINCT kind FROM robots ORDER BY kind;
SELECT DISTINCT kind, year FROM robots ORDER BY kind, year;

CamusDB does not support these shapes today:

Not supportedReason
COUNT(DISTINCT column)CamusDB does not implement distinct aggregates.
SELECT DISTINCT ... GROUP BY ...Grouping already produces distinct keys.
SELECT DISTINCT COUNT(*)DISTINCT cannot wrap an aggregate projection.

When a compatible NOT NULL index covers the distinct columns, the planner streams the distinct values from that index without building a hash table. EXPLAIN shows which path CamusDB used.

CASE expressions​

CASE picks a value based on conditions. The searched form evaluates its predicates in order:

SELECT
  name,
  CASE
    WHEN year < 1980 THEN 'classic'
    WHEN year >= 1980 THEN 'modern'
    ELSE 'unknown'
  END AS era
FROM robots;

The simple form compares one expression against each WHEN value:

SELECT
  status,
  CASE status
    WHEN 'A' THEN 'active'
    WHEN 'B' THEN 'blocked'
    ELSE 'other'
  END AS status_name
FROM users;

The first match wins. A WHEN condition that evaluates to NULL does not match. If nothing matches and there is no ELSE, the result is NULL.

CASE is a scalar expression, so it works anywhere a scalar expression does, including inside an aggregate. That is the usual way to write a conditional total:

SELECT SUM(CASE WHEN status = 'paid' THEN amount ELSE 0 END) AS paid_total
FROM orders;

CASE and END are reserved keywords. To use one as a column name, see Backticks.

Filter the rows​

SELECT id, name
FROM robots
WHERE year >= 1970 AND name ILIKE 'r%';

SELECT *
FROM robots
WHERE enabled OR year IS NULL;

SELECT year
FROM robots
WHERE year BETWEEN 2001 AND 2004;
CategoryOperators
Comparison=, !=, <, >, <=, >=, BETWEEN ... AND ...
BooleanAND, OR, and a bare boolean column, such as WHERE enabled
Pattern matchingLIKE, ILIKE, ~, ~*, !~, !~*
Null checksIS NULL, IS NOT NULL
MembershipIN (...), NOT IN (...), IN (SELECT ...), NOT IN (SELECT ...)
ExistenceEXISTS (SELECT ...)

BETWEEN is inclusive, so year BETWEEN 2001 AND 2004 matches 2001, 2004, and every year in between.

Pattern matching​

LIKE and ILIKE use the wildcards % and _. ILIKE is case-insensitive.

Use a regular expression operator when wildcards are not enough:

OperatorMatchesCase
~A regular expressionSensitive
~*A regular expressionInsensitive
!~A negated regular expressionSensitive
!~*A negated regular expressionInsensitive
SELECT username
FROM users
WHERE username ~ '^[a-zA-Z][a-zA-Z0-9_]{2,29}$';

SELECT sku
FROM products
WHERE sku !~ '\s';

Patterns are unanchored: they match anywhere in the value unless you write ^ and $.

Both operands must be strings. When either operand is NULL, the result is unknown, so the row does not pass a WHERE clause.

The engine is the .NET regular expression engine. Case-insensitive matching uses the invariant culture. Character classes, quantifiers, anchors, alternation, and groups all work. Use \p{L} or [a-zA-Z], not POSIX classes such as [[:alpha:]].

A malformed pattern raises CADB0400 InvalidInput. Every match runs under an internal timeout, so a pathological pattern fails instead of hanging.

To extract or replace with a regular expression rather than filter, see Regex Functions.

IN lists​

SELECT id, name FROM robots WHERE year IN (2020, 2022, 2024);
SELECT id, name FROM robots WHERE status NOT IN ('deleted', 'archived');
SELECT id, name FROM robots WHERE id IN (@id1, @id2, @id3);

On an indexed column, the planner turns a value list into repeated index probes instead of a scan. That pays off for small and moderate-sized lists.

NOT IN follows SQL null semantics. A NULL in the list makes every non-matching comparison evaluate to unknown, and CamusDB filters those rows out. So NOT IN against a set containing NULL often returns fewer rows than you expect.

IN also accepts a subquery. See Joins And Subqueries.

Aggregate the rows​

FunctionBehavior
COUNT(*)Counts every row.
COUNT(column)Counts non-null values.
SUM(column)Adds numeric values, ignoring nulls. NUMERIC input returns NUMERIC; INT64 input returns INT64; FLOAT64 input returns FLOAT64.
AVG(column)Returns a NUMERIC average for NUMERIC input, otherwise FLOAT64. Ignores nulls.
MIN(column)Returns the smallest non-null value.
MAX(column)Returns the largest non-null value.

Without GROUP BY, an aggregate reduces the whole table to one row:

SELECT COUNT(*), SUM(year), AVG(year), MIN(year), MAX(year)
FROM robots;

GROUP BY​

GROUP BY accepts columns and expressions:

SELECT role, COUNT(*) AS cnt
FROM app_users
GROUP BY role;

SELECT role, department, COUNT(*) AS cnt
FROM app_users
GROUP BY role, department;

SELECT year + 100 AS display_year
FROM robots
GROUP BY year + 100;

Standard projection rules apply: every non-aggregate projection must appear in the GROUP BY. So SELECT name, COUNT(*) FROM robots is an error; add GROUP BY name to fix it.

HAVING​

HAVING filters after aggregation. It can reference an aggregate alias, an aggregate expression, or a group key:

SELECT role, COUNT(*) AS cnt
FROM app_users
GROUP BY role
HAVING cnt > 1
ORDER BY role;

SELECT COUNT(*) AS total
FROM robots
HAVING total > 0;

HAVING needs a GROUP BY or an aggregate projection. To filter input rows rather than groups, use WHERE. It runs first, so it gives the aggregate less work.

Sort and paginate​

SELECT id, name, year
FROM robots
WHERE year >= 1970
ORDER BY year DESC, name ASC
LIMIT 25 OFFSET 50;

ASC is the default. LIMIT and OFFSET accept a literal integer or a placeholder, such as LIMIT @limit.

In a grouped query, ORDER BY can reference a selected aggregate's alias, an aggregate expression, or a grouped expression.

SELECT role, COUNT(*) AS cnt
FROM app_users
GROUP BY role
ORDER BY cnt DESC, role;

An alias in ORDER BY takes precedence over a base column with the same name. In a query without GROUP BY, an ORDER BY expression can also read a column that the SELECT list does not project.

CamusDB refuses two ORDER BY shapes with CADB0400 InvalidInput:

  • An aggregate function in ORDER BY without a GROUP BY clause.
  • In a grouped query, a computed expression that is in neither the SELECT list nor the GROUP BY clause. A grouped query sorts after projection, so the base columns the expression names no longer exist at that point. Project the value first, then sort by its alias.

When an index already provides the requested order, the planner skips the sort entirely. So ORDER BY with LIMIT on an indexed column is much cheaper than sorting the whole table. See Query Planning.

Read a past snapshot​

AS OF SYSTEM TIME reads a consistent historical snapshot. Write it after the FROM source and before the WHERE clause:

SELECT id, name, year
FROM robots AS OF SYSTEM TIME '-10s'
WHERE year >= 1970
ORDER BY year DESC;

The clause applies to read-only statements in autocommit mode. It pins the whole statement, including every join and subquery, to one timestamp. See Time-Travel Reads for the accepted formats and retention limits.

Force an index​

If you know an index suits a predicate better than the planner's estimate suggests, name it:

SELECT id, name
FROM robots@{FORCE_INDEX=robots_year_idx}
WHERE year >= 1980;

Confirm the effect with EXPLAIN before you leave a hint in production code. A hint can outlive the data distribution you tuned it for, and then it does more harm than good.

Parameters​

Placeholders can stand in for values in filters and pagination:

SELECT id, name
FROM robots
WHERE id = @id
LIMIT @limit;

The client that submits the statement binds the values. See Parameters And Prepared Statements.
