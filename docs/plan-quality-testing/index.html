Plan quality testing

The CamusDB.PlanQuality.Tests project detects query-planner changes that keep results correct but make queries perform substantially more work. It runs a fixed corpus against deterministic data, records repeatable execution counters, and compares them with baseline files committed to the CamusDB repository.

This complements correctness tests. A query can return exactly the same rows after a planner change while reading ten times more data. The plan-quality gate is designed to catch that regression.

  • Test project
  • Nightly workflow

What the harness measures​

Each query runs once through EXPLAIN (ANALYZE) for its plan counters and once as an ordinary query for its result.

MeasurementPurpose
Result hashGates correctness. Rows and columns are normalized before hashing.
WorkSum of rows_read, kv_lookups, and kv_scan_entries across plan nodes. This is the primary plan-quality gate.
Statement rows readComes from the slow-query log and includes reads that have no rendered plan node, such as materialized derived sources.
Join steps costedDetects growth in the work performed by join-order search.
Plan fingerprintReports operator and detail changes without unstable estimates or timings.
Join-order pathReports whether planning was cost-based, heuristic, or replayed from cache.
Q-errorCompares estimated and actual rows. The report includes median and maximum error.
Planning and execution timeDiagnostic only; hosted runner timing never gates a build.

The harness deliberately does not compare estimated_cost. A planner change can legitimately change the cost model's units or weights.

What fails the gate​

A run fails when:

  • A query fails or exceeds its timeout.
  • A result hash changes.
  • Work, statement rows read, or join steps costed grows by more than 1.5 times and by more than 100 units for one query.
  • The geometric mean of work ratios across the corpus grows by more than 5%.
  • The corpus and baseline contain different query ids.
  • In the Join Order Benchmark tier, CamusDB returns a different result from SQLite over the same generated rows.

Less work, a different plan with equivalent work, a changed join-order path, and a large q-error change are reported for review but do not fail by themselves.

Test tiers​

TierData and queriesSchedule
Small, scale 1About 42,000 deterministic retail rows and 99 queries covering scans, join shapes, outer joins, and subqueries.Every pull request and push to main, in the Plan-Quality job.
Small, scale 4The same corpus over four times the retail data. It exposes index and join choices hidden at the smaller scale.Nightly.

The retail data deliberately includes skewed foreign keys, correlated columns, duplicate indexed values, NULL values, and a mixture of indexed and unindexed relationships. This makes cardinality and access-path mistakes observable.

The JOB preparation script downloads the query corpus from the pinned Join Order Benchmark revision at runtime and creates matching SQLite results as an independent correctness oracle.

The nightly job​

The plan-quality-nightly GitHub Actions workflow runs every day at 06:30 UTC and can also be started manually for a selected Git ref. It has two independent jobs:

  1. small-tier-large-scale runs the retail corpus at scale 4, with a 35-minute test timeout.
  2. job pins Python 3.12, prepares the synthetic IMDB and SQLite data, and runs the 113 JOB queries with a two-minute timeout per query.

Both jobs upload their Markdown and JSON reports even when the gate fails. Artifacts are retained for 14 days. A red nightly run means the report needs inspection; wall-clock variation alone cannot make it red.

CamusDB versus SQLite and PostgreSQL on the Join Order Benchmark​

The JOB tier keeps a SQLite twin of its data as a correctness oracle. The same rows give a timing reference against two mainstream engines: SQLite, the embedded library, and PostgreSQL 16, the server the benchmark was written for. The CamusDB values below come from one machine on 2026-10-18, on the development tree of 0.15.3, which brings six changes to the estimates since the measurement of 2026-10-17: an equality on a popular value reads the value's share from the histogram; a LIKE pattern is priced from the histogram instead of a 10 percent default; the planner reads a small filtered dimension table at planning time and prices the probes through its actual keys; ANALYZE keeps a list of the most common values of each column, so a join on a skewed key multiplies the popular values as the data does; ANALYZE counts the NULL share of each column, so a join on a key that is NULL in half the rows estimates half the matches and prices half the probes; and the join search bounds the probes of a lookup step by the rows the key's table can still have in the left input, so a left input that a later join multiplied does not pay one probe per row. The SQLite and PostgreSQL values are the ones of 2026-10-17: the same rows, engines and settings. All three engines returned the same row for all 113 queries.

PostgreSQL executes the corpus in 0.74 s and spends 0.72 s to plan it, 2 ms at the median query and 23 to 30 ms on each of the 14- and 17-table queries, where it uses its genetic optimizer. CamusDB plans the same joins in 0.16 s in all, 0.8 ms at the median and 8 to 9 ms on the 17-table queries; the median was 0.3 ms on 2026-10-17, and the difference is the read of a small filtered dimension table at planning time. The first query of a run, 1a, pays 44 ms of just-in-time compilation in its planning time. On the heaviest queries the executor gap is the whole story: 16c and 16d take 35 ms in PostgreSQL and 74 and 71 ms in CamusDB, 6d 11 ms against 152 ms, and 15d 130 ms against 201 ms. PostgreSQL is faster than SQLite on 40 queries and 1.4x faster at the geometric mean; the two agree on where the hard queries are. CamusDB is faster than PostgreSQL on eleven queries, among them 28b (0.8 ms against 60 ms) and 29b (0.5 ms against 8 ms), where PostgreSQL's genetic optimizer misses the empty start that the exhaustive search over reachable subsets finds, and 19d (74 ms against 91 ms).

The first measurement, on the release before these changes, took 45.6 s with a geometric mean ratio of 80x. The probe of a non-unique index asked the store for a 512-entry page on every outer row, and the store materialized the whole page. The probe bound and the end key brought the time per unit of work down by half, to 29 s. The allocation diet cut the allocation of a run from 22.7 GB to 15.9 GB. The join-order search over reachable subsets then planned the nine widest queries, which the heuristic had ordered badly, and took the total from 28 s to 13 s. The memo of the probed keys took it to 7.5 s: an outer stream that repeats a key, every cast row of one movie for example, now reads the store once for it. The batched probes and Kahuna's inline scan page then halved the processor time of a run, from 13 s to 6 s, and the per-probe step cost in the join search took the total to 6.1 s, with 31 queries faster by a fifth or more against 7 slower by that much. ANALYZE statistics for the columns without an index then cut the rows read over the corpus by 38 percent: the seven slower queries had been priced from a 10 percent default on filters such as keyword = '…', and now read their distinct counts. That was the tree of 2026-10-17, at 3.9 s.

The six estimate changes since then moved the plans of 88 queries. They made the estimates right where they were wrong by orders of magnitude: the queries with a plan node estimated more than 100 times off went from 44 to 2, and those more than 1,000 times off from 7 to 1. The work moved both ways: 29 queries read less (33a and 33c nine times less, 30b six times, 31b, 23a and 21a four times) and 49 read more (16a three times, 6e three times, 17a and 17e twice), for 10 percent more work over the corpus. The corpus took 3.5 s against 3.9 s: the 88 queries whose plan changed took 2.5 s against 3.0 s, and the 25 whose plan did not change took the same time as before. The queries that read more are those where a probe into a wide table, name or char_name, became a hash join once the left input was estimated right: the step cost puts the two within a few percent of each other there, and the measured time says the probe wins by a fifth. The remaining gap to the measured plans is in that break-even, the price of a memo hit, not in the estimates.

Where the rest of the gap comes from​

CamusDB spends about 1.6 µs for each row read or index entry scanned at the median query. The ratio to SQLite falls as the query grows, because the fixed cost of a probe weighs less against the rows it returns:

Work of the queryQueriesMedian CamusDBMedian SQLiteMedian ratio
under 1,000130.3 ms< 0.1 ms10x
1,000 to 10,000754.2 ms0.3 ms9x
10,000 to 100,0002574 ms23.1 ms6x

The comparison cannot split that gap between plan choice and the cost of each row, because SQLite reports no counter equivalent to work. The flat cost per unit of work shows that the gap is not a fixed cost per query. The CamusDB rows go through an embedded transactional key-value store with MVCC, and through the plan-node counters of EXPLAIN (ANALYZE); SQLite reads B-tree pages in process. Measured on the retail data set at scale 4, a scanned row costs about 0.55 µs, a probe of a unique index 2 to 5 µs with the row it returns, and a probe of a non-unique index about 10 µs with its rows, of which about 6 µs is the store's seek for one key. The join search prices the probes that way, and the per-row cost of a scan does not depend on the table enough to change a decision: a scanned row of name costs 1.5 µs against 0.85 µs for char_name, but a probe into the same table costs more by the same factor, so the ratio the hash-or-probe decision depends on stays where the model has it.

The estimates of the cost-based path are within a factor of 1.1 of the actual rows at the median plan node, from 1.75 on 2026-10-17. Two of the 113 queries have one plan node with a q-error above 100, 28a at 1,240 and 15d at 166, from 44 before; the rest of the top five are 19c at 72, 29c at 62 and 26b at 54. The two that remain are chains through the most popular movies, where the pair-wise join estimate cannot see that the same few titles carry most of the rows of every table in the chain.

Run it locally​

Run the same small tier used on pull requests:

dotnet test CamusDB.PlanQuality.Tests/CamusDB.PlanQuality.Tests.csproj \
  --filter TestCategory=PlanQuality

The default report is written below CamusDB.PlanQuality.Tests/bin/Debug/net10.0/plan-quality/. Set PLAN_QUALITY_REPORT_DIR to choose another location.

Run the larger retail tier:

PLAN_QUALITY_SCALE=4 dotnet test \
  CamusDB.PlanQuality.Tests/CamusDB.PlanQuality.Tests.csproj \
  --filter FullyQualifiedName~SmallTierGate

Run the JOB tier after preparing its data:

scripts/plan-quality/job/prepare.sh /tmp/camusdb-job 0.003

JOB_DIR=/tmp/camusdb-job JOB_SCALE=0.003 dotnet test \
  CamusDB.PlanQuality.Tests/CamusDB.PlanQuality.Tests.csproj \
  --filter FullyQualifiedName~JobTierGate

Use PLAN_QUALITY_ONLY with a comma-separated set of query ids while investigating a subset. Partial runs never update a baseline.

Read a report​

The generated report contains:

  • Gate failures and non-blocking notes.
  • Work grouped by query tags.
  • Before-and-after fingerprints for changed plans.
  • Queries with the worst cardinality estimates.
  • Planning and execution timings for diagnosis.

The JSON report preserves every counter for every plan node and is useful for automated comparison or deeper analysis.

Updating a baseline​

When an intentional planner change moves plans, regenerate the corresponding baseline:

PLAN_QUALITY_UPDATE_BASELINE=1 dotnet test \
  CamusDB.PlanQuality.Tests/CamusDB.PlanQuality.Tests.csproj \
  --filter FullyQualifiedName~SmallTierGate

Before writing a baseline, the harness runs each query against a reference configuration with cost-based access-path and join-order search disabled. If a result differs or a query fails, it writes nothing.

Commit the baseline change with the planner change and explain why each plan moved. Baselines exist separately for small scales 1 and 4 and JOB scales 0.001 and 0.003.

Repeatability and scope​

The data generators are seeded, table loads occur in a fixed order, and the harness disables automatic analyze, row-id, plan, and result caches, and TTL. It runs ANALYZE explicitly and enables the slow-query log at a zero threshold to obtain statement-level reads. A determinism test repeats counters across fresh engines.

The harness currently runs on one node. It does not cover broadcast joins, distributed gathers, or placement decisions. Wall time is reported but not graded, and some reads performed while binding subqueries are not represented by plan-node counters.
