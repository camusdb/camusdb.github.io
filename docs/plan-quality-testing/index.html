Plan quality testing

The CamusDB.PlanQuality.Tests project detects query-planner changes that keep results correct but make queries perform substantially more work. It runs a fixed corpus against deterministic data, records repeatable execution counters, and compares them with baseline files committed to the CamusDB repository.

This complements correctness tests. A query can return exactly the same rows after a planner change while reading ten times more data. The plan-quality gate is designed to catch that regression.

  • Test project
  • Nightly workflow

What the harness measures​

Each query runs once through EXPLAIN (ANALYZE) for its plan counters and once as an ordinary query for its result.

MeasurementPurpose
Result hashGates correctness. Rows and columns are normalized before hashing.
WorkSum of rows_read, kv_lookups, and kv_scan_entries across plan nodes. This is the primary plan-quality gate.
Statement rows readComes from the slow-query log and includes reads that have no rendered plan node, such as materialized derived sources.
Join steps costedDetects growth in the work performed by join-order search.
Plan fingerprintReports operator and detail changes without unstable estimates or timings.
Join-order pathReports whether planning was cost-based, heuristic, or replayed from cache.
Q-errorCompares estimated and actual rows. The report includes median and maximum error.
Planning and execution timeDiagnostic only; hosted runner timing never gates a build.

The harness deliberately does not compare estimated_cost. A planner change can legitimately change the cost model's units or weights.

What fails the gate​

A run fails when:

  • A query fails or exceeds its timeout.
  • A result hash changes.
  • Work, statement rows read, or join steps costed grows by more than 1.5 times and by more than 100 units for one query.
  • The geometric mean of work ratios across the corpus grows by more than 5%.
  • The corpus and baseline contain different query ids.
  • In the Join Order Benchmark tier, CamusDB returns a different result from SQLite over the same generated rows.

Less work, a different plan with equivalent work, a changed join-order path, and a large q-error change are reported for review but do not fail by themselves.

Test tiers​

TierData and queriesSchedule
Small, scale 1About 42,000 deterministic retail rows and 99 queries covering scans, join shapes, outer joins, and subqueries.Every pull request and push to main, in the Plan-Quality job.
Small, scale 4The same corpus over four times the retail data. It exposes index and join choices hidden at the smaller scale.Nightly.
JOB, scale 0.003About 225,000 synthetic IMDB rows and all 113 Join Order Benchmark queries.Nightly.

The retail data deliberately includes skewed foreign keys, correlated columns, duplicate indexed values, NULL values, and a mixture of indexed and unindexed relationships. This makes cardinality and access-path mistakes observable.

The JOB preparation script downloads the query corpus from the pinned Join Order Benchmark revision at runtime and creates matching SQLite results as an independent correctness oracle.

The nightly job​

The plan-quality-nightly GitHub Actions workflow runs every day at 06:30 UTC and can also be started manually for a selected Git ref. It has two independent jobs:

  1. small-tier-large-scale runs the retail corpus at scale 4, with a 35-minute test timeout.
  2. job pins Python 3.12, prepares the synthetic IMDB and SQLite data, and runs the 113 JOB queries with a two-minute timeout per query.

Both jobs upload their Markdown and JSON reports even when the gate fails. Artifacts are retained for 14 days. A red nightly run means the report needs inspection; wall-clock variation alone cannot make it red.

The join-order path decides the worst cases​

The cost-based join-order search covers joins of at most 12 tables. Nine JOB queries join 14 or 17 tables: 28a to 28c, 29a to 29c, and 33a to 33c. They take the heuristic order. These nine queries hold 26% of the CamusDB time and 32% of the work.

Join-order pathQueriesCamusDBSQLiteWorkGeometric mean ratio
Cost-based search10433.8 s7.2 s3,965,48061x
Heuristic, more than 12 tables911.8 s< 0.1 s1,884,4721,968x

Query 29b shows the difference. SQLite starts from the two 4-row comp_cast_type tables and the 405-row complete_cast table. It then probes title by primary key with the title and year filters, and the join is empty after a few steps. The whole query takes less than 0.1 ms. The CamusDB heuristic starts from aka_name and cast_info through the person index. It reads 108,728 entries of cast_info, keeps 3,966 rows after the note filter, and hash-joins the other 15 tables. It reads 412,459 rows and entries for the same empty result and takes 4.0 s.

CamusDB is faster on 15c and 15d. There SQLite starts from aka_title and expands through movie_companies, movie_keyword and movie_info before it applies the selective LIKE filter on movie_info, and takes 2.9 s and 2.8 s. CamusDB starts from info_type and movie_info with that filter first. It takes 57 ms on 15c and 1.3 s on 15d.

Where the rest of the gap comes from​

CamusDB spends about 8 µs for each row read or index entry scanned, at every query size. The ratio to SQLite is therefore similar for small and large queries:

Work of the queryQueriesMedian CamusDBMedian SQLiteMedian ratio
under 1,000104 ms< 0.1 ms132x
1,000 to 10,0005024 ms0.2 ms87x
10,000 to 100,00040199 ms2.7 ms70x
over 100,000131,423 ms31.2 ms89x

The comparison cannot split that gap between plan choice and the cost of each row, because SQLite reports no counter equivalent to work. The flat cost per unit of work shows that the gap is not a fixed cost per query. The CamusDB rows go through an embedded transactional key-value store with MVCC, and through the plan-node counters of EXPLAIN (ANALYZE); SQLite reads B-tree pages in process.

The estimates of the cost-based path are within a factor of 3.5 of the actual rows at the median plan node. 29 of the 113 queries have one plan node with a q-error above 100, and 12 have one above 1,000. The worst are the 17-table queries 29a to 29c, which do not use the estimates for their join order.

Run it locally​

Run the same small tier used on pull requests:

dotnet test CamusDB.PlanQuality.Tests/CamusDB.PlanQuality.Tests.csproj \
  --filter TestCategory=PlanQuality

The default report is written below CamusDB.PlanQuality.Tests/bin/Debug/net10.0/plan-quality/. Set PLAN_QUALITY_REPORT_DIR to choose another location.

Run the larger retail tier:

PLAN_QUALITY_SCALE=4 dotnet test \
  CamusDB.PlanQuality.Tests/CamusDB.PlanQuality.Tests.csproj \
  --filter FullyQualifiedName~SmallTierGate

Run the JOB tier after preparing its data:

scripts/plan-quality/job/prepare.sh /tmp/camusdb-job 0.003

JOB_DIR=/tmp/camusdb-job JOB_SCALE=0.003 dotnet test \
  CamusDB.PlanQuality.Tests/CamusDB.PlanQuality.Tests.csproj \
  --filter FullyQualifiedName~JobTierGate

Use PLAN_QUALITY_ONLY with a comma-separated set of query ids while investigating a subset. Partial runs never update a baseline.

Read a report​

The generated report contains:

  • Gate failures and non-blocking notes.
  • Work grouped by query tags.
  • Before-and-after fingerprints for changed plans.
  • Queries with the worst cardinality estimates.
  • Planning and execution timings for diagnosis.

The JSON report preserves every counter for every plan node and is useful for automated comparison or deeper analysis.

Updating a baseline​

When an intentional planner change moves plans, regenerate the corresponding baseline:

PLAN_QUALITY_UPDATE_BASELINE=1 dotnet test \
  CamusDB.PlanQuality.Tests/CamusDB.PlanQuality.Tests.csproj \
  --filter FullyQualifiedName~SmallTierGate

Before writing a baseline, the harness runs each query against a reference configuration with cost-based access-path and join-order search disabled. If a result differs or a query fails, it writes nothing.

Commit the baseline change with the planner change and explain why each plan moved. Baselines exist separately for small scales 1 and 4 and JOB scales 0.001 and 0.003.

Repeatability and scope​

The data generators are seeded, table loads occur in a fixed order, and the harness disables automatic analyze, row-id, plan, and result caches, and TTL. It runs ANALYZE explicitly and enables the slow-query log at a zero threshold to obtain statement-level reads. A determinism test repeats counters across fresh engines.

The harness currently runs on one node. It does not cover broadcast joins, distributed gathers, or placement decisions. Wall time is reported but not graded, and some reads performed while binding subqueries are not represented by plan-node counters.
