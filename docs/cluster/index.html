Cluster mode

CamusDB runs standalone by default: one process on one machine. A standalone node is simple, but it is a single point of failure. If the machine stops, the database stops. If the disk fails, the data that is not in a backup is lost.

Cluster mode runs CamusDB on several nodes that act as one database. It keeps a copy of each write on more than one node, so the database continues to serve reads and writes when one node fails, and no committed write is lost.

Why use cluster mode​

Use cluster mode when one of these needs applies:

  • High availability. The application must continue to work when a machine fails, restarts for maintenance, or loses its network. A three-node cluster continues to commit while one node is down.
  • Durability on more than one machine. A write must survive the loss of a disk or a whole server. CamusDB confirms a commit only after a majority of the nodes holds the change. By default every node holds every partition. When you set kahuna.replication_factor, each partition lives on that many nodes, and the majority is of those replicas.
  • More capacity. One machine has a limit on CPU, memory, and disk. A cluster spreads the data and the work across several machines. See Key-range sharding and Distributed queries.

You do not need cluster mode for local development, tutorials, or quick tests. A standalone node is enough, and it starts with one command. SQL and transaction guarantees are the same in both modes, so an application can move from standalone to a cluster without changing its queries.

How cluster mode works​

In cluster mode, CamusDB:

  1. Divides the data across the nodes into partitions. A partition is one part of the database's key space.
  2. Elects one leader for each partition. The leader coordinates writes to that partition.
  3. Replicates each write through the Raft consensus algorithm. Consensus means that a majority of a partition's copies agree on each change before CamusDB commits it.

How distribution works and Multi-active availability give the details.

To run a cluster on Kubernetes, use the Kubernetes Operator. It creates the nodes and manages their membership for you.

CamusDB is in production use, but cluster mode is still evolving. Its APIs and storage formats can change between versions.

Run a standalone node​

Standalone is the default. It needs no cluster configuration:

dotnet tool install --global CamusDB.Server
camusdb

Use standalone mode for local tutorials, quick experiments, and single-node development.

Run a local cluster​

The source repository includes a Docker Compose file for a three-node cluster:

docker compose -f docker/local.yml up --build

The three nodes start on a private bridge network:

NodeHTTP SQL endpointHTTPS endpointgRPC endpointRaft port
camus1localhost:5095localhost:7141localhost:60957070
camus2localhost:5096localhost:7142localhost:60967072
camus3localhost:5097localhost:7143localhost:60977074

Point camus-cli at any of the three nodes. The table shows host ports; inside the network, every node listens on the defaults: HTTP 5095, gRPC 5096, and HTTPS 7141. The client gRPC API is on by default. Configure it per node with grpc_enabled and grpc_port.

Run a cluster node manually​

Each node needs --mode=cluster, a unique node name, its Raft host and port, the partition count, and the Raft address of every other node. List only the other nodes, never the node itself. Put these values in a config.yml file or pass them as flags. This is the first of three nodes, one per machine:

camusdb \
  --mode=cluster \
  --raft-nodename=camus-1 \
  --raft-host=192.168.1.10 \
  --raft-port=7070 \
  --http-port=5095 \
  --initial-cluster-partitions=3 \
  --initial-cluster 192.168.1.11:7070 192.168.1.12:7070 \
  --http-peers 192.168.1.11:5095 192.168.1.12:5095

The other two nodes run the same command with their own name and host, listing the remaining two addresses.

FlagPurpose
--configExplicit YAML configuration file. A missing explicit file is a startup error.
--modestandalone or cluster.
--raft-nodenameUnique node name in the cluster.
--raft-nodeidNumeric Raft node id.
--raft-hostHost address for Raft communication.
--raft-portPort for Raft communication.
--http-portHTTP API listener port.

--initial-cluster-partitionsNumber of Raft partitions to initialize.

A flag overrides the equivalent YAML value only when you supply it. The same settings in YAML look like this:

data_dir: /data/
mode: cluster
node_name: camus-1
raft_host: 192.168.1.10
raft_port: 7070
initial_partitions: 3
http_port: 5095
peers:
  - 192.168.1.11:7070
  - 192.168.1.12:7070
http_peers:
  - 192.168.1.11:5095
  - 192.168.1.12:5095

Give each node its own persistent data_dir. The Docker Compose setup mounts a separate volume for each node.

See Configuration for every YAML key and every flag.

How distribution works​

  • CamusDB divides the data across the Raft partitions.
  • Each partition elects its own leader.
  • Every node exposes the database API.
  • CamusDB routes reads and writes to the partition that owns the target key range.
  • Reads see only committed row versions. CamusDB keeps several versions of each row (MVCC), so a read sees a consistent snapshot.
  • Writes use locks, write intents (provisional values that become visible only at commit), and atomic commit.
  • A write across more than one partition uses two-phase commit.

Every row of a table lives under the same key prefix, so ordered table scans still work. The storage layer handles partition ownership and replication.

By default, the node that receives a query executes the whole query, reading remote pages through the storage locator. Turn on distributed queries to change that. CamusDB then splits an eligible scan into one fragment per partition and runs each fragment on the node that owns the rows, so filters and aggregates apply before the data crosses the network.

Multi-active availability​

There is no single active process that can fail. An application talks to any node it can reach, and CamusDB routes each write to the leader that can commit it safely.

Compare this with older models:

ModelWrite pathFailure behavior
Active/standbyOne active nodeA standby must become active before writes continue
Classic active-activeAny nodeNeeds conflict resolution to prevent a divergent state
CamusDBAny node, routed to the partition leaderThe remaining members of the partition elect a new leader

A write on a three-node cluster with one partition follows these steps:

  1. Node A is the partition leader.
  2. A client sends a write to node B.
  3. CamusDB routes the write to node A.
  4. Node A replicates the change through Raft.
  5. The transaction can commit after a majority accepts the change.
  6. Nodes B and C elect a new leader if node A fails later.

Consistency before split-brain writes​

A partition needs enough healthy members to reach consensus. When it cannot reach consensus, it stops all commits rather than accept a change that could conflict with another copy of the same data.

Availability is useful only while the data stays correct, so CamusDB takes the unavailable side of that trade.

Serializable isolation is the default in a cluster, exactly as on one node. See Transactions And Isolation for the guarantees and Distributed Transactions And HLC for the cross-partition commit protocol.

Configuration uses the same machinery. CamusDB commits each SET CLUSTER SETTING change through Raft on its own partition, so every node applies settings in the same order, and a node that was down catches up on replay. There is no rolling restart, and no node keeps a stale value.

Transfer partition leadership​

Operators and reliability tests can ask a data partition's current leader to hand leadership to another replica:

POST /v1/cluster/transfer-leadership
Content-Type: application/json

{ "partitionId": 1, "targetEndpoint": "10.0.0.3:7072" }

The request is a graceful handoff, not a crash failover. Send it to the node that currently leads the partition. targetEndpoint is the replica's Raft address (raft_host:raft_port), as shown in the placement table. The target must host the partition as a voter, a replica that takes part in elections and commits.

The response returns 200 when the target is observed as leader before the call returns. A non-success handoff returns 409 with a body that includes status and reason, such as NodeIsNotLeader, LeaderAlreadyElected, or Refused.

With authentication enabled, the endpoint requires a superuser. With authentication disabled, it is loopback-only, like other cluster mutation routes.
