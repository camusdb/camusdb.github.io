Caraxes chaos testing

Caraxes is the test harness that attacks CamusDB on purpose. It starts a real cluster in Docker, sends SQL load to it, and injects faults such as crashes and network splits. Then it checks that no committed data was lost or corrupted, and it gives a PASS or FAIL verdict with the evidence.

Unit tests on one node can't show what happens when a leader dies during a commit or a disk stalls under load. Caraxes makes these events repeatable and checks the result. It lives in the camusdb-caraxes repository and generates load with CamusDB.Workload.

A PASS is evidence about one run. It shows that one build, cluster shape, workload, and fault schedule passed the checks for the measured window.

Caraxes has found or guarded against these failures:

  • Bank transfers that changed the total balance under contention, which means a transfer wasn't atomic.
  • Scans that returned short counts while writes were in flight. A check after the run couldn't see them.
  • Acknowledged writes that were overwritten when two nodes applied different values at the same revision.
  • Bugs in crash recovery, re-election, rejoin, and leader transfer.
  • Wrong behavior on a full or stalled disk.
  • Placement, range-split, and leader-balancer bugs that appear only when all partitions carry work.
  • False performance results caused by host disk behavior, a saturated client, or a comparison of runs from different builds.

Quick start​

You need:

  • .NET 10 SDK
  • Docker with docker compose
  • A CamusDB checkout, by default at ~/camusdb

Run the commands on this page from the root of the Caraxes repository:

dotnet run --project Caraxes -- run --scenario scenarios/smoke-optimistic.yml

Caraxes builds the node image from docker/Dockerfile in your CamusDB checkout. This means that a run tests the code on your disk. CI can use the exit code directly. See Exit codes.

How a run works​

run does the full cycle:

  1. Publishes CamusDB.Workload from the CamusDB checkout.
  2. Starts the cluster and waits until all nodes are ready.
  3. Seeds the dataset.
  4. Waits settle_seconds (default 30) for partition leadership to settle.
  5. Starts the measured workload, with the fault schedule in parallel.
  6. Collects workload results, node metrics, logs, and crash dumps.
  7. Matches faults with errors, writes the verdict, and removes the cluster.

The workload is a one-shot container on the cluster's Docker network. It connects to the nodes over TLS by their in-cluster names, and you don't have to change certificate trust on the host.

Useful flags:

  • --tag <name> stores the run in a separate directory, runs/scenarios/<scenario>-<tag>. If you omit it, a run replaces the previous one.
  • --skip-build reuses the existing image.
  • --run-root <dir> sets the directory for run output. The default is ./runs.
  • --correctness-only shows recovery time and throughput recovery but doesn't fail the run on them. Use it on CI machines of unknown speed. The correctness checks apply as usual.

Scenario files​

A scenario is one YAML file. Its name is required and uses the pattern [a-z0-9][a-z0-9-]*:

name: bank-kill
cluster:
  name: bank-kill
  nodes: 3
  replication_factor: 3
  locking: optimistic
  isolation: read_committed
workload:
  kind: bank
  rows: 20000
  target_ops: 400
  duration: 60s
nemesis:
  seed: 7
  events:
    - { at: 20s, fault: kill, target: random, duration: 20s }
checks:
  max_recovery_seconds: 45

workloadThe load to generate. See Workloads.

A duration can be 250ms, 15s, 1m, or 1h. A bare number means seconds.

Workloads​

Each workload kind has a different correctness check. Choose the kind by the failure that you want to catch.

kindWhat it doesWhat it catches
accountsRead-modify-write on rows that don't conflict. The default.Throughput limits and recovery after faults.
bankTransfers money between any two rows, across partitions.A changed SUM(balance), which means a transfer wasn't atomic. This check is always on.
fanoutBank transfers between two different tables. Needs tables: 2 or more.The same as bank, with load on all partitions. Use it for split, placement, and failover tests.
tokensEach write deletes a row and inserts its successor in one transaction.Lost deletes, lost inserts, a deleted row that comes back, double spends, and stale index entries.
appendElle list-append transactions.Lost updates, write skew, read skew, dirty reads, and reads of aborted writes.
rwElle read-write registers: single-row reads and blind writes.The same anomalies on point reads and writes, through the primary key, a scan, an index, or a join.
predicateReads groups of rows with a WHERE clause and writes rows into groups.Phantoms and write skew on predicate reads, and a COUNT(*) that disagrees with the rows read.

A conserved sum can't detect all wrong orderings of transactions. The Elle kinds cover that gap.

Live scan probe. scan_probe_interval: 5s sends SELECT COUNT(*) to each gateway node during the run. A short count fails the run. This catches scan bugs that appear only while writes are in flight.

Delete workload. With the tokens kind, a table has exactly tokens rows (default 2,000) at each committed state. Each move reads a row through a non-unique index, deletes it, and inserts the next version. The index isn't unique, and only the engine's conflict detection prevents a double spend. After the run, each slot must have exactly one row at the expected version.

Range splits. With key_range_sharding: true and split thresholds in the kahuna: block, fanout gives ranges enough keys to split. A node with wrong split settings starts as normal, and no split happens. Set checks.require_split: true to fail the run as VACUOUS when no split happened. VACUOUS means that the run didn't test what it claims to test. See Key-range sharding.

Isolation checks with Elle​

Elle is the isolation checker from the Jepsen project. The append, rw, and predicate workloads record each attempt in history.edn. After the run, Elle searches that history for dependency cycles that the isolation level forbids.

Build and check the Elle jar once:

tools/elle/build.sh     # builds elle-cli with Elle 0.2.8 in Docker
tools/elle/validate.sh  # runs it against histories with known verdicts
dotnet run --project Caraxes -- run --scenario scenarios/append-smoke.yml

build.sh builds the jar in Docker, and it stops with an error for a jar with a different Elle version. The last elle-cli release bundles Elle 0.2.7, which has a defect in its read-write register checker. The host needs Docker, git, and unzip.

What fails the run, by isolation level:

LevelForbidden
Read committedG0, G1a, G1b, G1c (write cycles, aborted reads, intermediate reads, and circular information flow).
SerializableAll of the above, plus G-single, G2-item, G2, lost updates, internal inconsistency, and a predicate COUNT(*) mismatch when both reads share one transaction snapshot.
All levelsFinal-state errors. See the next paragraph.

By default, the model follows the isolation level: read-committed for read committed runs, and serializable for the others. The cluster default isolation is read_committed. Neither model requires real-time order, and a read-only snapshot can lag behind a write that already returned. Set elle.consistency_models: strict-serializable if you want to test real-time order.

Final-state check. After the writers stop, the workload reads back each key it wrote and compares it with its log of attempted writes:

  • A list must contain each acknowledged append exactly once.
  • A register must have a value that an acknowledged or unresolved write produced.
  • The primary key, the index, and the join must return the same value.
  • A row count over the key range detects duplicate primary keys.

How statements reach the server. txn_mode sends the same transactions through a different server path:

  • explicit (default): BEGIN, one round trip per statement, then COMMIT.
  • autocommit: each statement is a separate transaction.
  • pipeline: all statements in pipelined frames.

rw_access: secondary and rw_access: index don't work in pipeline mode.

Runs with too little history. A stuck cluster can pass with almost no history. checks.min_committed_txns fails such a run as VACUOUS. workload.stop_after_completed ends the run after a fixed number of operations. The run length then doesn't depend on machine speed.

workload:
  kind: rw                  # or append, predicate
  rw_key_type: int64        # int64 | string | numeric
  rw_access: pk             # pk | secondary | index | join
  txn_mode: explicit        # explicit | autocommit | pipeline
  stop_after_completed: 0   # 0 runs the whole duration
checks:
  min_committed_txns: 1000
elle:
  gated: true               # false reports findings without failing the run
elle keyDefaultMeaning
enabledtrueRun the check. false gives no isolation verdict.
jartools/elle/elle-cli-0.1.11-elle0.2.8-standalone.jarPath to the elle-cli jar that build.sh builds.
imageeclipse-temurin:21-jdkDocker image that supplies java. It must be a JDK image.
consistency_modelsderivedEmpty uses serializable, or read-committed for read committed runs.
anomaliesnoneExtra anomalies to search for, such as G1a,G1b.
gatedtruefalse shows Elle findings as MEASURED, NOT GATED.
cycle_search_timeout_msElle defaultRaise it if Elle returns unknown.
heap_mbJVM defaultJVM heap for long histories.
plotsfalseCycle diagrams. Needs an image with Graphviz.

Elle writes elle-result.json. valid? = true passes, and false fails. unknown also fails, because the search didn't prove the model.

Faults​

The nemesis block injects faults while the workload is in progress. Event times count from the start of the workload container, which includes the warmup (default 15 s). Caraxes lines up each fault with the per-second results in intervals.csv by UTC time.

Each event has an at time (default 0s), a fault, a target (default random), and a duration (default 10s). nemesis.seed defaults to 1.

FaultWhat it doesHeals by
killKills the node process (SIGKILL).Restarting the container.
stopStops the node cleanly (SIGTERM).Restarting the container.
pauseFreezes the process (SIGSTOP). Connections stay open.Resuming the process.
partitionCuts the node off from all peers.Removing the firewall rules.
slowAdds network latency. Set delay_ms, default 100.Removing the delay.
lossDrops packets. Set loss_percent, default 10.Removing the loss.
fill-diskFills /data until the disk is full.Deleting the filler file.
slow-diskThrottles the node's disk I/O.Removing the throttle.
clock-skewMoves the node's wall clock by offset_ms (default +10 s).Restoring real time.
leader-transferHands the node's partition leadership to other nodes. Set to to pick one.No heal needed.
remove-nodeDrains the node from the cluster, then stops it.It isn't healed. This is a permanent scale-down.
backupTakes an online backup under load.No heal needed.
add-nodeBoots a replacement node that joins the cluster.The node catches up and becomes a voter.
sqlExecutes one SQL statement, such as an online schema change.No heal needed.
disk-corruptKills the node (SIGKILL) and damages one data file on its volume. See Storage corruption.Restarting the node.
splitSplits one key space of a table at its median key. See Range splits.No heal needed. The fault window closes after duration.

Targets:

  • A node name, such as camus2.
  • random: a node picked from the seed, which makes the run reproducible.
  • leader: the node that leads the most partitions when the event fires.
  • zone:<name>: all nodes in that failure zone, together.

Set heal: false to leave a fault in place for the rest of the run. When the workload ends, Caraxes heals the open faults that it can heal. A fault with heal: false and a remove-node fault stay in place.

A seeded random schedule gives a chaos soak in place of a fixed timeline:

nemesis:
  seed: 42
  random:
    faults: [kill, pause, partition, slow, slow-disk]
    min_interval: 10s
    max_interval: 18s
    duration: 12s

count limits the number of faults. The default, 0, injects faults until the workload ends. The defaults for the other keys are min_interval: 10s, max_interval: 20s, and duration: 10s. A random schedule can't pick the sql fault.

Disk faults​

fill-disk needs cluster.data_tmpfs_mb, which puts /data on a size-capped RAM disk. The full node must refuse writes with CADB0536 (InsufficientDiskSpace). After the space is free, it must accept writes again, and it must not need a restart. A RAM disk is lost on restart, so this fault tests disk pressure only.

slow-disk throttles the real disk behind the node's data volume. The process, the network, and the peers stay healthy. The default write_bps: 4096 acts as a paused disk, and a few MiB per second acts as a slow disk. write_iops and read_bps (default 0, no limit) add more limits. device sets the MAJ:MIN of the disk, which Caraxes finds by default. slow-disk doesn't work with data_tmpfs_mb.

nemesis:
  events:
    - { at: 4m, fault: slow-disk, target: camus1, duration: 30s }
    - { at: 7m, fault: slow-disk, target: camus2, duration: 60s, write_bps: 2097152 }

Storage corruption​

disk-corrupt kills the node with SIGKILL, damages one data file on its volume, and restarts the node when the fault heals. It doesn't work with data_tmpfs_mb. Caraxes records each damage in runs/clusters/<cluster>/storage-damage/storage-damage.jsonl.

KeyDefaultMeaning
damage(required)bit-flip, truncate-tail, truncate-middle, chunk-shuffle, chunk-duplicate, or chunk-replace.
damage_layerstorestore for the key-value store, or wal for the Raft log.
damage_filesstsst (the largest), live-log, closed-log, or manifest.
damage_seed1Seed of the damage, for a reproducible run.
damage_count2Bits for bit-flip, or chunks for chunk-shuffle. Other damages ignore it.

See scenarios/corrupt-store-sst-bitflip-rf1.yml and scenarios/corrupt-store-sst-bitflip-rf3.yml.

Clock skew​

clock-skew needs cluster.clock_skew: true. It moves only the node's wall clock. offset_ms can't be 0, and it must be within ±12 hours. That clock feeds CamusDB's hybrid logical clock and the timeouts built on it. Raft elections use a separate clock, and the fault doesn't affect them. The bundled scenarios test jumps above 5 seconds, above 15 seconds, and of several minutes. A ±2 second run is the control.

cluster:
  clock_skew: true
nemesis:
  events:
    - { at: 15s, fault: clock-skew, target: camus1, duration: 20s, offset_ms: 10000 }

Range splits​

split divides one key space of a table in the workload database at its median key. At the scheduled time, it calls POST /v1/cluster/split-range. It asks the target node first and then the other nodes, follows the leader hint, and retries refusals that can clear with time. The run fails if a scheduled split didn't commit or didn't start.

KeyDefaultMeaning
split_tableworkload_accountsThe table to split.
split_index(row space)An index of the table to split. primary or <table>_pkey names the primary index.
split_timeout_seconds60Time limit for one split event.
split_retries60Attempts, half a second apart.

See scenarios/bank-split-kill-window.yml.

Backups and node replacement​

With cluster.backups: true, the backup fault takes backups during the load, and Caraxes grades their cost. backup_kind is incremental (the default), full, or coordinated.

backup_verify then checks that no data was lost:

  1. Take a final incremental backup after the load stops.
  2. Read a fingerprint of the live data: row count, SUM(balance), and SUM(version).
  3. Restore the backup chain and start the cluster from it.
  4. Read the fingerprint from each node and compare it with the live one.

The fingerprint includes SUM(version) because transfers don't change SUM(balance). SUM(version) grows with each write, and it detects a restore that lost the latest writes.

add-node replaces a node that is gone for good. By default, it seeds the new node from the backup chain. The node replays the backup and then receives the newer changes from the cluster. Set seed_from_backup: false to start the node empty and send it a full snapshot. node_name sets the name of the new node. The default is the next free index. The new node must become a voter, host the expected partitions, and read the same data as the other nodes.

nemesis:
  events:
    - { at: 20s,  fault: backup,   target: camus1, duration: 5s }
    - { at: 40s,  fault: kill,     target: camus3, heal: false }
    - { at: 100s, fault: add-node, target: camus1, duration: 5s }

See Backup and restore.

Online schema changes​

The sql fault executes one statement on a node during the workload, such as CREATE INDEX or ALTER TABLE ... ADD COLUMN. The sql key holds the statement. sql_timeout_seconds (default 1800) limits one statement, and it must cover the backfill of the largest table. Schedule kills around it to crash the node that applies the change. Retryable errors are retried up to sql_retries times (default 10). expect sets the required result: ok (default), error, or any.

After the workload, schema_verify checks that:

  • All nodes report the same schema, and the schema is stable.
  • An index contains the same rows and values as the table.
  • A new column has its default value in each row.
  • No foreign key points to a missing parent row.
  • The workload saw no errors that it couldn't retry.
  • With require_resume: true, a node logged that it resumed the interrupted change. If that log line is missing, the kill missed the change, and the run fails as VACUOUS.

See scenarios/schema-add-column-kill.yml and scenarios/schema-index-kill.yml.

Verdict​

A scenario passes when:

  • The workload accepted the run, and its correctness checks held.
  • The run had no internal errors. In a scenario with a nemesis block, internal errors are reported in errors.json, and they don't fail the run by themselves.
  • All rules in checks passed.

For each fault, Caraxes measures three values: the peak error rate, whether the workload completed operations during the fault, and the time from heal until the error rate falls to 1 percent or below. It writes the results to analysis.md and scenario.json.

- In-fault: error rate 40.45 %, write p99 392.9 ms (0.3x baseline)
- Max recovery time: 5.5 s; all healed faults recovered: yes

Capacity evidence​

A throughput number alone is easy to misread. Caraxes records the context that explains it:

FileShows
cluster-facts.jsonThe build, settings, and data placement on each node. Don't compare two runs with different fingerprints.
node-metrics.csv, bottleneck-report.mdWork per node, the commit path, and backlog growth. They show when one leader does all the writes.
client-resources.jsonThe load generator's CPU, memory, and thread-pool backlog. Use it to check that a slow result isn't caused by the client.
host-io.csvHost disk behavior during the run.
precondition.jsonThe warmup data written to put the host disk in its steady state.

Don't compare runs across disk setups: a RAM disk, a preconditioned disk, and a disk that wasn't preconditioned. Each setup is a different baseline.

To set a baseline, repeat a scenario at least three times and combine the results:

for i in 1 2 3; do
  dotnet run --project Caraxes -- run --scenario scenarios/capacity-baseline.yml --tag r$i
done

CamusDB.Workload baseline --runs \
  runs/scenarios/capacity-baseline-r1/artifacts/run,\
  runs/scenarios/capacity-baseline-r2/artifacts/run,\
  runs/scenarios/capacity-baseline-r3/artifacts/run

baseline sets a baseline when it has at least three comparable runs and their coefficient of variation is 10 percent or less. It also reports the spread between runs, as context. CamusDB.Workload compare returns an error for two runs from different builds or workload shapes. See Workload utility.

Matrix sweeps​

A matrix tests each combination of settings and writes one report:

dotnet run --project Caraxes -- matrix --matrix scenarios/matrix-resilience.yml

A matrix file has base cluster, workload, and checks blocks, plus axes. It can also set elle, teardown, and settle_seconds. Each cell is a separate scenario with a separate cluster.

axes:
  locking: [optimistic, pessimistic]
  nemesis:
    - name: none
    - name: kill
      seed: 7
      events:
        - { at: 20s, fault: kill, target: random, duration: 20s }

The axes are locking, isolation, txn_mode, nodes, sharding, parallelism, workers, and nemesis.

--list-cells prints the cell names, and --correctness-only works as for run. With --cell <name>, each CI job can test one cell. The sweep writes matrix-report.md and matrix.json, and it exits with a nonzero code if a cell failed.

Leader-balance test​

This test checks the leader balancer on an idle cluster:

dotnet run --project Caraxes -- leader-balance --spec scenarios/leader-balance.yml

It kills the node that leads the most partitions, restarts it, and checks that the balancer moves leadership back. The test passes when the node gets back at least half of its fair share and the leadership spread is close to even. leader-balance takes --skip-build.

Cluster commands​

These commands manage a cluster outside a test run:

dotnet run --project Caraxes -- up --spec scenarios/cluster-3.yml       # start and wait until ready
dotnet run --project Caraxes -- status --spec scenarios/cluster-3.yml   # health and placement
dotnet run --project Caraxes -- logs --spec scenarios/cluster-3.yml --node camus2
dotnet run --project Caraxes -- down --spec scenarios/cluster-3.yml     # remove containers and volumes

up takes --skip-build and --ready-timeout <seconds> (default 180). down takes --keep-volumes. logs takes --tail <lines> (default 200).

Nodes are named camus1 to camusN. Node i publishes REST on host port 15095 + i - 1 and gRPC on 16095 + i - 1. A Caraxes cluster can then run next to a local server on ports 5095 and 5096.

Workload keys​

workload keys map to CamusDB.Workload flags. Chaos runs test behavior under faults, and the defaults put less load on the cluster than the defaults of the standalone tool.

Artifacts​

Each run writes to runs/, or to the directory that --run-root sets. You can delete the files, but they are the evidence for the verdict. scenario.json records the CamusDB commit that Caraxes built. Use it to trace a verdict back to its code.

PathContains

runs/scenarios/<name>/analysis.mdFault analysis in readable form.

runs/scenarios/<name>/node-health.csv/ping samples per node.
runs/scenarios/<name>/artifacts/run/Workload results: summary.md, intervals.csv, errors.json, reconciliation.json, metrics, and node logs.

The scenarios/ directory has more files for specific investigations.

GitHub Actions runs these on a schedule:

  • Nightly append: the Elle list-append scenarios except append-autocommit.yml and append-pipeline.yml, plus the bank split and placement scenarios and bank-split-kill-window.yml.
  • Nightly Elle: the rw, predicate, and append matrices with no faults, plus single-node kill runs.
  • Weekly Elle volume: each Sunday, one of six matrix-elle-volume-* files, chosen by ISO week. Each cell runs up to one million committed transactions, with a 4-hour limit.

Not covered yet: block-device faults through device-mapper, because they need root access on the host.
