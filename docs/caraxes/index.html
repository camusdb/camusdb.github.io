Caraxes

Caraxes is the reliability and chaos-testing harness for CamusDB. It builds a Docker cluster from a declarative YAML spec, drives SQL load through CamusDB.Workload, injects faults while the load runs, and turns the collected artifacts into a PASS or FAIL verdict.

Use it when you want evidence rather than an opinion about how a build behaves under a node kill, a network partition, a full disk, or the loss of a whole failure zone.

The harness lives in its own repository, next to a CamusDB checkout. It builds the node image from the CamusDB repository's docker/Dockerfile, so a run always tests the code you have on disk.

Requirements​

  • .NET 10 SDK
  • Docker with docker compose
  • A CamusDB checkout, ~/camusdb by default

Every command below is run from the Caraxes repository root.

Cluster lifecycle​

Four commands manage a cluster on its own, without any workload:

# build the image, generate artifacts, start the fleet, wait until every node is ready
dotnet run --project Caraxes -- up --spec scenarios/cluster-3.yml

# per-node health plus the cluster's partition placement table
dotnet run --project Caraxes -- status --spec scenarios/cluster-3.yml

# one node's container logs
dotnet run --project Caraxes -- logs --spec scenarios/cluster-3.yml --node camus2

# stop the cluster and remove its containers, network, and volumes
dotnet run --project Caraxes -- down --spec scenarios/cluster-3.yml

up regenerates the dev certificate when the certificate SAN parameters changed, such as the node count or the subnet. It then rebuilds the image, writes one config.yml per node and a compose file under runs/<cluster>/, starts the fleet, and polls GET /v1/cluster/health until every node reports ready. Pass --skip-build to reuse the existing image, and --ready-timeout <seconds> to change the 180 second readiness deadline.

down removes the data volumes unless you pass --keep-volumes. The run directory is disposable output: the spec is the source of truth, so down regenerates the compose file and works even after you delete runs/.

Nodes are named camus1 through camusN. Node i publishes its REST port on host port 15095 + i - 1 and its gRPC port on 16095 + i - 1. Those bases are high on purpose, so a Caraxes cluster coexists with a local development server on the usual 5095 and 5096.

Cluster spec​

A cluster spec is one YAML file. Only name is required; every other key has a default.

name: rf3-baseline
nodes: 3
partitions: 3
replication_factor: 3
placement_rebalancer: true
leader_balancer: true
locking: optimistic
isolation: read_committed
diagnostics: true
KeyDefaultMeaning
name(required)Lowercase [a-z0-9-] identifier. Names containers, volumes, the compose project, and the derived image tag.
nodes3Node count.
partitions3Initial cluster partitions.
replication_factor3Per-partition replica-set size. 0 keeps full replication, where every node hosts every partition.
placement_rebalancertrueRepair under-replication, trim over-replication, and smooth skew on join or leave.
leader_balancertrueSpread partition leadership using load reports.
zones[]One failure-zone label per node, parallel to the node list. Empty means zone-unaware placement.
lockingoptimisticMaps to CamusDB default_transaction_locking.
isolationread_committedMaps to CamusDB default_isolation_level.
key_range_shardingfalseMaps to CamusDB key_range_sharding.
distributed_query_executionfalseMaps to CamusDB distributed_query_execution. See Distributed Queries.
max_query_parallelism1Maps to CamusDB max_query_parallelism.
diagnosticstrueTurns on OpenTelemetry and the Prometheus /metrics endpoint on every node.
subnet10.101.0First three octets of the cluster's /24 bridge network.
first_ip2Last octet of node 1. Node i gets first_ip + i - 1.
base_rest_port15095Host port of node 1's REST API.
base_grpc_port16095Host port of node 1's gRPC API.
base_raft_port7070Raft port of node 1. Node i advertises base_raft_port + 2 * (i - 1). Not published to the host.
spare_certs5Extra certificate SAN entries, so a node added later is covered without regenerating certificates.
data_tmpfs_mb0When above zero, each node's /data is a size-capped tmpfs of this many MiB instead of a named volume. Required by the fill-disk fault.
camusdb_repo~/camusdbPath of the CamusDB checkout that supplies the Dockerfile, the certificate script, and the build context.
image(derived)Image tag. Empty derives caraxes/camusdb:{name}.
kahuna{}Raw passthrough into the generated config's kahuna: section, for engine knobs the spec does not model.

The spec is validated before anything starts. A bad name, a zones list whose length does not match nodes, a malformed subnet, a /24 too small for the nodes plus the spare certificates, an unknown locking or isolation value, or a port outside 1 to 65535 all fail fast with a message that names the offending key. A spec error exits with code 2.

Running a scenario​

A scenario is one self-contained file that embeds a cluster: block, a workload: block, and optionally a nemesis: block and a checks: block.

dotnet run --project Caraxes -- run --scenario scenarios/smoke-optimistic.yml

The run verb performs the whole cycle:

  1. Publish CamusDB.Workload from the CamusDB checkout.
  2. Bring the cluster up and wait until every node is ready.
  3. Seed the dataset with CamusDB.Workload init.
  4. Drive the measured run, with the nemesis schedule in parallel when there is one.
  5. Collect artifacts, correlate faults, and write the verdict.
  6. Tear the cluster down, unless the scenario sets teardown: false.

It exits 0 on PASS and 1 on FAIL, so CI can gate on it directly. Teardown runs even when the workload fails, because a sweep that leaves a fleet running on every failure exhausts the machine.

The workload runs in a one-shot container attached to the cluster's Docker network. That container is based on the node image, which already trusts the baked development CA, and each node's certificate covers its camusN DNS name. The workload therefore reaches every node over TLS with no host-side trust changes.

name: smoke-optimistic
cluster:
  name: smoke-opt
  nodes: 3
  partitions: 3
  replication_factor: 3
  locking: optimistic
  isolation: read_committed
workload:
  database: caraxes
  rows: 20000
  mode: open
  target_ops: 400
  workers: 32
  duration: 60s
  warmup: 15s
  read_percent: 60
  write_percent: 40
teardown: true

Workload block​

The workload: keys map onto the flags of CamusDB.Workload. The defaults are lighter than that tool's own, because a chaos scenario runs many of them and cares about behavior under fault rather than about peak throughput.

KeyDefaultMeaning
kindaccountsaccounts for shard-disjoint read-modify-write, bank for contended transfers with a conserved-balance invariant.
databasecaraxesDatabase the scenario seeds and drives. init creates it when it is absent.
seed1847Dataset and workload seed.
rows100000Seeded row count.
payload_bytes256Payload size per row.
batch500Rows per seeding transaction.
modeopenopen for a fixed arrival rate, closed for saturation.
target_ops500Open-loop submitted operations per second.
workers32Concurrent workers.
read_percent / write_percent60 / 40Operation mix. The two must add up to 100.
writes_per_transaction1Writes per write transaction.
duration60sMeasured window.
warmup15sUnmeasured warmup.
drain10sDrain period after the measured window.
connections8Client connections.
max_in_flight4096Concurrency ceiling.
locking(inherits)Empty inherits the cluster's locking.
isolation(inherits)Empty inherits the cluster's isolation.
no_auto_preparefalseDisables automatic prepared statements.

Durations accept 15s, 1m, 250ms, and 1h. A bare number means seconds. The same parser serves the workload block and the nemesis block, so a scenario reads consistently.

Fault injection​

A nemesis: block drives faults concurrently with the workload. Every event is timed from the start of the measured run, so a fault window lines up with the workload's own per-second series.

nemesis:
  seed: 7
  events:
    - { at: 20s, fault: kill, target: random, duration: 20s }

Fault kinds​

FaultWhat it doesHeals by
killSIGKILL the node's process. No graceful shutdown, so it exercises crash recovery and re-election.Restarting the container.
stopGraceful stop: SIGTERM, then SIGKILL after Docker's grace period. Models a planned bounce.Restarting the container.
pauseFreeze the process with SIGSTOP. The node stops answering while its TCP connections stay open, which exercises suspicion timeouts rather than connection resets.SIGCONT.
partitionIsolate the node from every peer with iptables DROP rules in both directions.Flushing the node's filter table.
slowAdd one-way latency with tc qdisc netem. Set delay_ms (default 100).Removing the qdisc.
lossAdd packet loss with tc qdisc netem. Set loss_percent (default 10).Removing the qdisc.
fill-diskWrite a filler file into /data until the mount returns ENOSPC.Deleting the filler.
remove-nodeDrain the node through POST /v1/cluster/leave, then stop the container.Never. This is a one-way scale-down.

Set heal: false on an event to hold a fault open for the rest of the run. A kill then becomes crash-then-repair, where the cluster must re-replicate around a node that never comes back.

Every healable fault still in effect when the workload finishes is healed on the way out, using a fresh cancellation token. The cluster is never left partitioned, throttled, or full. Injection and healing are best-effort: a Docker hiccup is logged to the timeline and swallowed rather than failing the run it decorates.

Targets​

A target is a node name such as camus2, the keyword random, or zone:<name>. A zone target expands to every node in that failure zone, and the fault applies to each of them, so kill of a zone takes the whole zone down together. Random picks are drawn from the schedule's seeded generator, so a nemesis run reproduces exactly.

Random soaks​

The alternative to an explicit events: timeline is a seeded random: soak. A schedule may use one form or the other, never both.

nemesis:
  seed: 42
  random:
    faults: [kill, pause, partition, slow]
    min_interval: 10s
    max_interval: 18s
    duration: 12s

The soak picks a fault from the menu for a random node every min_interval to max_interval, holds it for duration, and repeats until the workload ends. Set count to cap the number of injections.

Disk faults​

fill-disk needs a size cap to mean anything, so the cluster must set data_tmpfs_mb. Each node's /data then becomes a RAM-backed, size-capped tmpfs the fault can exhaust. Size it with headroom. A tmpfs only slightly larger than CamusDB's min_free_disk_bytes write-admission watermark keeps free space below the watermark run-wide once the dataset is seeded, which leaves no clean baseline to compare the fault against.

The filled node is expected to refuse new writes cleanly with CADB0536 (InsufficientDiskSpace) and to resume admitting writes on its own once the disk is freed, with no restart. Because tmpfs is lost on restart, this fault is for disk-pressure behavior and not for durability.

Verdict​

A scenario passes when the workload accepted the run, reconciliation held, internal errors are explained, and every resilience check passed.

Reconciliation is the real consistency guard: it checks committed versions, row counts, and accounting after the run. Internal errors are graded by context. With no fault injected, an internal error is unexplained and fails the run, since the workload's own validity does not catch a server-side defect. Under a fault, a few client-side disposal races as connections are torn down are expected collateral, so they are reported loudly but do not by themselves flip a consistent, reconciled run to FAIL.

Resilience checks​

For a run with faults, Caraxes correlates the fault timeline with the workload's per-second intervals.csv, aligned by the wall-clock anchor the workload writes to run-meta.json. Each fault window then yields a peak error rate, whether the workload kept completing operations, and a recovery time measured from the heal until the error rate returns to near zero.

checks:
  max_recovery_seconds: 45
  require_recovery: true
  require_progress_under_fault: true
KeyDefaultFails the run when
max_recovery_seconds45A healed fault took longer than this to recover.
require_recoverytrueA healed fault never recovered before the run ended.
require_progress_under_faulttrueA fault window completed zero operations, meaning a total outage.

A second counts as recovered once its error rate is at or below 1 percent. The baseline uses the median of the clean seconds rather than the mean, because the recovery tail after a heal sits outside the fault window and would otherwise inflate the bar it is judged against. The in-fault figures stay means, since there the whole window's degradation is the point.

The correlation is written to analysis.md and to scenario.json:

# Fault analysis — bank-kill

- Baseline (clean seconds): error rate 0.00 %, write p99 1,382.0 ms
- In-fault: error rate 40.45 %, write p99 392.9 ms (0.3x baseline)
- Max recovery time: 5.5 s; all healed faults recovered: yes

| fault | healed | window (s) | peak error | failed | progressed | recovery (s) |
|---|---|---|---|---|---|---|
| kill/camus2 | yes | 20.3 | 100 % | 4,074 | yes | 5.5 |

Bank-transfer invariant​

workload.kind: bank replaces the shard-disjoint baseline with transfers between two rows drawn from the whole keyspace. That produces real write-write contention, absorbed with a bounded retry.

Every transfer conserves total balance and commits atomically, so SUM(balance) must be unchanged after the run. A changed sum is direct evidence of an atomicity break. This invariant is checked after the run and is never waived. Conflicts under fault are expected; a broken sum is a correctness failure a chaos run exists to catch.

name: bank-kill
cluster:
  name: bank-chaos
  nodes: 3
  partitions: 3
  replication_factor: 3
workload:
  kind: bank
  database: caraxes
  rows: 20000
  mode: closed
  workers: 32
  duration: 60s
  warmup: 15s
  read_percent: 50
  write_percent: 50
nemesis:
  seed: 5
  events:
    - { at: 20s, fault: kill, target: random, duration: 20s }
checks:
  max_recovery_seconds: 45
teardown: true

Matrix sweeps​

A matrix runs a cartesian sweep and writes a cross-cell report.

dotnet run --project Caraxes -- matrix --matrix scenarios/matrix-resilience.yml

A matrix file holds a base cluster:, workload:, and checks: block plus an axes: block. Cells are the product of the axes. Every axis is optional, and an unset axis contributes the base value alone.

AxisVaries
lockingoptimistic and pessimistic.
nodesCluster node count.
shardingkey_range_sharding on and off.
parallelismmax_query_parallelism.
nemesisNamed fault presets. A preset with no events or random is a fault-free baseline column.
axes:
  locking: [optimistic, pessimistic]
  nemesis:
    - name: none
    - name: kill
      seed: 7
      events:
        - { at: 20s, fault: kill, target: random, duration: 20s }

Every cell shares one image, built once, because cells differ only in runtime configuration. Cells run sequentially through the ordinary scenario path, so a cell behaves exactly like a hand-written scenario, and the fault behavior of one cell cannot perturb another. Each cell gets its own cluster name, so containers and volumes never collide.

The sweep writes matrix-report.md and matrix.json, lining up each cell's verdict, maximum recovery time, latency inflation, and first failure note. A cell that throws is recorded as a failure and the sweep continues. The exit code is non-zero when any cell failed.

Leader-balance test​

This test targets the Raft leader balancer directly, without a workload.

dotnet run --project Caraxes -- leader-balance --spec scenarios/leader-balance.yml

It measures how partition leadership is spread, where each node self-reports the partitions it leads through a LeaderLocal flag on GET /v1/cluster/placement. It then kills the node leading the most partitions, so those leaderships pile onto the survivors, restarts it, and watches whether the balancer moves leadership back.

The test passes when the rejoined node regains at least half its fair share and the final spread is near even. Half the fair share is a lenient bar on purpose, because the balancer is load-weighted and moves gradually. With the balancer off the rejoined node stays at zero, which is what makes this a test of the balancer rather than of re-election.

It waits up to 90 seconds for leadership to settle, 30 seconds after the kill for re-election, and up to 150 seconds after the restart for the balancer to act, polling every 5 seconds. Use the kahuna: passthrough to shorten the balancer's own intervals so it gets several passes inside that window:

name: leaderbal
nodes: 3
partitions: 9
replication_factor: 3
leader_balancer: true
kahuna:
  leader_balancer_interval_ms: 10000
  leader_balancer_report_interval_ms: 2000
  leader_balancer_report_ttl_ms: 8000
  min_leader_stability_ms: 2000

The test writes leader-balance.md and a per-poll leaders.jsonl:

# Leader-balance test — leaderbal

Verdict: **PASS** — fair share ~3/node, rejoined node regained up to 2, final imbalance 2.

| time | camus1 | camus2 | camus3 | resolved |
|---|---|---|---|---|
| 16:43:32 | 3 | 5 | 1 | 9/9 |
| 16:44:03 | 5 | 0 | 4 | 9/9 |
| 16:44:08 | 3 | 2 | 4 | 9/9 |

Artifacts​

Everything a run produces lands under runs/, which is disposable output.

PathHolds
runs/<cluster>/Generated compose.yml and one config/camusN.yml per node, for a cluster started from a bare spec.
runs/clusters/<cluster>/The same, for the cluster embedded in a scenario.
runs/scenarios/<name>/scenario.jsonThe run manifest: cluster and workload settings, the CamusDB commit under test, exit codes, the verdict, and the fault analysis.
runs/scenarios/<name>/analysis.mdFault correlation in readable form.
runs/scenarios/<name>/timeline.jsonlOne line per injection, heal, error, and note, each stamped with a UTC timestamp and an offset from the nemesis start.
runs/scenarios/<name>/artifacts/run/The workload's own artifacts: summary.json, summary.md, intervals.csv, errors.json, reconciliation.json, manifest.json, and run-meta.json.
runs/matrix/<name>/matrix-report.md, matrix.json, and one cell directory per combination.
runs/leader-balance/<cluster>/leader-balance.md and leaders.jsonl.

scenario.json records the short commit hash of the CamusDB checkout that was built, so a verdict can always be traced back to the code it judged.
